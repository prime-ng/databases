## How to read this document

Each algorithm gets a **deep section** with these subsections:

1. **The decision in one sentence** — the question the algorithm is answering.
2. **State at entry** — what's already in memory when this step starts.
3. **The exact rule** — the formula or pseudocode, no hand-waving.
4. **Worked example** — a small concrete scenario, with state evolving step by step.
5. **Edge cases & boundaries** — what unusual input does, where the design breaks down.
6. **Interactions with other algorithms** — what feeds it, what it feeds, and where the data flow is non-obvious.
7. **Where the bugs lurk** — the pathological cases you should test for.

Two algorithms get **extra-deep** treatment because their interactions are non-obvious and the most common source of "why did the timetable do that?" questions:

- **§10 LPT teacher pick + alternative-teacher retry** (the multi-phase teacher state model).
- **§12 Backtracking + constraint cache** (why the cache is cleared, and what could be smarter).

Symbols used in worked examples:
- `Card[A:5]` = a card from activity A, instance 5 of weekly periods.
- `T1, T2, ...` = teachers.
- `Slot(Mon, 3)` = day Monday, period index 3.
- `🟢` = placed cleanly. `🟡` = placed with a soft warning. `🔴` = force-placed (conflict). `⚫` = unplaced.

## Pipeline reminder (1 line each)

```
1.  Capacity Audit                — gate
2.  Reference Load                — snapshot
3.  Class Teaching Window         — per-class allowed slot range
4.  Constraint Load               — DB rows → Hard/Soft objects
5.  Parallel Group Load+Validate  — combined-class invariants
6.  Daily Target Build            — per-class floor/ceil per day
7.  Teacher Weekly Cap Build      — per-teacher max
8.  Activity Expansion            — weekly periods → individual cards
9.  LPT Teacher Assignment        — pick teacher per card, pre-charge load
10. Difficulty Ordering           — sort cards hardest first
11. Phase 1 Backtracking          — main CSP search
12. Slot Scoring                  — used inside (11)
13. Constraint Evaluation+Cache   — used inside (11)
14. Phase 2 Greedy                — leftover handler
15. Phase 3 Rescue                — relax soft pins
16. Phase 3b Force-Place          — last-resort, mark conflicts
17. Room Allocation Pass          — assign physical rooms
18. Grid Build / Verify / Bucket  — read-only post-processing
19. Persist                       — DB writes
```

## §1. Capacity Audit (Pre-flight)

### 1.1 The decision in one sentence
Is the demand on each teacher *theoretically* satisfiable, before we waste 25 seconds on a search that's doomed?

### 1.2 State at entry
- Activities loaded (`tt_activity` rows for the term).
- Eligible teachers loaded (`tt_activity_teacher` rows joined).
- Teacher caps loaded (`tt_teacher_availability.max_available_periods_weekly`).

### 1.3 The exact rule

For each teacher T:
```
pinned[T] = sum of weekly_periods where T is the ONLY eligible teacher
share[T]  = sum of (weekly_periods / eligible_teacher_count) where T is one of N
total[T]  = pinned[T] + share[T]
cap[T]    = max_available_periods_weekly  (or 40 default)

bucket[T] =
  if pinned[T] > cap[T]                          → OVERLOADED   (abort)
  elif total[T] > cap[T]  AND  pinned[T] > 0     → PINNED_OVERLOADED (abort unless ack)
  elif total[T] > 0.9 × cap[T]                   → TIGHT (warn)
  else                                            → OK
```

### 1.4 Worked example

Suppose three activities and two teachers:

| Activity | Weekly periods | Eligible teachers |
|---|---|---|
| Maths-9A | 6 | T1 (only) |
| Sci-9A | 5 | T1, T2 |
| Eng-9A | 4 | T2 (only) |

Caps: T1 = 8, T2 = 8.

```
pinned[T1] = 6  (Maths-9A is T1-only)
share[T1]  = 5/2 = 2.5  (half of Sci-9A's 5)
total[T1]  = 8.5

pinned[T2] = 4  (Eng-9A is T2-only)
share[T2]  = 5/2 = 2.5
total[T2]  = 6.5
```

Buckets:
- T1: pinned (6) ≤ cap (8) ✓, but total (8.5) > cap (8) and pinned > 0 → **PINNED_OVERLOADED**.
- T2: total (6.5) > 90% of cap (7.2)? No (6.5 < 7.2) → **OK**.

Result: generation aborts with "T1 is pinned-overloaded; reassign Sci-9A or acknowledge to continue."

### 1.5 Edge cases & boundaries
- **No availability row for a teacher** → cap defaults to 40. This is generous; many real schools have full-time teachers at 28–30 actual periods/week. Audit will under-report load.
- **`is_full_time=false` on availability** → not currently used by audit; only `max_available_periods_weekly` matters.
- **Teacher with `unavailable_for_all_days=1` constraint** → audit doesn't subtract these. A teacher unavailable on Monday but with cap=40 is treated as having all 40 periods available. This is a **soft drift** — the audit can pass while Phase 1 finds itself with a teacher who has no usable slots.
- **Activity with zero eligible teachers** → audit doesn't catch this; Phase 1 will fail to place. Worth a separate pre-check.

### 1.6 Interactions
- **Feeds nothing directly.** It either lets generation continue (returning the bucket lists for the warning UI) or it stops the run.
- **Limitations propagate to Phase 1.** When the audit says "OK" but Phase 1 still struggles, the audit's blind spots above are usually the cause.

### 1.7 Where the bugs lurk
- A `share` calculation that divides by `eligible_teacher_count` assumes uniform distribution — but LPT in §10 *won't* uniformly distribute. So `share` is optimistic.
- When `acknowledge_capacity_warnings=true`, the abort is bypassed but the warning is still recorded. Operators can lose track of what they acknowledged.

## §2. Reference Load (snapshot)

Not strictly an algorithm but worth flagging because of the *snapshot semantics*:

- Everything gets read into PHP arrays once, in `loadClassSections`, `loadActivities`, `loadSchoolDays`, `loadPeriodSet`.
- Eager-loading is aggressive (`->with(['teachers', 'subject', 'study_format', 'preferred_room_ids'])`) — minimizes round trips, but a cold cache run still hits dozens of tables.
- **The snapshot is the world for the rest of the run.** A teacher added mid-run isn't visible until the operator clicks Generate again.
- **Memory cost** scales linearly with `(activities × teachers per activity) + (periods × classes)`. A 600-activity school can pull 50–80 MB into PHP.

This matters because the constraint cache (§13) keys off in-memory IDs, not DB IDs. If you pre-warm objects but reload them mid-run, cache integrity breaks.

## §3. Class Teaching Window — per-class allowed slot range

### 3.1 The decision
For class C, what is the lowest and highest period index it can use?

### 3.2 State at entry
`tt_class_timetable_type_jnt` rows joined with `tt_period_set`'s `from_period_ord`/`to_period_ord`.

### 3.3 The exact rule

For each `(class, section)`:
```
windowFrom = period_set.from_period_ord   (e.g., 3 for toddler classes that start at 9:30)
windowTo   = period_set.to_period_ord     (e.g., 11)
```

Stored as a lookup map `windows[classKey] = {from, to}`.

When the solver tries a slot `(day, startIndex)` for a card with `duration_periods=d`:
```
isInWindow = (startIndex >= windowFrom)
          AND (startIndex + d - 1 <= windowTo)
```

### 3.4 Worked example
Class 9-A has window [3, 11]. Lab card has `duration=2`.
- Slot(Mon, 3): startIndex=3, end=4. 3≥3 ✓, 4≤11 ✓ → valid.
- Slot(Mon, 11): startIndex=11, end=12. 12 > 11 → **rejected** (lab would straddle past the window).
- Slot(Mon, 10): startIndex=10, end=11. 11 ≤ 11 ✓ → valid.

### 3.5 Edge cases
- **Class with multiple `class_timetable_type_jnt` rows** (e.g., normal-week + exam-week) → the join may produce two windows. The solver picks the row matching the requested timetable_type; if both apply, the orchestrator selects deterministically by `effective_from_date`.
- **Window of size 1** (`from=to`) → only single-period activities can fit; multi-period labs always rejected.
- **Window straddling a break** → still valid if both ends are in-window. The break-period gating is separate (handled by `tt_period_type.is_schedulable=false`, checked in `isBasicSlotAvailable`).

### 3.6 Interactions
- **Feeds:** every slot evaluation in Phase 1, 2, 3.
- **Does NOT feed:** Phase 3b force-place; it can place outside the window because force-place is "any 1-period anywhere it doesn't conflict."

## §4. Constraint Load — DB rows to Hard/Soft objects

### 4.1 The decision
Take a database row that says "constraint type = TEACHER_NOT_AVAILABLE, params = {teacher_id: 45, day: Monday}" and turn it into a runnable PHP object that can be asked "does placing card X at slot Y violate me?"

### 4.2 State at entry
- `tt_constraint` rows for the term.
- `tt_constraint_type` joined for each row's `code`.
- `ConstraintRegistry` (a static PHP map, populated at app boot) mapping `code → fully-qualified-class-name`.

### 4.3 The exact rule

```
for each tt_constraint row R:
    code = ConstraintType::find(R.constraint_type_id).code
    klass = ConstraintRegistry::resolve(code)
    if not klass:
        klass = GenericHardConstraint or GenericSoftConstraint  (fallback)
    instance = new klass(R.params_json + R.target_id + R.weight + R.applicable_days)
    if R.is_hard:
        manager.hardConstraints.push(instance)
    else:
        manager.softConstraints.push(instance)
```

### 4.4 Worked example

Row in `tt_constraint`:
```
id: 142
constraint_type_id: 27 (code = TEACHER_NOT_AVAILABLE)
target_type: ?
target_id: 45 (teacher id)
is_hard: 1
weight: 100
params_json: {"unavailable_periods": [{"day":"Monday","period":6},{"day":"Monday","period":7}]}
applicable_days: ["Monday"]
```

Resolution:
1. Look up code `TEACHER_NOT_AVAILABLE` → resolves to `TeacherUnavailablePeriodsConstraint` class (per `SmartTimetableServiceProvider::registerConstraints`).
2. Instantiate with the params: the object now holds `{teacher_id: 45, unavailable_periods: [...]}`.
3. `is_hard=1` → push to `hardConstraints[]`.

When asked `passes(slot=(Mon,6), card=Card[Maths-9A:1], ctx)`:
- The card's selected teacher is T45.
- Slot is Monday, period 6.
- Constraint matches (teacher 45, Monday, period 6 is in unavailable_periods).
- Returns `false` → reject this slot.

### 4.5 Edge cases
- **Code not in registry** → falls through to `GenericHardConstraint` which reads only meta fields; it doesn't enforce the constraint logic. This is how silent under-enforcement happens.
- **Effective dates** — a constraint with `effective_from > today` is filtered out in `DatabaseConstraintService` before instantiation. Operators creating future constraints won't see them affect today's run.
- **Hard constraint with weight 0** — the weight is irrelevant for hard rules (boolean), but DB still stores it. Don't expect it to "soften" a hard constraint.
- **Soft constraint marked `is_hard=1` by data error** — the system trusts the flag; the constraint will reject placements rather than score them. This is a real failure mode worth a data-validation script.

### 4.6 Interactions
- **Feeds:** Phase 1 (every slot eval), Phase 2 (every greedy try), Phase 3 (still hard-checked unless rescue relaxes a specific named constraint).
- **Does NOT feed:** Phase 3b force-place (which intentionally violates hard constraints) — though it does record which constraint was violated for the bucketing in §17.

## §5. Parallel Group Validation

### 5.1 The decision
A parallel group says "9-A Maths and 9-B Maths must run at the same time." Validate the group has a workable shape *before* the solver tries to place it.

### 5.2 State at entry
- `tt_parallel_group` and `tt_parallel_group_activity` rows.
- The activities they reference.

### 5.3 The exact rule

For each group G:
1. Members = activities linked via `tt_parallel_group_activity`.
2. Anchors = members where `is_anchor=1`. **Exactly 1 required.** If 0 or >1, error.
3. All members must have the same `duration_periods`. If any differ, error.
4. No teacher may appear in two members' `tt_activity_teacher` rows. If any overlap, error.
5. All members' classes must use the same `period_set` (so they can be scheduled at the same `startIndex`). If any differ, error.

### 5.4 Worked example

Group `Assembly_2026`:
- Members: Assembly-9A, Assembly-9B, Assembly-9C, Assembly-9D.
- Anchors: Assembly-9A flagged.
- Durations: all 1.
- Teachers: Assembly-9A=T1, 9B=T2, 9C=T3, 9D=T1 ❌

Result: error — "Teacher T1 cannot be in both Assembly-9A and Assembly-9D."

### 5.5 Edge cases
- **Single-member group** → valid technically; solver treats it as a normal card, anchor logic is a no-op.
- **Group with 0 members** → filtered out, but lingers in DB. Cosmetic clutter only.
- **Member's class is on a different period_set** — caught by rule 5. Without it, "place anchor at period 4" might be valid for one class and out-of-window for another.

### 5.6 Interactions
- **Feeds:** difficulty ordering (anchors get +5,000 boost, all parallel members get +20,000 — see §11).
- **Phase 1 placement logic:** when the anchor places, the solver immediately places all other members at the same `(day, startIndex)`. If that fails, anchor placement is undone and a different slot is tried.
- **Phase 3b force-place:** can split a parallel group (one member force-placed, others not). Surfaces as `A_SIBLING_PARALLEL` bucket in §17.

## §6. Daily Targets — floor and ceiling

### 6.1 The decision
For each `(class, day)`, what's the minimum and maximum number of periods that should land there?

### 6.2 State at entry
- `tt_school_days` (which days are working).
- `sch_academic_term.term_total_teaching_periods_per_day`.
- Optional `tt_slot_requirement` overrides.

### 6.3 The exact rule

```
weeklyDemand[class] = sum of required_weekly_periods across all activities for class
workingDays         = count of tt_school_days where is_school_day=1
target = weeklyDemand / workingDays
floor  = floor(target)        (or override from tt_slot_requirement)
ceil   = ceil(target) + 1     (give 1-period leeway)
```

### 6.4 Worked example
Class 9-A has total weekly demand of 33 periods, school works 6 days.
```
target = 33 / 6 = 5.5
floor  = 5
ceil   = 7   (ceil(5.5)=6, +1 leeway)
```

So slot scoring (§13) will:
- **Reward** the day having 0–4 placements: +25 (below floor).
- **Lightly penalize** 5–7 placements: −10 (in band — already enough).
- **Hard-reject (effectively)** 8+ placements: −1,000.

### 6.5 Edge cases
- **Demand exceeds capacity** (e.g., 50 weekly periods, 6 working days, 6 periods/day = 36 capacity) → `ceil` math says 9.3, no day has 9 periods. The solver is forced to pile on, which triggers the −1,000 hard reject and cascades to Phase 3 rescue.
- **Half-day** via `tt_day_type.reduced_periods=1` → not currently differentiated; daily target is the same for every day. This is a known limitation.
- **Single-period day** (some schools) → ceil=1 might force the +25 reward to fire forever, distorting other choices.

### 6.6 Interactions
- **Feeds:** slot scoring (the +25/−10/−1,000 day-balance terms).
- **Does NOT feed:** difficulty ordering; ordering is per-card, daily targets are per-day.

## §7. Teacher Weekly Caps

### 7.1 The decision
For each teacher, what's the maximum periods they may carry per week?

### 7.2 State at entry
`tt_teacher_availability.max_available_periods_weekly` (joined to teacher).

### 7.3 The exact rule

```
for each teacher T with at least one tt_teacher_availability row:
    cap[T] = max(max_available_periods_weekly across rows)   (use max, not sum)
for teachers without rows:
    cap[T] = 40   (hardcoded default)
```

### 7.4 Worked example
T1 has two availability rows:
- Row 1 (linked to Maths req): `max_available_periods_weekly=20`.
- Row 2 (linked to Sci req): `max_available_periods_weekly=15`.

Cap = max(20, 15) = 20. (The cap is per teacher, not per requirement; the rows can disagree but we trust the largest.)

### 7.5 Edge cases
- **Multiple rows with different caps** → max wins, even if some rows are "outdated." This silently loses tighter caps.
- **`is_full_time=true` but cap=12** → cap wins; the bool is documentation, not enforced.
- **Default 40 too generous** → covered in §1 capacity audit blind spots.

### 7.6 Interactions
- **Feeds:** LPT teacher pick (the pre-charge limit), per-slot teacher load check (`teacherOccupied[T]` count vs cap).
- **Does NOT feed:** alternative-teacher retry directly — that picks from eligible teachers without re-consulting the cap, only checks slot-level conflict. (This is a small bug-shaped thing — see §15.)

## §8. Activity Expansion — flatten weekly periods to cards

### 8.1 The decision
"Maths-9A needs 5 periods/week" → produce 5 cards.

### 8.2 The exact rule

```
cards = []
for each activity A:
    for i in 1..A.required_weekly_periods:
        card = clone_metadata_of(A)
        card.instance_index = i
        card.duration_periods = A.duration_periods
        cards.push(card)
```

### 8.3 Worked example

| Activity | required_weekly_periods | duration_periods | Cards |
|---|---|---|---|
| Maths-9A | 5 | 1 | Card[Maths-9A:1], …, Card[Maths-9A:5] |
| Sci-Lab-9A | 2 | 2 | Card[Sci-Lab-9A:1], Card[Sci-Lab-9A:2] |
| Sports-9A | 1 | 1 | Card[Sports-9A:1] |

Total 8 cards.

Each card carries a reference to its parent activity, so all 5 Maths cards still know their `preferred_periods_json`, `is_compulsory`, etc.

### 8.4 Edge cases
- **`split_allowed=false`** → all instances must land on different days. Tracked in slot scoring (penalty −100 if split would happen).
- **`required_weekly_periods=0`** → no cards generated. Activity quietly absent from output.
- **`duration_periods=2` with required=3** → 3 cards each occupying 2 consecutive slots = 6 actual cells. Combined with class cap of (say) 8 periods/day, only 4 such cards fit per day.

### 8.5 Interactions
- All later steps work on cards, not activities. **Crucially**, LPT (§10) picks teacher *per card*, but the result is consistent across all cards of the same activity by design (the LPT pass goes activity-by-activity, picking once and assigning to all instances).

## §10. LPT Teacher Assignment + Alternative-Teacher Retry — **DEEP DIVE**

This is the algorithm that surprises people most, because the teacher state evolves across **two phases** with subtly different rules.

### 10.1 The decision (Phase 0: LPT)
Among the eligible teachers for a card, which one gets pre-assigned, so that overall teacher load is balanced *before* the search begins?

### 10.2 The exact rule (LPT pass)

```
charge[teacher] = 0  for all teachers   # in-memory counter, NOT persisted

# Walk activities (not cards) in random order:
for each activity A:
    eligible = A.activity_teacher rows  (teachers eligible for this activity)
    pick the teacher T with min(charge[T])   # tie-break random
    A.selectedTeacherId = T.id
    charge[T] += A.required_weekly_periods × A.duration_periods
    # propagate to all cards from A:
    for each card C in cardsOfActivity(A):
        C.selectedTeacherId = T.id
```

**Important nuance:** LPT picks once per *activity*, not per card. All 5 Maths-9A cards get the same teacher. The pre-charge is `weekly_periods × duration_periods` — i.e., total cell-time, not card-count.

### 10.3 Worked example — LPT pass

Three activities, two eligible teachers (T1, T2). Both initially `charge=0`.

| Activity | weekly | duration | Eligible |
|---|---|---|---|
| A1 | 5 | 1 | T1, T2 |
| A2 | 2 | 2 | T1, T2 |
| A3 | 6 | 1 | T1, T2 |

LPT walks them in random order. Suppose order is A2, A3, A1.

```
Step 1: A2. charge[T1]=0, charge[T2]=0. Tie → random; suppose T1.
        selectedTeacher[A2] = T1
        charge[T1] = 0 + (2 × 2) = 4
        charge[T2] = 0
Step 2: A3. charge[T1]=4, charge[T2]=0. T2 wins.
        selectedTeacher[A3] = T2
        charge[T1] = 4
        charge[T2] = 0 + (6 × 1) = 6
Step 3: A1. charge[T1]=4, charge[T2]=6. T1 wins.
        selectedTeacher[A1] = T1
        charge[T1] = 4 + (5 × 1) = 9
        charge[T2] = 6
```

Final:
- T1 carries A1+A2 = 5 + 4 = 9 cell-periods.
- T2 carries A3 = 6 cell-periods.

So at the end of LPT, before any actual placement, T1 and T2 have 9 vs 6. Reasonable balance given the inputs. Cards inherit:

```
Card[A1:1..5]   → selectedTeacher = T1
Card[A2:1..2]   → selectedTeacher = T1
Card[A3:1..6]   → selectedTeacher = T2
```

### 10.4 The alternative-teacher retry (Phase 2)

This is where things get interesting.

After Phase 1 backtracking finishes, suppose `Card[A1:5]` is still unplaced because T1 has no free slot left. Phase 2 (greedy) walks the leftovers:

```
for each unplaced card C:
    candidates = getPossibleSlots(C)     # filtered by class window, duration
    for slot in candidates (best score first):
        if isBasicSlotAvailable(C, slot)
        and constraintManager.checkHard(slot, C):
            place(C, slot); break
    if not placed:
        # tryAlternativeTeacher
        for T_alt in eligibleTeachersOf(C.activity), excluding C.selectedTeacherId:
            for slot in candidates:
                if T_alt is free at slot
                and other hard constraints pass with T_alt:
                    C.selectedTeacherId = T_alt
                    place(C, slot)
                    goto next_card
```

### 10.5 The non-obvious behaviors of alternative-teacher retry

This is the part that confuses people. Five subtle things:

#### (a) The `charge[]` map is not updated
LPT's `charge[]` lives only inside the LPT pass. Phase 2's `tryAlternativeTeacher` does NOT consult or update it. It only checks "is T_alt free at this *specific slot*" — not "is T_alt under their cap."

**Consequence:** if Phase 2 reassigns 3 cards from T1 to T2, T2 might end the run with 9 cell-periods while T1 ends with 3 — even though LPT had carefully balanced 9 vs 6.

#### (b) The order of `eligibleTeachers` for retry is not specified
The current code just iterates the eligible teachers list as it came from the database. It does NOT re-sort by least-loaded.

**Consequence:** the first eligible teacher who has a free slot wins, even if a less-loaded teacher would have been a better choice.

#### (c) Retry is per-card, not per-activity
Once Phase 2 reassigns Card[A1:5] from T1 to T2, the *other* Maths cards (A1:1..4) are still on T1 (already placed). Now T2 teaches Maths once a week, T1 teaches Maths four times.

**Consequence:** what was a "Maths is T1's subject" pattern in the LPT phase becomes a split assignment after rescue.

#### (d) Retry doesn't consult `tt_teacher_availability.is_preferred_teacher`
The original LPT pick honored `is_primary_teacher` and `is_preferred_teacher` (via the eligible filter). Retry just picks "any eligible." If the school had marked T2 as a backup that should rarely teach Maths, retry will use them anyway.

#### (e) Phase 1 doesn't try alternatives
Phase 1's backtracking only ever uses `selectedTeacherId`. It never considers alternative teachers, even when an alternative would let the search succeed in fewer iterations. So a card that could've been placed cleanly by switching teachers is instead force-placed by Phase 3b.

### 10.6 Worked example — what happens when Phase 1 fails on a card

State after LPT (from §10.3):
- A1 (5 periods) → T1
- A2 (2 periods × 2 duration) → T1
- A3 (6 periods) → T2

Suppose Phase 1 places everything except `Card[A1:5]`. Trace:

```
Phase 2 begins.
Card[A1:5] is unplaced.

Iteration with selectedTeacher = T1:
    Try Slot(Mon,3): T1 already teaching there → fail.
    Try Slot(Tue,5): T1 already teaching there → fail.
    Try Slot(Wed,2): T1 free! But class 9-A already at daily ceiling → constraint fails.
    ... no slot fits T1.

tryAlternativeTeacher:
    Eligible (excluding T1): T2.
    Try T2 with Slot(Mon,3): T2 is free, hard constraints pass → PLACED.
    Card[A1:5].selectedTeacherId = T2.

charge[] is NOT updated. T2 now carries 7 cell-periods (A3=6 + this 1) but the system doesn't know.
```

Result: A1 is now split across T1 (4 instances) and T2 (1 instance).

### 10.7 Edge cases
- **No alternative teacher available** → card remains unplaced; goes to Phase 3 rescue.
- **All eligible teachers exhausted** → still unplaced; goes to Phase 3b force-place, where the bucketing categorizes the conflict.
- **Activity with `tt_activity_teacher.is_required=1`** → that teacher is never replaced (the alternative pool excludes them only if the constraint is properly modeled; today the code doesn't always check this).
- **Co-teacher activities** (multiple `assignment_role_id` rows) — current LPT and retry assume one primary. Multi-teacher activities have undefined alternative semantics.

### 10.8 Where the bugs lurk
- **Stale charge** (§10.5a) is the biggest design gap. A simple fix: have Phase 2 increment a parallel `runtimeCharge[]` and prefer least-loaded among alternatives.
- **No re-sorting** (§10.5b) means retry is order-dependent. Subtle bugs where a re-run produces different teacher assignments because eligible-list order differs.
- **Audit blindness:** §1's capacity audit assumes uniform `share`, but LPT can deviate from uniform. So a teacher predicted to carry 5 periods can end up carrying 9 — without the audit catching it.

### 10.9 Interactions summary

```
LPT (§10) → sets selectedTeacherId per card, pre-charges T1/T2 in-memory
   │
   ▼
Phase 1 Backtracking (§12) — uses selectedTeacherId, never tries alternatives
   │
   ▼ (leftovers)
Phase 2 Greedy
   ├─ Try selectedTeacherId first
   └─ tryAlternativeTeacher → mutates selectedTeacherId per card
       (does NOT update charge[]; does NOT honor preference flags)
```

This is by far the most "magic at a distance" interaction in the system.

## §11. Difficulty Ordering — full formula breakdown

### 11.1 The decision
What order should the cards be presented to the backtracking search?

### 11.2 The exact rule (re-stated)

```
score = activity.difficulty_score_calculated   # 0–100, from ActivityScoreService
if A.required_weekly_periods >= 6:  score += 10000
score += A.required_weekly_periods × 500
score += A.duration_periods × 3
score += teacherCount × 2
if A.is_compulsory:                  score += 20
if classTeacherFirst && A is class teacher activity:
    score += 1000 + A.priority × 20
if A in parallel group:              score += 20000
if A is parallel anchor:             score += 5000
sort cards descending by score
```

### 11.3 Worked example — three cards

| Card | wk | dur | teachers | compulsory | class-teacher | parallel | anchor | difficulty |
|---|---|---|---|---|---|---|---|---|
| Maths-9A | 5 | 1 | 2 | yes | no | no | no | 70 |
| Sports-9A | 1 | 1 | 1 | no | no | no | no | 30 |
| Assembly-9A | 1 | 1 | 1 | yes | no | yes | yes | 50 |

Score breakdown:

```
Maths-9A:    70 (base) + 0 (≥6 false) + 5×500=2500 + 1×3=3 + 2×2=4 + 20 (compulsory) + 0 + 0 + 0
           = 70 + 2500 + 3 + 4 + 20  =  2,597

Sports-9A:   30 + 0 + 1×500=500 + 3 + 1×2=2 + 0 + 0 + 0 + 0
           = 30 + 500 + 3 + 2  =  535

Assembly-9A: 50 + 0 + 1×500=500 + 3 + 2 + 20 + 0 + 20000 (parallel) + 5000 (anchor)
           = 50 + 500 + 3 + 2 + 20 + 20000 + 5000  =  25,575
```

Order: Assembly-9A (25,575), Maths-9A (2,597), Sports-9A (535).

### 11.4 What this ordering really means
- **Parallel groups dominate** — anything in one is always first. The +20,000 makes everything else look like noise.
- **Among non-parallel cards**, weeklyPeriods × 500 dominates. Maths-9A's 5 weekly periods ≈ 2,500 points; Sports-9A's 1 period ≈ 500. The ratio (5:1 in weeklyPeriods becomes 5:1 in score) is too literal — a 1-period subject with a single specialist teacher is *not* 5x easier to place than a 5-period generic subject.
- **`is_compulsory +20` is noise.** It makes a 0.7% difference at most.
- **`difficulty_score_calculated` (0–100) is also noise** in practice — drowned by ×500 and ×20,000.

### 11.5 The pathological case (this is why your discrepancy doc exists)

Suppose two cards:
- A: weekly=5, generic subject, 5 eligible teachers, plenty of room types.
- B: weekly=1, specialist subject, 1 eligible teacher (T7), specific lab room required.

```
A: 0 (no parallel) + 5×500=2500 + 1×3 + 5×2=10 + 0 + 0 = 2513
B: 0 + 1×500=500 + 1×3 + 1×2=2 + 0 + 0 = 505
```

A places first. After A consumes some of T7's slots (no — T7 isn't even in A's list, so A doesn't affect T7), and after the special lab room gets used... wait, A doesn't use that lab either.

Actually, the failure mode is: A doesn't conflict with B, but A's placements fill the grid. By the time B's turn comes, the few periods where T7 *and* the lab room are simultaneously free have been overwritten by A's (lower-priority but earlier) placements.

A scarcity-aware ordering would have placed B first, when both T7 and the lab room had wide availability.

### 11.6 Edge cases
- **Tie scores** → Phase 1 uses stable sort; the original list order (random from Activity Expansion) wins. So generation can produce different timetables on re-runs.
- **`difficulty_score_calculated` is null** → treated as 0. Activities never scored by ActivityScoreService get the lowest base.
- **Parallel group with one anchor and one member** → both get +20,000; only anchor gets +5,000. Anchor places first within the group.

### 11.7 Interactions
- **Feeds:** Phase 1 backtracking traverses the card list in this order.
- **Affects:** the *probability of success* in Phase 1. A bad ordering means more backtracking, more cache invalidation, more time lost.

## §12. Phase 1 Backtracking + Constraint Cache — **DEEP DIVE**

This is the algorithmic core. It's also where the cache interaction creates the most subtle behavior.

### 12.1 The decision
Given the ordered cards, find a placement that satisfies all hard constraints, preferring high-soft-score slots.

### 12.2 The exact rule (recursive)

```
function backtrack(index):
    if iterations exceeded budget: return TIMEOUT
    if index == cards.length: return SUCCESS    # all placed

    card = cards[index]
    candidates = getPossibleSlots(card)
        # filter: in class window, duration fits, day eligible
    candidates.sortBy(score)  # descending — best first
        # score from §13 slot-scoring formula

    for slot in candidates:
        if isBasicSlotAvailable(card, slot)
        and constraintManager.checkHard(slot, card, ctx):
            place(card, slot)
            result = backtrack(index + 1)
            if result == SUCCESS: return SUCCESS
            undo(card, slot)
            constraintManager.clearCache()  # ←──── KEY LINE

    return FAIL
```

### 12.3 Worked example — small backtracking trace

Three cards, very simple grid (1 class, 2 days, 3 periods/day, 2 teachers):

```
Cards (after ordering):
  C1 = Maths   selectedTeacher=T1   duration=1
  C2 = English selectedTeacher=T2   duration=1
  C3 = Sports  selectedTeacher=T1   duration=1

Hard constraints: TeacherConflict only.
```

Backtracking trace:

```
backtrack(0)  — placing C1
  candidates: (Mon,1), (Mon,2), (Mon,3), (Tue,1), (Tue,2), (Tue,3)
  Try (Mon,1): basic-available ✓, hard-check ✓ → PLACE.
    state: C1@Mon-1, T1 busy at Mon-1.

  backtrack(1)  — placing C2
    candidates: (Mon,1), (Mon,2), (Mon,3), (Tue,1), (Tue,2), (Tue,3)
    Try (Mon,1): basic-available ✗ (class already busy) → skip.
    Try (Mon,2): basic-available ✓, hard-check ✓ → PLACE.
      state: C1@Mon-1, C2@Mon-2.

    backtrack(2)  — placing C3
      candidates: (Mon,1), (Mon,2), (Mon,3), (Tue,1), (Tue,2), (Tue,3)
      Try (Mon,1): basic-available ✗ → skip.
      Try (Mon,2): basic-available ✗ → skip.
      Try (Mon,3): basic ✓, hard ✓ → PLACE. SUCCESS.
```

Three placements, no backtrack needed. Cache was warmed but never relied on.

### 12.4 Worked example — backtracking with cache pollution

Now imagine 5 cards and a tighter constraint set. Trace fragment:

```
backtrack(2) — placing C3 (Sports, T1)
  candidates: ... all evaluated
  At (Tue,2): hard-check evaluates TeacherMaxDailyConstraint.
    Cache key: hard-9A-Tue-2-C3.
    T1 already has 2 placements on Tue (from C1, C2 earlier).
    Result: pass=false (would exceed daily max for T1).
    Cache: stores hard-9A-Tue-2-C3 → false.

  No slot works for C3.
  Return FAIL.
```

Now backtrack to C2's level:

```
undo(C2, Mon-2)
clearCache()                       ← THIS IS THE CRITICAL LINE
  Why: T1's load just changed. The cached hard-9A-Tue-2-C3=false
        was conditional on T1 being busy at Mon-2. Now that's
        undone, the cached "false" is wrong.

backtrack(1) — try next slot for C2
  Try (Mon,3): hard-check ✓ → PLACE.

backtrack(2) — placing C3 again
  Cache is empty. Re-evaluates everything fresh.
  At (Tue,2): T1 still has the same 2 Mon placements (C1 at Mon-1, C2 now at Mon-3).
    Wait — does TeacherMaxDailyConstraint still reject?
    Yes if it says "no more than 2 Mon periods for T1," and T1 still has 2.
    Hmm, this isn't actually about T1's load on Tue; it's about T1's Mon load.
    The example needs adjusting...

(Concrete principle: any placement that's been undone may have invalidated
 a previously-cached result. The cache cannot tell which results depended
 on the undone placement, so it conservatively clears everything.)
```

### 12.5 The cache key explained

```
Key shape: "{type}-{classKey}-{dayId}-{startIndex}-{cardId}"
       e.g.: "hard-9A-2-3-42"

  type      = "hard" or "soft"
  classKey  = "9-A"
  dayId     = day (here Tuesday=2)
  startIndex= period index 3
  cardId    = the card's ID 42
```

Why this shape:
- Two different cards trying the same slot get different keys (good — they may have different teachers, different durations).
- The same card retried at the same slot gets the same key (good — answer is same as long as global state hasn't changed).
- **But the cache doesn't know about global state.** It assumes "card X at slot Y" has a deterministic answer. The moment a *different* card's placement changes some constraint's view, the answer for X at Y might flip.

### 12.6 Why the cache must be cleared on backtrack

A constraint like `TeacherConflictConstraint` reads `context.teacherOccupied[teacherId][dayId][periodId]`. This is a shared, mutable map. When card C1 places at (Mon,1) and uses T1, the map gets `teacherOccupied[T1][Mon][1] = true`. Now any later card that asks "can T1 use Mon-1?" will be told no — and that answer is cached.

If we then undo C1 (remove from Mon-1), `teacherOccupied[T1][Mon][1]` becomes false again. But the cached "no" is still in memory. Without `clearCache()`, the next attempt to place C1 at Mon-1 — or any other card that consults Mon-1 for T1 — would see the stale "no" and reject incorrectly.

The cache is **coarse**: it clears all entries, not just the ones related to the undone placement. A finer cache could track dependencies (e.g., "this cache entry depended on T1's Mon-1 status") and invalidate selectively. That's a real future optimization but it's not in the current code.

### 12.7 The performance trade-off

The cache is the single biggest performance win. Without it:
- Every slot evaluation re-runs ~20+ constraint checks.
- A medium school's search visits ~100K candidate slots.
- That's ~2M constraint evaluations per run.

With the cache:
- First evaluation populates.
- Subsequent evaluations of the same `(card, slot)` are O(1).
- Hit rate is typically 60–80% during forward placement.
- But every backtrack flushes everything, so hit rate drops in deep-backtrack runs.

### 12.8 Cutoffs and what happens at timeout

```
backtrack_timeout = 25 seconds   (wall clock)
max_iterations   = 50,000
max_backtracks   = 50,000
```

When any cutoff fires, the search returns **the best partial placement found so far** (not the in-progress branch). The orchestrator then hands the partial state — `placements`, `occupied`, `teacherOccupied` plus the unplaced card list — to Phase 2 greedy.

### 12.9 Edge cases
- **No candidates for a card** → `getPossibleSlots(card)` returns empty list. Skip to next card via the FAIL path (the recursive call returns FAIL, parent moves to its next slot).
- **Slot scoring identical** (a tie) → original candidate order wins; nondeterministic if ordering is hash-based.
- **Cache memory bloat** → on a deep search, cache can grow to 100K+ entries before a backtrack. Only relieved on backtrack. Memory pressure is real on large schools.

### 12.10 Where the bugs lurk
- **Stale cache after undo** (handled, but only because of the brute-force `clearCache()`). If anyone optimizes this without dependency tracking, expect mysterious "constraint passes but shouldn't" bugs.
- **Order-of-evaluation effects in soft scoring** — soft scoring isn't cached the same way; it's recomputed for each candidate slot. So re-ordering candidates can produce different sums under floating-point arithmetic (rare but real).
- **`SimulatePlacement` paths** (when a constraint needs to look ahead) currently mutate the same context. If a future constraint adds asynchronicity, this becomes an issue.

### 12.11 Interactions

```
Phase 1 ──┬── reads constraint manager (§4)
          ├── calls getPossibleSlots() — uses class window (§3) + activity duration
          ├── orders candidates by slotScore() — see §13
          ├── per slot:
          │     ├── isBasicSlotAvailable() — class/teacher occupancy + window + cap
          │     └── constraintManager.checkHard() — reads cache, evaluates, caches
          ├── on success: place() — mutates occupied/teacherOccupied/placements
          └── on backtrack: undo() + clearCache()
```

## §13. Slot Scoring — the formula in depth

### 13.1 The decision
Among hard-feasible slots for a card, which one is *preferable*?

### 13.2 The formula (re-stated)

```
score = 0

# Activity-level preferences
if slot.day,startIndex matches preferred_time_slots_json: score += 40
if slot.day,startIndex matches avoid_time_slots_json:     score -= 50
if slot.startIndex in preferred_periods_json:             score += 20
if slot.startIndex in avoid_periods_json:                 score -= 30

# Spread evenly
if A.spread_evenly:
    if class hasn't placed this activity on slot.day yet: score += 10
    else:                                                 score -= 15

# Day-balance (driven by §6 daily targets)
postCount = (count of class placements on slot.day) + 1
if postCount < floor[class][day]:    score += 25
elif postCount in [floor, ceil]:     score -= 10
elif postCount > ceil[class][day]:   score -= 1000

# Min-per-day pressure
if A.min_per_day not yet met on slot.day:                 score += 15

# Split-allowed=false
if !A.split_allowed and slot.day is a *new* day for A:    score -= 100

# Soft constraints (sum over softConstraints[])
score += 0.5 × sum(softC.score(slot, A, grid, periods))
```

### 13.3 Worked example

Suppose Card[Maths-9A:3] (3rd of 5 Maths instances), trying slot (Wed, 4).

State at this point:
- Maths-9A has been placed at (Mon,2) and (Tue,2). Pinning preference is Period 2.
- Class 9-A has 3 placements on Wed already (none Maths). Floor=4, Ceil=6.
- Maths preferred_periods_json = `[2]`.
- spread_evenly = true.

Computation:
```
preferred_time_slots match? No.
avoid match? No.
preferred_periods (4 in [2]?): No.       (would be +20 if startIndex=2)
avoid_periods: No.
spread_evenly: Wed has 0 Maths placements yet → +10.
day-balance:
    postCount = 3 + 1 = 4
    floor=4, ceil=6 → in band → -10.
min_per_day: not configured → 0.
split_allowed: irrelevant (Wed is new day, but split_allowed=true) → 0.
soft constraints: suppose pin-by-period soft constraint exists for Maths.
    PinByPeriodConstraint(period 2): slot.startIndex=4, not 2 → score -10.
    Multiplied by 0.5 → -5.

Total: 10 + (-10) + (-5) = -5.
```

Now try slot (Wed, 2) for the same card:
```
preferred_periods (2 in [2]): YES → +20.
spread_evenly: Wed has 0 Maths yet → +10.
day-balance: same +(-10).
soft pin-by-period: 2==2 → +20 × 0.5 = +10.
Total: 20 + 10 + (-10) + 10 = +30.
```

So (Wed, 2) is strongly preferred over (Wed, 4) — by 35 points. The backtracking loop would try (Wed, 2) first.

### 13.4 The −1,000 day-balance hard reject
This is technically a *soft* score, but in practice a slot scoring −1,000+ is ignored by the search because every other slot has a positive or near-zero score. So it functions like a hard reject in 99% of cases. **But** if every available slot for a card scores below −1,000 (a packed-class scenario), the search still takes the least-bad — which is one of the −1,000 cells. This is the "cap relaxation" that Phase 3 rescue can later turn off.

### 13.5 Edge cases
- **Empty preferred_periods_json** → both +20 and 0 don't trigger; just no bonus. Correct.
- **Conflicting preferences**: Activity has `preferred_periods=[2]` *and* `avoid_periods=[2]`. The +20 and the −30 both apply: net −10. Probably a data-entry bug.
- **Soft constraint scoring for a non-relevant constraint**: most constraints first call `isRelevant(activity)` and return 0 if not relevant. A few don't, leading to mysterious scoring drift. Test by counting `getRelevantConstraints` per card.

### 13.6 Interactions
- **Feeds:** the candidate ordering inside Phase 1 backtracking and Phase 2 greedy.
- **Does NOT feed:** Phase 3b force-place (which doesn't care about scores, just fits 1-period anywhere).
- **Reads from:** §6 daily targets, §3 class windows (indirectly via candidate filtering), the activity's JSON fields.

## §14. Constraint Evaluation Engine — cache mechanics in detail

### 14.1 The decision
"Does this card-slot pair pass all hard constraints?" or "What's its soft score?"

### 14.2 The exact rule

```
function checkHard(slot, card, ctx):
    key = "hard-{classKey}-{dayId}-{startIndex}-{cardId}"
    if cache.has(key): return cache.get(key)
    for c in hardConstraints:
        if c.isRelevant(card)
        and not c.passes(slot, card, ctx):
            cache.set(key, false)
            return false
    cache.set(key, true)
    return true

function evaluateSoft(slot, card, ctx):
    key = "soft-{classKey}-{dayId}-{startIndex}-{cardId}"
    if cache.has(key): return cache.get(key)
    score = 0
    for c in softConstraints:
        if c.isRelevant(card):
            score += c.score(slot, card, ctx) × c.getWeight()
    cache.set(key, score)
    return score

function clearCache():
    cache = {}
```

### 14.3 What the cache stores
| Key shape | Value | When invalidated |
|---|---|---|
| `hard-<classKey>-<day>-<period>-<cardId>` | bool | On `clearCache()` (every backtrack) |
| `soft-<classKey>-<day>-<period>-<cardId>` | float | On `clearCache()` |

**No partial invalidation.** The whole cache is dropped on every undo.

### 14.4 Why this design

It's coarse but **correct**. A finer cache would need:
- Each constraint to declare its dependencies (e.g., "I depend on T1's Mon-1 occupancy").
- A reverse index: when (T1, Mon, 1) changes, find all cache keys depending on it.
- Selective invalidation.

That's a large engineering change; the current authors chose simplicity over peak performance.

### 14.5 Performance characteristics

| Phase | Cache hit rate | Reason |
|---|---|---|
| Phase 1, forward (no backtracks) | 60–80% | Most candidates re-evaluated for adjacent cards |
| Phase 1, after backtrack | 0% (just cleared) | Then climbs again as forward proceeds |
| Phase 2 greedy | High | No backtracks at all; once cached, stays cached |
| Phase 3 rescue | Mixed | Relaxations may invalidate some keys via `clearCache` |
| Phase 3b force-place | Low | Cache cleared because hard rules being broken |

### 14.6 Edge cases
- **Constraint with side effects** (rare, but exists in some custom soft constraints) → cache returns the same answer each time even if the underlying state changed. Don't write side-effecting constraints; the cache assumes purity.
- **`isRelevant` returns false** → constraint skipped, doesn't affect score. Faster than skipping inside `passes()`.

## §15. Phase 2 — Greedy with Alternative Teacher

(Cross-references §10 for the alternative-teacher mechanics.)

### 15.1 The decision
For each leftover card from Phase 1, find any legal placement (no backtracking).

### 15.2 The exact rule

```
for each unplaced card C (in original order):
    candidates = getPossibleSlots(C).sortBy(slotScore desc)
    placed = false

    # First pass: try with the original selectedTeacher
    for slot in candidates:
        if isBasicSlotAvailable(C, slot)
        and constraintManager.checkHard(slot, C, ctx):
            place(C, slot); placed = true; break

    # Second pass: try alternative teachers
    if not placed:
        for T_alt in eligibleTeachersOf(C.activity), excluding C.selectedTeacherId:
            for slot in candidates:
                if T_alt is free at slot
                and remaining hard constraints pass with T_alt:
                    C.selectedTeacherId = T_alt
                    place(C, slot)
                    placed = true; break
            if placed: break

    if not placed:
        leave for Phase 3 / 3b
```

### 15.3 Worked example
Already covered in §10.6.

### 15.4 Edge cases & interactions
See §10.5 — the five non-obvious behaviors.

## §16. Phase 3 — Rescue Pass

### 16.1 The decision
Some leftovers were blocked by *soft pins* that the operator chose, not by genuine impossibility. Loosen those pins one at a time and retry.

### 16.2 The exact rule

```
relaxations = [
  pin_activities_by_period,        # drop "same period across days"
  daily_cap_overflow,               # allow ceil+1 periods on a day
  class_teacher_first_lecture,      # let other activities take period 1
  allow_consecutive_periods,        # allow same-activity back-to-back
]

for each unplaced card C:
    for each relaxation R:
        temporarily disable R
        retry greedy placement (§15)
        if placed: re-enable R, move to next card
        else: re-enable R; try next relaxation
    if not placed: leave for Phase 3b
```

### 16.3 Worked example

Card[Maths-9A:5] is unplaced because every period 2 (Maths is pinned to P2) is taken across all days.

```
Try relaxation 1: pin_activities_by_period = false
    Now any period is fair game, not just P2.
    Retry greedy: Slot(Fri, 5) is available, place it.
    ✓ placed. Re-enable pin_activities_by_period for next card.
```

So Maths-9A:5 lands at (Fri, 5) instead of P2 somewhere. Operator sees the timetable is "mostly P2 but one Friday-period-5 placement."

### 16.4 Edge cases
- **Multiple cards per relaxation** — relaxations are tried per-card, not globally. So drop pinning for card X, retry, succeed; restore pinning for card Y. Means rescue can fix one card without disturbing pinning for the rest.
- **Relaxation order matters** — if a card could be placed by either dropping pinning or dropping daily cap, the first-listed relaxation wins. Operators can't override the order.

### 16.5 Interactions
- **Reads:** the same constraint manager and grid state as Phase 2.
- **Does NOT alter:** the constraint definitions themselves; only the four named generation options.

## §17. Phase 3b — Force-Place + In-Phase Bucketing

### 17.1 The decision
A card couldn't be placed even after rescue. Drop it onto the schedule with a conflict marker, and label *which kind of conflict* it caused.

### 17.2 The exact rule

```
if strict_no_conflicts:
    leave card unplaced
    return

for each remaining unplaced card C (must be 1-period, durations >1 stay unplaced):
    for slot in get1PeriodSlotsInWindow(C):

        # Determine bucket by examining who's in the way:
        existing = occupied[classKey][day][period]
        if existing is in same parallelGroup as C:           bucket = A_SIBLING_PARALLEL
        elif existing is sub-activity of C's parent:         bucket = A_SIBLING_PARENT
        elif existing teacher's role.allows_overlap = true:  bucket = B_ROLE_OVERLAP
        elif this would breach class daily cap:              bucket = D_CAPACITY
        else:                                                 bucket = C_REAL_TEACHER

        # Force-place with the bucket label
        forcePlace(C, slot, bucket)
        cell.is_active = false
        cell.has_conflict = true
        cell.conflict_details = { bucket, existing, ... }
        break
```

### 17.3 Worked example

Card[Sports-9A:1] (1 period, T1) is unplaced. We try (Mon, 5) which already has Maths-9A there (T1 teaching).

```
existing = Maths-9A (T1)
parallel group? Maths-9A and Sports-9A: not in any group → no.
sibling sub-activity? Sports-9A is not a sub of Maths-9A's parent → no.
T1's role on existing: PRIMARY (allows_overlap=false) → no.
Daily cap breach? Class 9-A has 6 placements Mon, ceil=6, post-place=7 → YES.
bucket = D_CAPACITY.

Force-place at (Mon, 5):
    cell.activity = Sports-9A
    cell.teacher = T1   (still T1 — not the alternative!)
    cell.is_active = false
    cell.has_conflict = true
    cell.conflict_details = { bucket: 'D_CAPACITY', existing: Maths-9A }
```

UI shows a 🔴 cell with "D_CAPACITY: would breach daily cap."

### 17.4 First-match-wins gotcha
The bucket conditions are evaluated in order. If a placement *both* breaches a daily cap *and* puts T1 in conflict with a sibling parallel member, it gets `A_SIBLING_PARALLEL` (the first match), not `D_CAPACITY`. Operators reading the bucket may miss the harder problem.

### 17.5 Edge cases
- **Card with `duration_periods > 1`** → not eligible for force-place; stays unplaced. This is a known gap (multi-period activities can't be force-placed even when 1-period cells are available).
- **No 1-period slots in window** → card stays unplaced.
- **`strict_no_conflicts=true`** → entire phase skipped; leftovers reported as unplaced.

### 17.6 Interactions
- **Reads:** parallel-group membership, sub-activity parent links, teacher role records, daily caps.
- **Output flows to:** §18 grid build (cells materialized), §19 diagnostics (each force-placed card listed), §20 bucket display.

## §18. Room Allocation Pass

### 18.1 The decision
Now that we know *when* each card runs, *where* (which physical room) does it run?

### 18.2 The exact rule

Two passes: **score-then-walk**.

```
# Pass 1: score every entry's room priority
for each placement entry E:
    A = E.activity
    score = 0
    if A.required_room_id:                                score = 100
    elif A.compulsory_specific_room_type:                 score = 80
    elif A.required_room_type_id:                         score = 60
    elif A.preferred_room_ids:                            score = 30
    elif A.preferred_room_type_id:                        score = 20
    else:                                                  score = 0
    E.roomPriority = score

# Pass 2: walk entries, highest score first
sortBy(roomPriority desc)

for each entry E:
    candidates = roomsCompatibleWith(E.activity)  # filtered by type, capacity, can_host
    candidates.sortBy(matchPriority for E)         # specific > preferred-list > preferred-type > generic
    for room in candidates:
        if not roomBusy[room][E.day][E.period]:
            assign(E, room)
            roomBusy[room][E.day][E.period] = true
            break
    else:
        E.roomConflict = true
        cell.has_conflict = true
```

### 18.3 Worked example

Three placements at (Mon, 4):
- E1: Sci-Lab-9A — required_room_id = Lab-1.
- E2: Maths-9A — preferred_room_type_id = Classroom.
- E3: PE-9A — required_room_type_id = Sports-Room.

Pass 1 scores:
```
E1.roomPriority = 100
E2.roomPriority = 20
E3.roomPriority = 60
```

Sorted: E1, E3, E2.

Pass 2:
```
E1 → walks rooms; tries Lab-1; free → assigned.
E3 → walks rooms; tries Sports-Room (assume one), free → assigned.
E2 → walks rooms; tries each Classroom; first free one (say CR-9) → assigned.
```

If E1's Lab-1 was busy (an earlier placement at the same time, e.g., 10-B Sci-Lab):
```
E1 walks alternates — but its constraint is HARD (`required_room_id`).
No fallback satisfies the hard match → roomConflict=true.
Cell gets has_conflict=true and is_active=false.
```

### 18.4 Why a separate pass and not part of the solver?

Adding rooms to the search space squares the branching factor. A 100-card school with 50 rooms goes from 100 placements to 100×50=5000 possibilities per step. The post-pass sacrifices some optimality for huge speedup.

The cost: rooms can run out for low-priority activities even when a different time-slot would have had room availability. The solver doesn't know to re-time those.

### 18.5 Edge cases
- **No rooms of the required type** → roomConflict, cell flagged.
- **Capacity (sch_rooms.capacity) too small** for class size — currently NOT enforced; cell goes through. Worth flagging as a future check.
- **Lab room hosting a regular lecture** → allowed unless `can_host_lecture=false`. Defaults are permissive.

### 18.6 Interactions
- **Reads:** every placed cell from Phase 1/2/3/3b.
- **Writes:** `room_id` per cell; `has_conflict=true` on room failure.
- **Does NOT** retroactively unplace cards even on room failure — the time placement stands; only the room field is empty/conflicted.

## §19. Diagnostics & Bucketing

### 19.1 Placement diagnostics

For every activity that ended with fewer placements than `required_weekly_periods`:
```
diag[activityId] = {
    expected: required_weekly_periods,
    placed: count of cells in tt_timetable_cell where activity_id = X and is_active=true,
    shortage: expected - placed,
    mostCommonReason: bucket label or "no_candidate_slots",
    sampleBlockingSlot: a (day, period) where placement was attempted and failed
}
```

### 19.2 Bucketing (post-process the force-placements)

Already computed in-phase by §17. Diagnostics roll them up:
```
bucketCounts = {
    A_SIBLING_PARALLEL: count of cells with this bucket,
    A_SIBLING_PARENT:   count,
    B_ROLE_OVERLAP:     count,
    C_REAL_TEACHER:     count,
    D_CAPACITY:         count,
}
```

UI shows a colored badge per bucket so the operator can prioritize C and D fixes (real conflicts) over A and B (often acceptable overlaps).

### 19.3 Edge cases
- **Activity with shortage but no force-placement** → unplaced (rare with non-strict mode). `mostCommonReason` = "no_candidate_slots."
- **Diagnostics computed before room-allocation conflicts** — so a cell with a room conflict but a clean time placement isn't flagged in placement diagnostics. Room conflicts are tracked separately.

## §20. Cross-Cutting Interactions (the easy-to-miss ones)

### 20.1 The teacher state has *three* layers
1. **LPT charge[]** — set during §10, never updated again. Lives only in PHP memory.
2. **`teacherOccupied[T][day][period]`** — mutated on every placement; cleared on every undo. The "real-time" view.
3. **DB `tt_teacher_workload`** — written at persistence, only after publishing. Reflects the final state.

A bug in any one of these is invisible to the others. If you tweak LPT, don't forget Phase 2's lack of charge updates.

### 20.2 The cache only knows about `(card, slot)` — not about teachers
The cache key includes `cardId` but not `teacherId`. If alternative-teacher retry changes a card's teacher mid-Phase-2, the cache doesn't reflect it (cache was cleared at end of Phase 1 anyway, but if not, results would be stale).

### 20.3 Difficulty ordering happens once, frozen
After §11 sorts the cards, that order is the order. Phase 2 walks leftovers in the same order. Phase 3 too. There's no re-prioritization based on what's left over. If a hard-to-place card is at position 800 of 850, it's still attempted at position 800 in every later phase — even though after 25 seconds of partial filling, it might now be the easiest.

### 20.4 Soft constraints don't influence Phase 1 backtracking direction
Slot scoring orders candidates inside the loop, but soft scores don't *force* or *prevent* placement — they only break ties among hard-feasible candidates. So a soft constraint at weight 0.5 has the same effect as one at weight 5.0 in terms of which slot is chosen, *as long as the relative ordering is preserved*. The absolute scale doesn't matter inside Phase 1.

But **at write time** (`tt_timetable.soft_score`), the absolute scale matters for analytics. So weights serve two masters with different sensitivities.

### 20.5 Force-placement violates the constraint system
Phase 3b deliberately ignores hard constraints. Cells written are flagged `has_conflict=true, is_active=false`. The constraint manager isn't informed. So:
- Reports counting "constraint violations" for the published timetable depend on `tt_constraint_violation` rows, written by `bucketForcedPlacements`, not on a re-evaluation pass.
- A subsequent manual edit (refinement) re-runs constraint checks via `RefinementService`, which uses the same constraint manager and treats the force-placed cell as a normal cell (it doesn't know the cell was force-placed). This can produce mysterious "all my cells are fine" reports while bucket counts are non-zero.

## §21. Edge cases & known boundary conditions

### 21.1 Things the algorithms handle gracefully
- Empty activity list → empty timetable, no errors.
- Single-card school → trivially placed at the highest-scoring slot.
- All cards in one parallel group → one placement, all members co-located.
- A teacher with cap=0 → never picked by LPT; activities pinned to that teacher fail in audit.
- A class with window of size 0 (`from > to`) → no candidates; activity diagnostics report "no_candidate_slots" for every card.

### 21.2 Things the algorithms quietly mis-handle
- **Half-day weeks** (different daily targets per day-of-week) — daily target is uniform.
- **Fortnightly schedules** — not modeled; one-week pattern only.
- **Multi-teacher required activities** (team teaching) — LPT picks one; the others not enforced.
- **Cross-class shared resources beyond rooms** (shared equipment, shared specialists) — modeled only via teacher pivot; no per-equipment availability.
- **Day-date variation** (Monday is normal, but specific Monday is half-day) — `tt_class_working_day_jnt` exists but unused.
- **Lab straddling lunch** — class window check passes (window doesn't know about breaks), but break-period gating in `isBasicSlotAvailable` rejects. Card stays unplaced.

### 21.3 Things to test before refining weights
- A **scarcity-stressed dataset** — one specialist teacher covering 2 subjects across 5 classes. Tests if difficulty ordering surfaces them early.
- A **parallel-heavy dataset** — 10+ parallel groups. Tests anchor handling and force-place A_SIBLING bucketing.
- A **room-tight dataset** — 5 labs needed simultaneously, 3 lab rooms exist. Tests room-conflict bucket.
- A **teacher-cap-tight dataset** — every teacher within 95% of cap. Tests audit and LPT balance.
