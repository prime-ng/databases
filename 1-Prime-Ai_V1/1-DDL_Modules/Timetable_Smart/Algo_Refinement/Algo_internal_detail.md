## 0. Read this first — what the system is actually doing

Generating a school timetable is, mathematically, a **Constraint Satisfaction Problem (CSP)**. You have:

- A grid of empty cells: `(class, day, period)`.
- A pile of "cards" called **activities** (e.g., "Class 9-A, Maths, 5 periods/week").
- A web of **constraints** ("teacher can't be in two places at once," "lab needs a 2-period block," "class teacher should take the first period").

Your job: place every card into the right cells without breaking any hard constraint, and if possible without irritating any soft constraint.

There is **no single algorithm** that does this. SmartTimetable runs a *pipeline* of about **15 algorithms in sequence**, each one's output feeding the next. The orchestrator is `TimetableGenerationService`; the heavy CSP engine inside is `PrimeSolver`; room placement runs as a separate post-pass; and several support algorithms (capacity audit, difficulty scoring, constraint evaluation) run before, during, or after the main solve.

**Why so many?** Because each algorithm is good at a *narrow* job. Backtracking is great at "find a complete legal placement" but slow when no complete placement exists. Greedy is fast but myopic. Rescue is "loosen the rules just a bit." Force-place is "give up gracefully and mark conflicts in red." Room allocation is "now that we know *when*, figure out *where*." Each handles what the previous one couldn't.

## 1. The pipeline — order of operations at a glance

Here is the entire generation, top to bottom. Each line is one algorithm; the indentation shows which ones run *inside* a parent.

```
1.  CAPACITY AUDIT                       (pre-flight feasibility check)
2.  REFERENCE LOAD                       (read classes, activities, days, periods, rooms)
3.  CLASS TEACHING WINDOW BUILD          (which periods each class is allowed to use)
4.  CONSTRAINT LOAD                      (turn DB rows into hard/soft objects)
5.  PARALLEL GROUP LOAD + VALIDATE       (combined classes — must move together)
6.  DAILY TARGET BUILD                   (floor/ceiling periods per day per class)
7.  TEACHER WEEKLY CAP BUILD             (each teacher's max periods/week)
8.  PRIME SOLVER  ────────────────────────┐ (the engine)
       8.1  ACTIVITY EXPANSION            │  one card per weekly period
       8.2  LPT TEACHER ASSIGNMENT        │  pick a teacher per card
       8.3  DIFFICULTY ORDERING           │  sort cards hardest first
       8.4  PHASE 1 — BACKTRACKING        │  recursive search, 25 s budget
              uses: SLOT SCORING          │
              uses: CONSTRAINT EVALUATION │
              uses: WINDOW + DAILY CAP    │
       8.5  PHASE 2 — GREEDY              │  fallback for what backtracking left
              uses: ALTERNATIVE TEACHER   │
       8.6  PHASE 3 — RESCUE              │  relax soft pins, retry
       8.7  PHASE 3b — FORCE PLACE        │  last resort, 1-period, marked CONFLICT
9.  ROOM ALLOCATION PASS                 (now place rooms — separate algorithm)
10. SCHOOL GRID BUILD                    (nest into [class][day][period] for UI)
11. PARALLEL COMPLIANCE VERIFY           (sanity check the parallel groups)
12. PLACEMENT DIAGNOSTICS                (per-activity shortage explanations)
13. FORCED-PLACEMENT BUCKETING           (categorize the conflicts A/B/C/D)
14. STORE TO DB                          (skeleton → populate → publish)
```

A 250-student school typically takes 30–40 seconds end-to-end. Phase 1 (backtracking) alone consumes most of that budget; everything else is sub-second.

## 2. The algorithms in detail

For each algorithm I give:
- **Job** — what it solves in one sentence
- **Inputs** — what it needs (and where the previous step produced it)
- **How it decides** — the rule or formula in plain language
- **Parameters that drive it** — the knobs you'd tune
- **Output** — what it hands to the next step
- **What can go wrong** — the failure mode you'd see in production

---

### 2.1 Capacity Audit — "do we even have enough teachers?"

**Job:** Before we waste 30 seconds searching, prove that the demand is even *theoretically* satisfiable.

**Inputs:**
- All activities for the term (`tt_activity` rows): how many weekly periods each one needs.
- For each activity, the eligible teachers (`tt_activity_teacher`).
- Each teacher's weekly cap from `tt_teacher_availability.max_available_periods_weekly`.

**How it decides:** For each teacher, sum the weekly periods of activities that *only that teacher* can cover ("pinned to me"), and the share of activities they could cover. Then bucket the teacher into one of:
- **Overloaded** — pinned demand alone exceeds their cap. Mathematically impossible; abort.
- **Pinned-overloaded** — pinned demand ≤ cap, but pinned + likely share > cap. Abort unless operator clicks *acknowledge*.
- **Tight** — within 90% of cap. Warn but continue.
- **OK** — comfortable headroom.

**Parameters:**
- Teacher cap (default 40 if no row in `tt_teacher_availability`).
- The "tight" threshold (90%, hardcoded today).
- `acknowledge_capacity_warnings` option lets the operator override pinned-overloaded.

**Output:** A list with three buckets (overloaded, pinned-overloaded, tight). If any teacher is in `overloaded`, generation throws and stops. Otherwise the lists are returned for display.

**Failure mode:** Audit passes but the actual solve still fails (e.g., constraints make a feasible-on-paper plan infeasible). This is why we still need the search — the audit is necessary, not sufficient.

---

### 2.2 Reference Load

Not really an algorithm — it's the bulk read of `sch_classes`, `sch_sections`, `sch_class_section_jnt`, `tt_activity` (with eager-loaded teachers/subject/study format), `tt_school_days`, `tt_period_set_period_jnt`, `sch_rooms`. Everything below operates on these in-memory arrays. Mention it because: **the entire pipeline trusts this snapshot. If a teacher is added mid-generation, the run won't see them until the next click.**

---

### 2.3 Class Teaching Window — "what slots is this class even allowed to use?"

**Job:** A toddler section attends only periods 3–11; a senior class attends 1–10. The solver needs to know each class's allowed slot range so it doesn't try to place activities into off-hours.

**Inputs:** `tt_class_timetable_type_jnt` rows (per-class period-set assignment) plus the period-set's `from_period_ord`/`to_period_ord`.

**How it decides:** For each `(class, section)`, look up the `period_set_id` and read its window. Store as `[classKey] → {fromIndex, toIndex}`.

**Output:** A simple lookup table the solver consults on every candidate placement (`isSlotInClassWindow`).

---

### 2.4 Constraint Load — "turn database rows into Yes/No checkers"

**Job:** Read the user-defined constraint rows, instantiate the right PHP class for each, group them as Hard or Soft, and return a manager object the solver can ask "does this placement break any hard rule?"

**Inputs:**
- `tt_constraint` rows for the term, filtered to `is_active=1` and within `effective_from/to`.
- Each row has a `constraint_type_id` pointing at `tt_constraint_type` which has a `code` (e.g., `TEACHER_NOT_AVAILABLE`).
- Each code is mapped to a PHP class via the **ConstraintRegistry** (a global lookup table populated at app boot).

**How it decides:**
1. For each row, look up the code → class.
2. Pass the row's `params_json` (e.g., "this constraint applies to teacher #45 on Monday periods 6–8") into a fresh instance of that class.
3. Drop it into either the *hard* bucket (rejection rules) or the *soft* bucket (scoring rules), based on `is_hard`.

**Parameters:**
- `default_weight` from `tt_constraint_type` if the row didn't override it.
- `applicable_days JSON` for day-of-week scoping.
- `params_json` — varies per constraint type.

**Output:** A `ConstraintManager` with two arrays — `hardConstraints[]` and `softConstraints[]` — plus a built-in evaluation cache. **This object is the most-touched data in the entire run** — every candidate slot pings it.

**Failure mode:** A constraint type code in the DB that has no PHP class registered will fall through to a "generic" class that reads its own meta but does no real check. Silent under-enforcement.

---

### 2.5 Parallel Group Load + Validate — "combined sections must move together"

**Job:** When two sections share a lecture (e.g., 9-A and 9-B sit together for the school assembly), they form a *parallel group*. They must be placed at the same `(day, period)`, with the same duration, and no shared teacher.

**Inputs:** `tt_parallel_group` and `tt_parallel_group_activity` rows.

**How it decides (validation):** For each group, check:
1. **Exactly one anchor** — one activity flagged as the leader.
2. **Equal durations** — every member has the same `duration_periods`.
3. **No teacher overlap** — no teacher appears in two members of the same group.

If any check fails, generation halts with a clear error.

**Output:** A list of parallel groups, each with member-activity IDs and the anchor. The solver later treats the anchor as the "scout" — it places the anchor first, then forces the other members onto the same `(day, period)`.

---

### 2.6 Daily Target Build — "floor and ceiling per day"

**Job:** Compute, for each `(class, day)`, how many periods of teaching can land there. Floor = at least N. Ceiling = at most M.

**Inputs:** `tt_school_days` (which days are working), `sch_academic_term.term_total_teaching_periods_per_day`, plus any class-level slot requirement (`tt_slot_requirement`).

**How it decides:** Total weekly teaching demand for the class ÷ number of working days, then ±1 to give a floor/ceiling band. If the school has a 6-day week and 30 weekly teaching periods, target is 5/day with floor 4, ceiling 6.

**Output:** `[class][day] → {floor, ceil}`. Used inside slot scoring (§2.10).

---

### 2.7 Teacher Weekly Cap Build — "each teacher's bucket size"

**Job:** Build a fast lookup: for any teacher ID, how many periods they're allowed in a week.

**Inputs:** `tt_teacher_availability.max_available_periods_weekly`.

**How it decides:** Straight read, summed across teacher's term-wide availability rows. If no row exists, fall back to a hardcoded default of 40.

**Output:** `[teacherId] → cap`. Consumed by LPT (§2.9) and the running-load check during placement.

---

### 2.8 Activity Expansion — "one card per weekly period"

**Job:** Convert "Maths needs 5 periods/week" into 5 individual cards the solver can place one at a time.

**Inputs:** Each activity's `required_weekly_periods` and `duration_periods`.

**How it decides:** Loop `required_weekly_periods` times. Each iteration creates an instance card carrying the parent activity's metadata. If `duration_periods=2` (e.g., a lab), the card occupies 2 consecutive slots when placed.

**Output:** A flat list of cards (potentially hundreds for a medium school). This is what the solver actually places.

**Why it matters:** All later scoring is per-card, not per-activity. A 5-period subject competes 5 times for slots; a 1-period subject competes once. (This is one of the discrepancies you flagged — the per-card competition gets compounded by the ×500 weight in difficulty ordering.)

---

### 2.9 LPT Teacher Assignment — "give the next class to the least-loaded teacher"

**Job:** When an activity has multiple eligible teachers, pick *one* per card to use throughout the run.

**Acronym:** LPT = **Longest Processing Time** scheduling — a classic load-balancing heuristic borrowed from job-shop scheduling.

**Inputs:** Each card's eligible teachers from `tt_activity_teacher`. A running count of how many periods each teacher has already been pre-charged.

**How it decides:** For each card, among the eligible teachers, pick the one with the *lowest current pre-charge*. Increment that teacher's counter by `duration_periods`. Tie-break randomly.

**Why a "pre-charge"?** The solver hasn't actually placed anything yet, but if every card just blindly picked the most-experienced teacher, that teacher would be over-allocated before search even started. Pre-charging spreads load on paper, before the search confirms it on the grid.

**Parameters:** None (the algorithm is parameter-free; only the cap from §2.7 limits it).

**Output:** Each card now has a single `selectedTeacherId` it'll try to use. Placement search uses *this* teacher; if the slot doesn't fit, **Phase 2 (greedy) tries an alternative teacher** before giving up on the card.

---

### 2.10 Difficulty Ordering — "place the hardest cards first"

**Job:** Sort the cards so the most constrained ones get placed first, while the grid still has lots of free slots. Easy cards fit around them.

**Analogy:** Wedding seating. You place the difficult guests (vegetarian, allergic, disabled access) first; the flexible guests fit in the remaining seats.

**Inputs:** Each card's properties.

**How it decides — the formula (this is the §9 controversy):**

```
score  = activity.difficulty_score_calculated   (0–100, from ActivityScoreService)

if   weeklyPeriods >= 6      → score += 10000   (heavy load first)
score += weeklyPeriods       × 500
score += duration_periods    × 3
score += teachers_count      × 2
if   is_compulsory           → score += 20
if   class_teacher_first_lecture && this is a class-teacher activity:
                                score += 1000 + activity.priority × 20
if   in parallel group       → score += 20000
if   is parallel-group anchor → score += 5000

sort cards descending by score
```

**Parameters / weights:** Every constant above is a tunable. The defaults are wired into PrimeSolver. The current `weeklyPeriods × 500` is what makes a 5-period subject dominate a 1-period one.

**Output:** The same card list, reordered. Phase 1 backtracking walks them in this order.

**Where the discrepancies live:** This formula is the centre of your discrepancy doc. The component breakdown:

| Component | Multiplier | Plain-English meaning |
|---|---|---|
| `difficulty_score_calculated` | ×1 (base 0–100) | Pre-computed elsewhere; effectively swamped by the bigger numbers below. |
| Heavy-load bonus | +10,000 if ≥6 periods | Pushes high-volume subjects to the front. |
| `weeklyPeriods × 500` | Volume signal | The big one — by far the most influential per-card factor. |
| `duration_periods × 3` | Block size | A 2-period lab gets +6, a 1-period lecture gets +3. Trivial. |
| Teacher count × 2 | Multi-teacher penalty | Multi-teacher activities are harder to place, but the multiplier is small. |
| Compulsory +20 | Flag | Effectively noise next to the others. |
| Class-teacher bonus +1,000 | Pinning | Reserves the first period for the class teacher. Strong but not as strong as parallel. |
| Parallel-group +20,000 | Coordination | Dwarfs everything else — parallel anchors always go first. |
| Anchor +5,000 | Within parallel | Within a group, the anchor leads. |

### 2.11 Phase 1 — Backtracking Search (the main engine)

**Job:** Find a complete legal placement (every card on the grid, no hard violations).

**Analogy:** Sudoku. You put a number in a cell; if it doesn't work, you erase it and try a different number. If no number works, you erase the *previous* cell too and try a different number there.

**Inputs:**
- The ordered card list from §2.10.
- The constraint manager from §2.4.
- The grid (initially empty), tracked as three nested arrays:
  - `placements[instanceId]` — where each card landed
  - `occupied[classKey][dayId][periodId]` — what's in each cell
  - `teacherOccupied[teacherId][dayId][periodId]` — what each teacher is doing

**How it decides — the recursive loop:**
```
function backtrack(index):
    if index == cards.length:
        return success                            # all placed!
    card = cards[index]
    candidates = getPossibleSlots(card)           # filter by class window, duration
    for each slot in candidates (best score first):
        if isBasicSlotAvailable(card, slot)
        and constraintManager.checkHardConstraints(slot, card, ctx):
            place(card, slot)
            if backtrack(index + 1):              # recurse to next card
                return success
            undo(card, slot)                      # didn't work — try next slot
    return failure                                # no slot works — caller will undo
```

**Slot ordering inside the loop:** Candidates are sorted by **slot scoring** (§2.12) — best score first — so the search exploits the soft preferences while it still has freedom.

**Hard cutoffs (parameters):**
- `backtrack_timeout` = 25 seconds. After this, abort to Phase 2.
- `max_iterations` = 50,000.
- `max_backtracks` = 50,000.

**Why it's slow:** In the worst case, the search tree is exponential in the number of cards. Real timetables fall in a "polynomial-but-painful" zone — the heuristics (difficulty ordering, slot scoring, constraint cache) are what make it tractable.

**Output:** Either a complete placement (`success`) or a partial placement at timeout. Either way, control passes to Phase 2.

---

### 2.12 Slot Scoring — the soft-score formula (used inside backtracking)

**Job:** Among the slots that satisfy hard constraints, prefer the slot that satisfies the most *soft* preferences. Used to order candidates inside the backtracking loop.

**Inputs:** The candidate slot, the card, the activity's preference fields, the day-balance state.

**Formula (this is the §8.5 discrepancy zone):**

| Signal | Bonus / Penalty | Source |
|---|---|---|
| Activity's `preferred_time_slots_json` exact `(day, period)` match | +40 | `tt_activity` |
| Activity's `avoid_time_slots_json` match | −50 | `tt_activity` |
| Activity's `preferred_periods_json` (any day, this period) | +20 | `tt_activity` |
| Activity's `avoid_periods_json` | −30 | `tt_activity` |
| `spread_evenly` and day already has 0 placements | +10 | `tt_activity` |
| `spread_evenly` and day already has ≥1 placement | −15 | `tt_activity` |
| Day-balance: post-place count below floor | +25 | derived (§2.6) |
| Day-balance: post-place count within floor/ceil band | −10 | derived |
| Day-balance: post-place would exceed ceiling | **−1,000** (effective hard reject) | derived |
| `min_per_day` not yet met on this day | +15 | `tt_activity` |
| `split_allowed=false` and would land on a *new* day | −100 | `tt_activity` |
| Sum of soft constraints satisfied (× 0.5) | varies | `tt_constraint` rows |

**How it decides:** Slot with the highest score is tried first inside the backtracking loop. If it leads to a dead end, the next-best is tried, and so on.

**Output:** A score per slot. Used to order, not to filter.

### 2.13 Constraint Evaluation Engine — the inner heartbeat

**Job:** Answer "would placing this card in this slot break any hard rule?" and "what soft score does it get?"

**Inputs:** Slot, card, current placement context, the constraint manager from §2.4.

**How it decides:**
1. Build a cache key: `{type}-{classKey}-{dayId}-{startIndex}-{cardId}`.
2. If we've evaluated this exact tuple before, return the cached answer.
3. Otherwise, walk all hard constraints. As soon as one fails, return *false* and cache it. If all pass, the card-slot is valid.
4. For soft scoring: walk all soft constraints, sum their scores.

**Why caching matters:** During backtracking, the same `(slot, card)` tuple is asked about thousands of times. Without caching, generation would balloon to minutes. **The cache is cleared on every backtrack** (otherwise stale negative answers from an undone branch would poison new searches).

**Parameters:** None — this is mechanical.

**Output:** A bool (hard) or a float (soft) per query.

---

### 2.14 Phase 2 — Greedy Placement (and Alternative-Teacher Retry)

**Job:** Whatever Phase 1 left unplaced (because of timeout or dead end), try to fit greedily — best-slot-first, no backtracking.

**Inputs:** The partial placement from Phase 1, plus the still-unplaced cards.

**How it decides:** For each unplaced card:
1. Get candidate slots, sorted by slot score (§2.12).
2. Try the top slot. If hard constraints pass, place it and move on.
3. If no slot works with the originally-assigned teacher, call `tryAlternativeTeacher()` — re-pick a teacher from the eligible list and rerun the candidate search.
4. If still nothing, leave the card for Phase 3.

**Why "greedy"?** It commits to its first valid placement and never reconsiders. Fast but myopic.

**Output:** A fuller placement; whatever's still unplaced goes to Phase 3.

---

### 2.15 Phase 3 — Rescue Pass (relax pinning)

**Job:** Some cards failed because of *soft pins* — like "place class-teacher activities first" or "pin Maths to period 2 every day." When demand is tight, those pins block legal placements. Rescue temporarily turns them off.

**Inputs:** The partial placement after Phase 2, plus the still-unplaced cards.

**How it decides:** Re-run the greedy logic but with these relaxations applied (in priority order, until the card fits):
1. Drop the **same-period pin** (`pin_activities_by_period`) — let the card go to a different period than its sibling instances.
2. Drop the **daily cap** (`auto_relax_daily_cap_on_overflow`) — allow N+1 periods in a day if the alternative is no placement.
3. Drop the **class-teacher-first** preference if the card is the class teacher's.
4. Drop the **consecutive** preference if `allow_consecutive_periods=false` was the only blocker.

**Parameters:** Each relaxation can be independently disabled via the generation options.

**Output:** A still-fuller placement. Whatever remains unplaced goes to Phase 3b.

---

### 2.16 Phase 3b — Force-Placement (last resort)

**Job:** If a card *still* can't be placed legally, drop it onto the schedule with a **conflict marker** rather than silently dropping it. Operator sees red cells and decides what to do.

**Inputs:** Whatever Phase 3 couldn't place.

**How it decides:**
1. Restrict to **1-period** placements (no multi-period blocks here).
2. For each unplaced card, find any slot where placing it would only conflict with:
   - A sibling activity in the same parallel group, or
   - A sibling activity that's a sub-activity of the same parent, or
   - A teacher in an `allows_overlap=true` role (e.g., co-teacher), or
   - Otherwise — a real teacher conflict, or
   - A capacity overflow.
3. Place it there, but flag the cell as `is_active=false, has_conflict=true` (the third state in the cell lifecycle).

**Disabled when:** `strict_no_conflicts=true` is set on the request — then unplaced cards are simply dropped.

**Output:** A placement where every card has *some* slot, but some are flagged red. Goes into bucketing (§2.21).

---

### 2.17 Room Allocation Pass — "now that we know *when*, figure out *where*"

**Job:** Up to here, the solver only cared about `(class, day, period, teacher)`. Now assign each placed card to a physical room.

**Why separate?** Rooms add a whole new constraint dimension. Doing it during search would multiply the search space. By post-processing, we keep search fast and accept that occasionally a room conflict forces re-scheduling.

**Inputs:** The placed cards from Phase 1/2/3, the room master (`sch_rooms`), room-type master, room availability detail.

**How it decides — priority cascade:**

```
For each placement, score the activity's room requirements:
  required_room_id (HARD specific room)        → +100
  compulsory_specific_room_type                → +80
  required_room_type_id                        → +60
  preferred_room_ids JSON (any of these)       → +30
  preferred_room_type_id (any room of type)    → +20
  no preference                                → 0

Sort placements by room-priority descending.
For each placement, walk rooms in this order:
  1. Try the HARD specific room (rejecting if busy).
  2. Try a SOFT preferred room (any-of list).
  3. Try a room of the preferred type.
  4. Fall back to any free room of any acceptable type.
  5. If nothing free → mark room conflict.
```

**Parameters:** The 100/80/60/30/20 ladder is hardcoded.

**Output:** Each cell now has a `room_id`. Cells with room conflicts get the same `is_active=false, has_conflict=true` flag.

### 2.18 School Grid Build

Reorganizes the flat list of placements into the 3-D structure the UI expects: `[classKey][dayId][periodId] → cell`. Trivial — not really an algorithm, but worth naming because everything downstream (preview render, exports, conflict detection) reads from this shape.

---

### 2.19 Parallel Compliance Verify

**Job:** Sanity-check that every parallel group ended up with all members on the same `(day, period)`. If somehow they didn't (a bug, a relaxed rescue, or a force-place misfire), this surfaces it.

**How it decides:** For each parallel group, walk every member's placement. They should match in `(day, startIndex)`. Any mismatch is a violation logged to the conflicts list.

**Output:** A list of parallel-violations to display to the operator.

---

### 2.20 Placement Diagnostics

**Job:** For every activity that didn't get fully placed, explain *why* — was it teacher-conflict, room-conflict, capacity, window-violation? This is the "Why didn't this fit?" tooltip in the UI.

**How it decides:** Walks the failure reasons recorded by each phase (the solver keeps a log of "tried slot X, blocked by constraint Y"). Aggregates the most common blocker per activity.

**Output:** `[activityId] → { shortage, mostCommonReason, sampleBlockingSlot }`. Pure diagnostics — does not change the placement.

---

### 2.21 Forced-Placement Bucketing

**Job:** Categorize the conflicts produced in Phase 3b so the operator can read them quickly.

**Buckets:**
- **A_SIBLING_PARALLEL** — overlap is with another member of the same parallel group. Often acceptable (they're meant to overlap).
- **A_SIBLING_PARENT** — overlap is with a sub-activity of the same parent. Often a split-lab case.
- **B_ROLE_OVERLAP** — overlap is with a teacher in a role that allows overlap (co-teacher / assistant). Soft conflict.
- **C_REAL_TEACHER** — overlap is a genuine teacher double-booking. Operator must fix.
- **D_CAPACITY** — placement breaks a daily/weekly cap. Operator must fix.

**How it decides:** For each force-placed cell, check the conflict source against the bucket conditions in order. First match wins.

**Output:** A bucketed conflict list. UI surfaces the four categories with different colors so the principal can triage.

---

### 2.22 Persistence (skeleton → populate → publish)

Not an algorithm but worth naming because the **3-state cell model** lives here:

| `is_active` | `has_conflict` | Meaning |
|---|---|---|
| true | false | A real placed lesson — green |
| true | true | Placed but has a room/teacher problem — amber |
| false | true | Force-placed (real conflict) — red, doesn't count as a real lesson |
| false | false | Untouched skeleton — empty period |

The skeleton is created up-front (so the timetable exists in `tt_timetable_cell` from second 0). After Phase 3b finishes, `populateFromResult` issues bulk UPDATEs to flip cells to their final states. `publishTimetable` then archives the prior active timetable and flips the new one to PUBLISHED.

```
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  DIFFICULTY ORDERING → cards sorted hardest first                  │
└────────────────────────────────┬───────────────────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  PHASE 1 — BACKTRACKING                                            │
│      consults: WINDOWS, CAPS, CONSTRAINT MGR (with cache)          │
│      uses:     SLOT SCORING to order candidate slots               │
│  → partial or complete placement                                   │
└────────────────────────────────┬───────────────────────────────────┘
                                 │ (unplaced cards continue)
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  PHASE 2 — GREEDY (+ alternative-teacher retry)                    │
└────────────────────────────────┬───────────────────────────────────┘
                                 │ (still-unplaced)
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  PHASE 3 — RESCUE (relax soft pins)                                │
└────────────────────────────────┬───────────────────────────────────┘
                                 │ (still-unplaced)
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  PHASE 3b — FORCE PLACE (1-period only, marked CONFLICT)           │
│             [skipped if strict_no_conflicts=true]                  │
└────────────────────────────────┬───────────────────────────────────┘
                                 │ (every card now has a slot)
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  ROOM ALLOCATION PASS                                              │
│  → each cell now has a room_id (or a room_conflict)                │
└────────────────────────────────┬───────────────────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  GRID BUILD → [class][day][period] structure                       │
│  PARALLEL VERIFY → list of any parallel-group violations           │
│  DIAGNOSTICS → why-didn't-this-fit per activity                    │
│  BUCKETING → A/B/C/D categorization of the red cells               │
└────────────────────────────────┬───────────────────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│  PERSIST → tt_timetable_cell UPDATEs, tt_timetable_cell_teacher    │
│            INSERTs, tt_timetable status flip                       │
└────────────────────────────────────────────────────────────────────┘
```

**The key insight on data flow:**
- **Phase 1 outputs the *partial* placement state** (the three nested grids: `occupied`, `teacherOccupied`, `placements`). Phase 2 inherits all three and continues mutating.
- **Phases 2, 3, 3b all share the same in-memory state** — they don't rebuild it. They are layered fallbacks on the same canvas.
- **Room allocation reads the placement but only writes the room field.** It can't move a card to a different time, so if no room fits, the card stays where it is and gets a room_conflict flag.
- **Diagnostics and bucketing are read-only** — they observe the placement and produce reports, but never modify it.

This is why a refinement to one phase rarely breaks another: each phase has clean inputs (the previous phase's state + the static reference data) and a clear output (an evolved placement state). You can replace Phase 1 with a different solver (e.g., genetic, simulated annealing — both schema-allowed but unimplemented) without touching Phases 2/3/3b, as long as it produces the same shape of state.

## 5. Where each algorithm can go wrong

A debugging cheat sheet — when the timetable looks wrong, this tells you which algorithm's decision to suspect.

| Symptom | Most likely culprit | Why |
|---|---|---|
| "Easy subject placed early, hard subject force-placed" | **Difficulty ordering** | weeklyPeriods×500 over-rewards volume vs. scarcity. |
| "Some teachers idle, others maxed out" | **LPT assignment** | LPT only sees pre-charge from selectedTeacher; alternative-teacher rotation in Phase 2 doesn't update LPT counters. |
| "Lots of red cells in Phase 3b" | **Capacity audit missed it** | Audit is per-teacher; doesn't catch room-bottlenecks or constraint-cluster bottlenecks. |
| "Class teacher *not* in first period" | **Slot scoring** | The +1000 difficulty bonus is on *ordering*; the actual first-period preference is enforced via a soft constraint that can be outvoted. |
| "Lab placed straddling lunch" | **Class teaching window** filter is OK but **break-period gating** in `isBasicSlotAvailable` rejected it — symptom usually shows as "lab couldn't be placed at all." |
| "Two activities scheduled in the same room" | **Room allocation** ran out of rooms; check the cell's `has_conflict` flag. |
| "Generation takes 60 s+ on a small school" | **Constraint cache** likely thrashing — too many constraints or too many cards causing key explosion. |
| "Generation failed silently" | **Phase 1 timeout** + Phase 2/3/3b chain disabled by `strict_no_conflicts`. |
| "Parallel group split across periods" | **Parallel verify** would flag it — check the diagnostics output. |
| "Force-placement bucketing miscategorizes a conflict" | **Bucketing** — it's first-match-wins, so the order matters; an A_SIBLING_PARALLEL match short-circuits a real C_REAL_TEACHER. |

## 6. What's *not* an algorithm but is often confused with one

- **Constraint Manager** — a registry of yes/no checkers. Not itself an algorithm; it's the data structure the engine consults.
- **`tt_priority_config`** — a precomputed scoring table per requirement (7 indices: tot_students, teacher_scarcity, weekly_load_ratio, etc.). It's *input* to ActivityScoreService → `difficulty_score_calculated`. Not consumed directly by the solver.
- **`ActivityScoreService::calculateDifficultyScore`** — runs *before* generation (separate trigger). Computes the 0–100 score that becomes the base for the §2.10 ordering formula.
- **Soft constraints** — they don't *decide*; they *score*. Their score is summed in §2.12 and used to break ties between candidate slots. None of them can reject a placement.

## 7. One-paragraph recap (for explaining to someone else)

> SmartTimetable runs a **15-step pipeline**. First it audits whether teacher capacity is sufficient (gate). Then it loads everything it needs into memory: classes, activities, school days, periods, constraints, parallel groups, room masters. It expands "5 periods/week" into 5 individual cards, hands each card to its lightest-loaded eligible teacher (LPT), and sorts the cards from hardest to easiest using a weighted formula (parallel groups first, then volume × 500, etc.). The main solver is a **recursive backtracking search** with a 25-second budget — it tries the best slot for each card and, when a card can't be placed, backs up and retries the previous card. Whatever backtracking can't finish in 25 s is handed to a **greedy fallback**, then a **rescue pass** that relaxes soft pins, then a **force-placement** that drops cards into conflict-flagged cells. Once every card has a time slot, a separate **room allocation pass** assigns physical rooms using a HARD→SOFT priority cascade. Finally the system builds the UI grid, verifies parallel groups, computes "why didn't this fit?" diagnostics, buckets the conflicts into A/B/C/D categories, and persists everything to the database. Each step's output is the next step's input — every fallback layer operates on the same in-memory placement state, so refining any single step is safe as long as it produces the same shape of state.
