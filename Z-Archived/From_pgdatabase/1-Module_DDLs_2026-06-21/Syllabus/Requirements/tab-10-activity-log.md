# Syllabus Tab 10: Activity Log

This tab provides a comprehensive audit trail of all syllabus-related changes. It tracks coverage snapshots over time, individual CRUD operations on syllabus entities, and topic equivalency mappings across academic sessions.

---

## How It Works

The screen presents a filterable timeline of syllabus activity. The user can filter by entity type (Lesson, Topic, Competency, Schedule), by action type (Create, Update, Delete, Import, Lock), by user, by date range, and by class-subject combination.

The main view shows a paginated, chronological list of events. Each event entry shows the date and time, the user who performed the action, the entity type and name, the action performed, and a brief description of what changed. For updates, the previous and new values are shown where relevant.

A Coverage Snapshots section displays summary data captured at regular intervals (weekly or monthly). Each snapshot records the total lesson count, topic count, mapped competencies count, scheduled entries count, and completion percentage for each class-subject pair. This enables trend analysis over the academic year — for example, seeing how syllabus coverage has grown month over month.

A Topic Equivalency section allows users to map topics from one academic session to another. When a new academic year starts and lessons are revised, the equivalency mapping shows which topics from the previous year are equivalent to which topics in the current year. This is critical for longitudinal student performance analysis — a student's mastery data from last year's "Linear Equations" topic can be carried forward to this year's equivalent topic.

---

## Important Business Rules

- The activity log is read-only. No actions can be performed from this tab.
- Activity data is captured automatically by the system through model event listeners or database triggers. Manual entry is not supported.
- Coverage snapshots are generated by a scheduled job (cron). The default interval is weekly, configurable by the school.
- Topic equivalency mapping is typically done once per academic year during the syllabus migration period.
- An equivalency mapping is not required for every topic — only topics that have a direct counterpart in the previous year's syllabus.
- Activity logs are retained for the life of the school's subscription. No automatic purging occurs.
- When viewing activity for a deleted entity, the entity name is displayed as "[Deleted]" along with the entity ID.
- The system logs all CRUD operations on slb_lessons, slb_topics, slb_topic_competency_jnt, slb_syllabus_schedule, and hpc_lesson_version_control tables.
- Topic equivalency is a 1:1 mapping — one current topic maps to exactly one previous topic. A separate junction or equivalency table handles this at the application level (not present in the core DDL, implemented via application logic).

## Database Columns & Behavior

### slb_lessons (audited via triggers)
- All columns are captured in audit log on INSERT, UPDATE, DELETE. The audit stores the old and new values for each changed column.

### slb_topics (audited via triggers)
- All columns are captured in audit log. Special attention to `path`, `path_names`, `code`, and `analytics_code` changes for hierarchy rebuild tracking.

### slb_topic_competency_jnt (audited via triggers)
- Changes to topic-competency mappings are logged including the weightage and is_primary flag changes.

### slb_syllabus_schedule (audited via triggers)
- Schedule changes are logged including teacher reassignments, date changes, and priority changes.

### hpc_lesson_version_control (audited via triggers)
- Version status transitions are logged for compliance and audit purposes.

### hpc_curriculum_change_request (audited via triggers)
- Change request lifecycle events are logged: creation, submission, approval, and rejection.

### Coverage Snapshots (application-level storage)
- Stored in a dedicated application table or as JSON snapshots. Fields captured per class-subject pair: total_lessons, total_topics, total_competencies_mapped, total_scheduled_entries, completion_percentage, snapshot_date.

### Topic Equivalency Mapping (application-level storage)
- Stored in a dedicated junction table or application-level structure. Fields: from_topic_id (previous year), to_topic_id (current year), academic_session_id_from, academic_session_id_to, mapping_type (DIRECT, SPLIT, MERGED), created_by, created_at.

## Deep Analysis

### Business Workflows & State Machines
- **Activity Log View** → read-only timeline; filter by entity type, action, user, date range, class-subject → paginated list.
- **Coverage Snapshot Generation** → scheduled cron job (default weekly) → aggregate lesson/topic/competency/schedule counts per class-subject → INSERT snapshot record.
- **Topic Equivalency Mapping** → curriculum coordinator maps topics across academic sessions → one-time setup during rollover → 1:1 mapping (one current topic → one previous topic).
- **State machine**: None — activity log is pure audit (append-only). Coverage snapshots are generated by cron (no user action). Equivalency mapping is a straight CREATE/UPDATE.

### Validation Rules & Edge Cases
- **Read-only enforcement** — no create/edit/delete actions on the timeline; UI must disable all mutation buttons.
- **Deleted entity display** — if the source entity has been hard-deleted, display "[Deleted] (ID: 123)".
- **Activity log retention** — retained for life of school subscription; no automatic purge.
- **Coverage snapshot** — if cron fails, the gap in snapshots is visible; must handle missing snapshots gracefully in trend line charts.
- **Equivalency mapping uniqueness** — one `to_topic_id` maps to exactly one `from_topic_id`; duplicate mapping rejected at app layer.
- **Mapping types** — DIRECT (same topic), SPLIT (one old → multiple new), MERGED (multiple old → one new); stored as ENUM.
- **Cross-session mapping** — `academic_session_id_from` must be from a prior session; `academic_session_id_to` must be the current session; validated at app layer.
- **Manual entry not supported** — all activity data is system-generated via model event listeners or DB triggers.

### Integration Points
- `slb_lessons` — audit triggers on INSERT/UPDATE/DELETE.
- `slb_topics` — audit triggers; path/code changes logged.
- `slb_topic_competency_jnt` — mapping changes logged.
- `slb_syllabus_schedule` — schedule/teacher reassignment changes logged.
- `hpc_lesson_version_control` — version status transitions logged.
- `hpc_curriculum_change_request` — change request lifecycle logged.
- **Cron/scheduler** — generates weekly coverage snapshots.
- **Student longitudinal performance** — reads equivalency mapping to carry forward mastery data across academic years.
