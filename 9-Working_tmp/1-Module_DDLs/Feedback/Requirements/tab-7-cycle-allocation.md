# Feedback Tab 7: Cycle Allocation

This screen manages the explicit list of targets for each feedback type within a cycle. It shows who is being rated, by whom, and tracks participation — how many responses were expected versus how many have been received. The target list can be auto-populated by the system or entered manually by the administrator.

---

## How It Works

When a cycle feedback type is configured with auto-populated targets enabled, the system automatically computes the list of eligible targets based on the relationship type's context rule. For example, for STUDENT_TO_CLASS_TEACHER, the system finds all class teachers and counts their students as potential respondents. The administrator can review this auto-generated list and make adjustments.

For manual target allocation, the administrator uses a search and select interface to pick specific targets. They can add individuals (specific teachers, students, employees) or aggregate entities (departments). The administrator can also set the context for each target, such as which class section or subject applies.

The screen shows each target with its type, identity, context information, the expected number of respondents, how many have submitted, and how many responses meet the submitted status. This helps administrators monitor participation and identify targets that need attention or reminders.

---

## Important Business Rules

- Auto-populated targets are generated by a scheduled job or on-demand by the administrator. The computation respects the relationship type's context rule to find valid respondent-target pairs.
- A target can appear in multiple cycle feedback types within the same cycle if different relationships point to the same person (e.g., a teacher who is both a class teacher and subject teacher).
- When auto-population is enabled, targets are recomputed each time the cycle status changes to Active. Manual additions made after auto-population are preserved.
- Expected response count is computed as the number of eligible respondents for that target in this feedback type. This count is recalculated when the cycle activates.
- Received response count includes all responses (Draft + Submitted) while submitted response count only counts responses with status = Submitted.
- The administrator can manually add individual targets even when auto-population is enabled. These additional targets are preserved during re-computation.
- A target cannot be removed if it has existing responses. The target record is soft-deactivated instead, and existing responses remain valid.
- The context fields (class_section_id, subject_id, tt_activity_id, context_json) capture the specific context in which the target is being evaluated for this cycle.

## Database Columns & Behavior

### fbk_cycle_targets
- `id` — Primary key. INT UNSIGNED, auto-increment.
- `cycle_id` — FK to fbk_cycles.id. INT UNSIGNED. Cascade delete.
- `cycle_feedback_type_id` — FK to fbk_cycle_feedback_types.id. INT UNSIGNED. Cascade delete.
- `target_type_id` — FK to fbk_target_types.id. Denormalised from the relationship type. SMALLINT UNSIGNED.
- `target_user_id` — FK to sys_users.id. Populated when target is a user (teacher, staff, admin). INT UNSIGNED, nullable.
- `target_student_id` — FK to std_students.id. Populated when target is a student. INT UNSIGNED, nullable.
- `target_employee_id` — FK to sch_employees.id. Populated when target is an employee (driver, warden, etc). INT UNSIGNED, nullable.
- `target_department_id` — FK to sch_departments.id. Populated when target is a department. INT UNSIGNED, nullable.
- `class_section_id` — FK to sch_class_section_jnt.id. Context class-section. INT UNSIGNED, nullable.
- `subject_id` — FK to sch_subjects.id. Context subject. INT UNSIGNED, nullable.
- `tt_activity_id` — FK to tt_activity.id. Precise subject-teacher context. INT UNSIGNED, nullable.
- `context_json` — Flexible context data like transport route or hostel. JSON, nullable.
- `expected_response_count` — Total eligible respondents. INT UNSIGNED, default 0.
- `received_response_count` — Responses received (any status). INT UNSIGNED, default 0.
- `submitted_response_count` — Responses with Submitted status only. INT UNSIGNED, default 0.
- `is_active` — Soft delete flag. TINYINT(1), default 1.

## Deep Analysis

### Business Workflows & State Machines

This tab manages the target list for each cycle feedback type. The primary workflows are:

1. **Auto-population**: On cycle activation (or on-demand), the system runs a computation job that walks the relationship type's context rule and inserts rows into fbk_cycle_targets. This is a batch insert/upsert operation.
2. **Manual addition**: Admin searches for entities (by name, ID, class, etc.) and adds them as targets. The system creates a new fbk_cycle_targets row with the appropriate target identity column populated.
3. **Removal**: Admin can remove (soft-deactivate) a target only if it has zero responses. Targets with existing responses get is_active=0.
4. **Re-computation**: When auto-population is re-run, the system must merge auto-generated targets with manually added targets. Manual additions are identified by a flag (either a dedicated column or by inferring from the absence of auto-population logic).

No formal state machine on individual targets — they are either active (is_active=1) or soft-deactivated (is_active=0).

### Validation Rules & Edge Cases

- **Polymorphic target identity**: Exactly one of target_user_id, target_student_id, target_employee_id, target_department_id must be populated, determined by fbk_target_types.linked_entity_table_id. The application must enforce this constraint (the DB has nullable columns but no CHECK constraint).
- **Duplicate prevention**: The same combination (cycle_id, cycle_feedback_type_id, target identity) should not have duplicate active rows. A UNIQUE index or application-level check is needed.
- **Removal with responses**: If fbk_responses.cycle_target_id references this target, deletion is blocked. The UI should offer deactivation instead.
- **Auto-population with manual additions**: The merge algorithm must:
  - Keep all existing manually-added targets (even if auto-population would not regenerate them).
  - Add new auto-generated targets that don't already exist.
  - Remove auto-generated targets that are no longer valid (if context changed). Manual targets are never removed by auto-population.
  - Flag: The current schema lacks an "is_auto_populated" flag. The application needs a way to distinguish auto from manual rows. Use a convention (e.g., if target matches an auto-population query result, mark it) or add a dedicated column.
- **Expected response count computation**: This is the count of eligible respondents for this target. For STUDENT_TO_CLASS_TEACHER, it's the number of students in the class section(s) the teacher teaches. This count can change between cycles (enrollment changes).
- **Participation count staleness**: received_response_count and submitted_response_count are maintained on every response submission/withdrawal. There is a risk of drift if responses are manually deleted or if the counts are not atomically updated. Use DB triggers or application-level atomic updates.
- **Context restriction by scope**: When the cycle feedback type has a scope filter (scope_type_id = Specific_Classes), the auto-population must respect the filter. If scope_filter_json contains class_section_ids, only targets within those class sections are generated.
- **Large datasets**: A school may have thousands of targets per cycle feedback type. The auto-population job should be run asynchronously (queue job) with progress tracking.

### Integration Points

- **fbk_cycles** via cycle_id — cascade delete removes all targets.
- **fbk_cycle_feedback_types** via cycle_feedback_type_id — cascade delete.
- **fbk_target_types** via target_type_id — determines polymorphic identity column to use.
- **sys_users** via target_user_id — for user-type targets (teachers, staff).
- **std_students** via target_student_id — for student targets.
- **sch_employees** via target_employee_id — for employee targets (drivers, wardens, etc.).
- **sch_departments** via target_department_id — for department aggregates.
- **sch_class_section_jnt** via class_section_id — context resolution.
- **sch_subjects** via subject_id — subject context.
- **tt_activity** via tt_activity_id — timetable activity context.
- **fbk_responses** via cycle_target_id — participation tracking and deletion guard.
- **Auto-population engine**: Scheduled job or on-demand service that walks the relationship type's context rule and generates target rows.
