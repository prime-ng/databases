## Section 1: Module Overview

### 1.1 Purpose
StudentProfile (STD) is the foundational student data module for every school in the Prime-AI platform. It manages the complete student information lifecycle from initial admission registration through transfer or alumni status. Every other school module that references student data draws from this module.

### 1.2 Business Value
- Reduce new student admission time from days to under five minutes
- Maintain a single authoritative student registry, eliminating duplicate records
- Provide each student and parent with system access credentials immediately upon admission
- Enable all downstream modules (fees, timetable, exams, transport, LMS) to access consistent, accurate student data
- Support government compliance reporting: RTE, EWS, caste category, Aadhar, APAAR
- Record complete academic history, health information, and attendance for every enrolled student
- Provide a structured digital leave workflow replacing paper applications

### 1.3 Scope

**In Scope:**
- Student system account creation and credential management
- Demographic profile: identity documents, extended profile, addresses, photo
- Guardian and parent records, and parent portal access management
- Academic session enrollment, class assignment, and session history
- Subject selection per enrollment (for optional-subject schools)
- Previous education history
- Student document upload and verification
- Health profile, vaccination records, and medical incident logging
- Daily attendance marking (individual, QR scan, and bulk class)
- Attendance correction workflow (two-step approval)
- Student leave type configuration (school admin)
- Leave application lifecycle (8-state FSM): submission, teacher review, communication thread, document upload, automatic attendance update on approval
- Student lifecycle: status toggle, archive (soft delete), restore, permanent removal
- Profile completion tracking
- Administrative reports: Admission Register, Student Strength, Medical Profile

**Out of Scope:**
- Fee management and invoicing (StudentFee module)
- Student portal self-service views (StudentPortal module)
- Period-wise and subject-wise attendance recording (Timetable / LMS modules)
- Behavioral assessment (BehaviouralAssessment module)
- Admission enquiry and lead management (Admission module)
- Alumni management after student departure
- HR and staff leave management (HrStaff module)
- Student ID card physical printing automation
- Finance accounting entries (Accounting module)

### 1.4 Terminology

| Business Term | Definition |
|---|---|
| Student Record | The master entry for a student comprising system account, demographic profile, guardian links, and enrollment history |
| Admission Number | A school-assigned unique identifier for each student; system auto-format: STD-YYYY-000001 |
| Student Code | System-generated sequential code stored in the user account (same as Admission Number) |
| Academic Enrollment | The assignment of a student to a specific class-section in an academic year, with status and roll number |
| Current Enrollment | The one active academic enrollment per student, enforced at the database level via a unique constraint |
| Guardian | A parent, legal guardian, or emergency contact linked to a student; may hold parent portal access |
| Profile Completion | A five-stage indicator: Account, Demographics, Guardian, Enrollment, Previous Education |
| Leave Application | A formal digital request for student absence, subject to class teacher review and decision |
| Leave Type | A configurable category of student leave (e.g., Sick Leave, Casual Leave) with associated policies |
| Attendance Correction | A formal request to amend a previously recorded attendance entry, requiring two-step approval |
| RTE | Right to Education — government quota for underprivileged students |
| EWS | Economically Weaker Section — government category for fee concessions |
| APAAR ID | Academic Bank of Credits ID — 12-digit national student identifier (India) |
| Aadhar | National biometric identity document issued by UIDAI (12-digit) |
| Transfer Certificate (TC) | Official document issued when a student transfers out of the school |
| Session Status | The current lifecycle state of an academic enrollment: Active / Promoted / Left / Suspended / Alumni / Withdrawn |
| Timetable Eligibility | A flag on the enrollment indicating whether the student is counted in timetable slot generation |

## Section 3: Functional Requirements

### REQ-STD-001: Student List & Search
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][REPORT]
**Description:** The system provides a paginated, searchable, filterable list of all students in the school, enabling staff to quickly locate any student and take action.

**Actors:** School Admin, Registrar, Principal, Class Teacher (own class only)
**Business Rules:** None specific — general access control applies

**Acceptance Criteria:**
1. The list is paginated at 12 students per page, ordered by most recently created. YES/NO
2. Staff can search by admission number, first name, last name, student code, email, or mobile. YES/NO
3. Staff can filter by active/inactive status and by profile completeness (complete / incomplete). YES/NO
4. Each student card displays: photo, name, admission number, class-section, and session status. YES/NO
5. A user without the View Students permission cannot access the list (access denied). YES/NO

**Integration:** Reads class-section from School Setup; reads academic session from the academic calendar.

### REQ-STD-002: Student System Account Creation

## Section 6: Workflows

### Workflow 1: New Student Admission
**Trigger:** Admin or Registrar initiates a new admission
**End States:** Profile complete with credentials dispatched; or partial profile in progress
**Actors:** School Admin / Registrar | System

**Steps:**
1. Staff creates student account (Tab 1) → System generates Student Code, creates system login, assigns Student role → dispatches welcome email
2. Staff enters demographic details (Tab 2) → System validates Admission Number and Aadhar uniqueness → saves profile
3. Staff records address(es) → System validates city; saves addresses
4. Staff links guardian(s) (Tab 3) → System validates mobile uniqueness → saves guardian and junction flags
5. Staff assigns academic enrollment (Tab 4) → System validates no duplicate year; sets as Current within a database transaction
6. Staff records previous education (Tab 5) → System saves history records
7. (Optional) Staff uploads documents, records health profile, vaccination records
8. System recalculates profile completion percentage

**Exception Paths:**
- Duplicate email → Account creation rejected; staff must use a different email or locate the existing user
- Duplicate admission number → Rejected at save; staff must assign a unique number
- Duplicate guardian mobile → Guardian creation rejected; staff must link the existing guardian record

**Notifications:**
| Step | Recipient | Channel | Message |
|---|---|---|---|
| Step 1 | Student | Email | Welcome email with login credentials |

---

### Workflow 2: Academic Enrollment Current-Session Transition
**Trigger:** Admin assigns a new current session to a student
**End States:** New enrollment is Current; previous enrollment is Historical

**Steps:**
1. Staff opens Student Edit → Session tab → Add Enrollment (or sets existing as Current)
2. System checks for existing current enrollment
3. Within a single database transaction: previous enrollment Current flag cleared → new enrollment Current flag set
4. System validates no duplicate academic year

**Exception:** Transaction failure → full rollback; student retains original current enrollment; staff sees error message

---

### Workflow 3: Parent Portal Access Granting
**Trigger:** Staff triggers "Grant Portal Access" for a guardian
**End States:** Guardian has system login; Can Access Parent Portal = Yes

**Steps:**
1. Staff selects guardian → Clicks "Grant Portal Access"
2. System creates system account with "Parent" role (or links existing account if guardian already registered)
3. System links System Account to guardian record; sets Can Access Parent Portal = Yes
4. System dispatches credentials email to guardian's email address

**Exception:** Guardian already has a system account → System links existing account; no duplicate created

**Notifications:**
| Step | Recipient | Channel | Message |
|---|---|---|---|
| Step 4 | Guardian | Email | Parent portal login credentials |

---

### Workflow 4: Attendance Correction
**Trigger:** Student or Parent submits a correction request (from Student or Parent Portal)
**End States:** Attendance Corrected (approved) / Unchanged (rejected)
**Actors:** Student/Parent | Class Teacher | School Admin | System

**Steps:**
1. Student/Parent submits correction request (original record + requested status + reason) → Status: Pending
2. Class Teacher reviews → Approves or Rejects (Step 1 approval) → records remarks and timestamp
3. School Admin reviews → Gives final approval or rejection → records remarks and timestamp
4. On final approval → System updates attendance record to requested status

**Exception:** Teacher rejects (Step 2) → request closed; Admin step is skipped; attendance unchanged

**Notifications:**
| Step | Recipient | Channel | Message |
|---|---|---|---|
| Step 1 | Class Teacher | In-App | New attendance correction request |
| Step 3 | Student/Parent | In-App / Email | Correction approved / rejected |

---

### Workflow 5: Student Leave Application Lifecycle (8-State FSM)
**Trigger:** Student or Parent submits a leave application (via Student or Parent Portal)
**End States:** Approved (attendance auto-updated) / Rejected / Cancelled
**Actors:** Student/Parent | Class Teacher | System

**FSM Transitions:**
- Draft → Submitted (student submits)
- Submitted → Under Review (teacher opens)
- Under Review → Info Requested (teacher queries)
- Under Review → Doc Requested (teacher requests document)
- Info Requested → Submitted (student responds)
- Doc Requested → Submitted (student responds or uploads)
- Under Review → Approved (teacher approves)
- Under Review → Rejected (teacher rejects)
- Any open state (Draft / Submitted / Info Requested / Doc Requested) → Cancelled (student cancels)

**Steps:**
1. Student/Parent creates leave application → saves as Draft
2. Student formally submits → Status: Submitted → System routes to class teacher; logs status-change remark
3. Class Teacher opens application → Status: Under Review; system logs remark
4a. Teacher Approves → provides remarks → Status: Approved → System auto-creates Leave attendance records for each approved day → logs remark
4b. Teacher Rejects → provides reason → Status: Rejected → no attendance impact → logs remark
4c. Teacher Requests Info → writes query → Status: Info Requested → logs remark → student notified
4d. Teacher Requests Document → writes document request → Status: Doc Requested → logs remark → student notified
5. Student/Parent responds → Status: Submitted → originating request marked resolved → teacher re-enters Step 3
6. Student Cancels → Status: Cancelled → no attendance impact → logged

**Notifications:**
| Step | Recipient | Channel | Message |
|---|---|---|---|
| Step 2 | Class Teacher | In-App | New leave application submitted |
| Step 4c/4d | Student/Parent | In-App / Email | Teacher has requested information / document |
| Step 4a | Student/Parent | In-App / Email | Leave application approved |
| Step 4b | Student/Parent | In-App / Email | Leave application rejected |

---

### Workflow 6: Student Record Archive / Restore / Permanent Removal
**Trigger:** Admin initiates a delete, restore, or permanent remove action
**End States:** Archived / Active / Permanently removed

**Steps:**
1. Admin archives (soft delete) → Record hidden from main list; appears in Trash; all related data retained; action logged
2. Admin restores from Trash → Record returns to main list with full data intact; action logged
3. Admin permanently removes (force delete, only from Trash) → All related records cascade-deleted per database constraints; action logged

**Exception:** Force-delete on an active (non-archived) record → System rejects; staff must archive first
