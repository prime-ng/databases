## 1. Module Overview

### 1.1 Purpose
The System Configuration module is the platform control centre for Prime-AI. Running exclusively on the central (non-school) domain and accessible only to authorised platform staff, it provides the tools to govern how the entire platform behaves: what settings are active, what navigation structure every school sees, what pick-list options appear in school forms, and how the platform's audit trail is reviewed. Every change made here propagates across all schools on the platform.

### 1.2 Business Value
- A single place for platform administrators to manage all cross-cutting configuration without a code deployment.
- A menu management system that allows the platform team to update school navigation structure at any time.
- A dropdown management system that lets platform administrators (and, where permitted, school administrators) extend pick-list options for any module form field without a schema change.
- A complete, append-only audit trail of every platform-level configuration change for compliance and incident investigation.
- A backup management system to protect platform data with scheduled and on-demand runs.

### 1.3 Scope

**In Scope:**
- Platform-level settings management (communication credentials, authentication rules, feature flags)
- Navigation menu hierarchy management, soft delete, restore, drag-and-drop reorder
- Menu translation management (per-language labels)
- Dropdown needs registry (which form fields across the platform require configurable pick-lists)
- Dropdown value management (the actual pick-list options)
- Platform audit log viewer
- Menu synchronisation from code definitions to the database
- Platform backup scheduling and execution
- Location reference data management (country, state, city, district)
- Platform media asset viewer

**Out of Scope:**
- Tenant-specific module configuration (within each school's own settings)
- User account and role CRUD management (Prime module's responsibility)
- Email/SMS delivery infrastructure (SystemConfig stores credentials only; Notification module dispatches)
- Database migration and tenant database provisioning
- System health dashboards and uptime monitoring (future enhancement)
- Backup file restore operation (future enhancement — currently download only)

### 1.4 Terminology (≥5 Required)

| Business Term | Meaning |
|---------------|---------|
| Platform Setting | A named key-value pair that controls a platform-wide behaviour (e.g., SMTP server address, minimum password length). The key is a system code contract — never editable after creation. |
| Navigation Menu | A single entry in the application sidebar tree — either a category heading (groups items, not a link) or a direct link to a screen |
| Menu Sync | A Super-Admin-only operation that reads canonical menu definitions from application code and overwrites the database records, ensuring every school's sidebar matches the current intended navigation structure |
| Dropdown Need | A registered declaration that a specific form field on a specific screen requires a configurable pick-list; it records the database table, column, and menu context for that field |
| Dropdown Value | A single option within a pick-list (e.g., "A+" is one Dropdown Value under the blood-group Dropdown Need) |
| Group Key | The auto-derived identifier for a family of Dropdown Values; always in the format `tablename.columnname` — derived server-side, never user-entered |
| Activity Log | An append-only record of every configuration change, capturing who, what, when, and before-and-after values; sensitive values are never stored in plain text |
| Backup Run | A single execution of the platform backup operation; tracked through Queued → Running → Completed / Failed states with file size and duration |
| Backup Schedule | A recurring trigger definition that automatically initiates backup runs at a configured frequency |
| Sensitive Setting | A Platform Setting whose key contains "password", "api_key", "secret", or "token" — its value is masked in list views and excluded from audit log entries |
| Super Admin | The single designated platform owner; protected by a database trigger that prevents creating a second Super Admin or demoting the existing one |
| Platform Manager | A central platform staff member with broad management permissions (menus, translations, dropdowns) but no platform settings write access |
| Location Reference Data | The platform-wide tables of countries, states, cities, and districts used across school registration and student profile forms |

### REQ-SYS-001 — Platform Settings Management
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]

**Description:** Platform Administrators maintain a set of named key-value configuration entries that control platform-wide behaviour. Settings are grouped by category (Communication, Authentication, Platform, Features). Sensitive values are masked in all list views. The setting key is a code contract and cannot be changed after creation.

**Actors:**
- Initiates: Super Admin (create, edit, delete)
- Views: Super Admin, Platform Manager, Platform Support

**Business Rules:** BR-SYS-001 (key immutable), BR-SYS-005 (sensitive masking in list), BR-SYS-006 (sensitive values excluded from audit), BR-SYS-012 (all mutations logged)

**Acceptance Criteria:**
1. The settings list groups records by category and masks values for sensitive keys (replaces value with bullet characters in all list views and API responses).
2. The edit form presents a type-appropriate input: toggle switch for Yes/No, numeric field for Number, date picker for Date, structured code editor for JSON, password-type field for sensitive keys.
3. Saving a setting records only the updated value and public-flag; the key field is stripped from the update payload even if submitted.
4. After a successful update, an audit log entry is written with before-and-after values; for sensitive keys, the log records "value updated" rather than the actual value.
5. A user without the Settings Edit permission cannot access the edit form (403 response).
6. A Super Admin can create a new setting specifying a unique snake_case key, description, data type, initial value, and public flag; duplicate keys are rejected.

**Integration:** Notification module reads SMTP/SMS credentials; Auth system reads password-policy and MFA settings.

**Enhancement Notes:** ENH-SYS-001 (send test email/SMS from settings UI to verify credentials).

### REQ-SYS-002 — Navigation Menu Management
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]

**Description:** Platform Administrators maintain the application's navigation hierarchy — a tree of category headings and direct-link menu items stored centrally and rendered as the sidebar in every school application. Full lifecycle is supported: create, view, edit, drag-and-drop reorder, toggle status, soft delete, restore, and permanent removal. The system identifier (code) is immutable after creation.

**Actors:**
- Initiates: Super Admin (all operations), Platform Manager (create, edit, soft delete, toggle, reorder)

**Business Rules:** BR-SYS-002 (code immutable), BR-SYS-003 (category must be root), BR-SYS-004 (sibling renumbering on reorder), BR-SYS-012 (all mutations logged)

**Acceptance Criteria:**
1. The menu tree renders all items hierarchically with icon, translated title (falls back to the original title if no translation exists), route, sort position, status, and category/link badge.
2. Creating a menu item requires: a unique system identifier (accepted only at creation), title, icon, sort position, and route (bypassed for category headings with no parent item).
3. A category heading item must have no parent; the system rejects any attempt to assign a parent to a category heading at create, edit, or reorder time (HTTP 422 with descriptive error).
4. Dragging an item to a new position triggers automatic sequential renumbering of all siblings, closing gaps in sort order.
5. Soft-deleting an item with active children is rejected; the system shows how many active children prevent the deletion.
6. Restoring a soft-deleted item returns it to the active listing; the trashed items list shows all soft-deleted items.
7. Permanently removing an item requires Super Admin permission and produces an irreversible hard delete from the database.
8. Toggling an item's active status returns an immediate response without a full page reload.
9. Any platform user without the required Menu permission receives a 403 response.

**Integration:** All school applications read this hierarchy to render their sidebars; Menu Sync (REQ-SYS-007) keeps this data aligned with code definitions.

### REQ-SYS-003 — Menu Translation Management
**Priority:** Standard (P1) | **Tags:** [DATA_ENTRY][CONFIGURATION]

**Description:** Each Navigation Menu item can carry a translated title for any available language. Platform Administrators create and update these translations so school applications render navigation in the school's configured language. Language selection is dynamic — sourced from the platform's available languages list, not hardcoded.

**Actors:**
- Initiates: Super Admin, Platform Manager

**Business Rules:** BR-SYS-017 (upsert — no duplicate per menu item + language), BR-SYS-012 (mutations logged)

**Acceptance Criteria:**
1. The menu edit form shows existing translations grouped by language and allows adding or updating a translation for any available language.
2. Saving a translation uses upsert logic — updates the existing record if one exists for that menu item + language combination, or creates a new record if not.
3. No two translation records for the same menu item can share the same language.
4. When the sidebar is rendered and no translation exists for the active language, the menu item's default title is used as fallback.
5. The language list is drawn from the platform's registered available languages, not hardcoded.

### REQ-SYS-004 — Dropdown Needs Registry
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]

**Description:** The Dropdown Needs Registry is a master catalogue declaring which form fields across the platform require configurable pick-lists. Each entry identifies the database tier, table, and column for a field, maps it to its menu navigation context, and records whether school administrators may extend it with their own values. This registry is the prerequisite for all Dropdown Value creation.

**Actors:**
- Initiates: Super Admin (full lifecycle)
- Views: Super Admin, Platform Manager

**Business Rules:** BR-SYS-014 (unique table + column combination), BR-SYS-015 (system-protected entries locked), BR-SYS-012 (mutations logged)

**Acceptance Criteria:**
1. The registry list shows all entries with: database tier, table name, column name, menu navigation path, whether schools may add values, and active status.
2. The list can be filtered by database tier and by whether tenant schools are permitted to create values.
3. Creating a need requires: database tier, table name, column name, and at least a field label; the combination of table + column must be unique in the registry (duplicates rejected).
4. System-protected entries cannot be edited or deleted; any attempt returns a descriptive error.
5. Soft-deleting a need is blocked if active dropdown values are mapped to it; the system shows the count of affected values.
6. A user without the Dropdown Management permission receives a 403 response.

### REQ-SYS-005 — Dropdown Value Management
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]

**Description:** Dropdown Values are the actual pick-list options that appear in school forms. They are grouped under an auto-derived key (tablename.columnname) and linked to a Dropdown Need. Platform Administrators can manage the full lifecycle. School Administrators may create values only for Needs where the "school may add values" flag is enabled.

**Actors:**
- Initiates (platform path): Super Admin, Platform Manager
- Initiates (school path): School Administrator (where permitted by the Dropdown Need)

**Business Rules:** BR-SYS-007 (need required before value), BR-SYS-008 (group key derived server-side), BR-SYS-009 (ordinal auto-assign + uniqueness), BR-SYS-016 (delete blocked if referenced), BR-SYS-019 (school path: key read-only, no need creation), BR-SYS-012 (mutations logged)

**Acceptance Criteria:**
1. The values list groups entries by their derived key in accordion panels showing: display order, value text, data type, and status.
2. Creating a value requires the administrator to locate the relevant Dropdown Need first — via either a DB-field selector (database tier → table → column; platform users only) or a menu-navigation selector (category → main menu → sub menu → tab → field; both platform and school users).
3. The group key is derived server-side from the matched Dropdown Need and is never accepted from the request body.
4. The system auto-assigns the next available display order number within the key group; two values in the same key cannot share an ordinal.
5. Two values within the same key cannot have identical display text; duplicates are rejected.
6. Deactivating a value immediately hides it from school forms. Permanent deletion is blocked if any school's data references the value; the system shows a reference count.
7. After creating a value, the junction record linking it to its Dropdown Need is created automatically, and the Dropdown Need's "has values" indicator is set to true.
8. On the school-administrator path, only Needs with the school-editable flag enabled are accessible; the group key is read-only.

### REQ-SYS-006 — Activity Log Viewer
**Priority:** Standard (P1) | **Tags:** [REPORT][DASHBOARD]

**Description:** The Activity Log Viewer is a read-only, paginated screen for reviewing every configuration change made within the System Configuration module. Log entries are append-only; no actor can edit or delete them.

**Actors:**
- Views: Super Admin, Platform Support

**Business Rules:** BR-SYS-006 (sensitive values excluded from log detail), BR-SYS-012 (all mutations produce log entries)

**Acceptance Criteria:**
1. The log list shows: entity type, entity identifier, acting platform user, event type, and timestamp; ordered newest-first with 50 entries per page.
2. The list is filterable by entity type, event type, platform user, and date range.
3. Clicking a log entry expands a detail panel showing the structured before-and-after change record.
4. Detail panels never display raw sensitive values (API keys, passwords); instead they show "value updated (hidden for security)."
5. No create, edit, or delete controls appear anywhere on this screen.
6. Platform Manager cannot access the Activity Log Viewer; only Super Admin and Platform Support can.

### REQ-SYS-007 — Menu Synchronisation
**Priority:** Core (P0) | **Tags:** [WORKFLOW][CONFIGURATION]

**Description:** Menu Sync is a deliberate, Super-Admin-only operation that reads the canonical navigation menu definitions from application code and writes them to the database, ensuring every school's sidebar reflects the current intended structure. It is irreversible and must never proceed without an explicit Super Admin permission check.

**Actors:**
- Initiates: Super Admin exclusively

**Business Rules:** BR-SYS-011 (Super Admin only, check must never be commented out or bypassed), BR-SYS-012 (sync event logged)

**Acceptance Criteria:**
1. The Sync button is visible and executable only by a Super Admin; any other actor receives a 403 response.
2. Before proceeding, the system shows a confirmation prompt: "This will overwrite all school menus — are you sure?"
3. The sync removes retired/renamed menu codes, creates entries for new codes, and updates existing entries in place.
4. On completion, a summary is shown: items created, updated, removed, and unchanged.
5. The sync writes a single audit log entry with the acting Super Admin's identity, timestamp, and summary counts.
6. If the sync fails partway through, the system logs the failure event and presents a descriptive error message without leaving the database in an inconsistent state.

**Enhancement Notes:** ENH-SYS-005 (menu preview before sync).

### REQ-SYS-008 — Platform Backup Management
**Priority:** Standard (P1) | **Tags:** [WORKFLOW][SCHEDULED]

**Description:** Super Admins can trigger manual database backups and define recurring backup schedules. Each run executes asynchronously as a queued background job; the backup history list shows live status updates. Completed backups can be downloaded or removed. Notifications are sent on completion and failure.

**Actors:**
- Initiates: Super Admin exclusively

**Business Rules:** BR-SYS-020 (runs are queued, async, with notifications), BR-SYS-012 (mutations logged)

**Acceptance Criteria:**
1. The manual backup form lets the Super Admin select database connections and tenant school databases to include.
2. Submitting queues a background job; the system creates a Backup Run record in "Queued" state and redirects to the backup history list with a confirmation message.
3. The history list shows status updates on active runs (Queued / Running / Completed / Failed) without requiring a full page reload; file size and duration appear when the run completes.
4. A completed run can be downloaded as a file from the history list.
5. A run record and its associated file can be deleted by the Super Admin.
6. The backup schedule form accepts frequency, retention period, and backup type; saving creates or updates the schedule without triggering an immediate run.
7. On run completion the system sends a success notification; on failure a failure notification with an error description.
8. A non-Super-Admin platform user receives a 403 response on any backup management route.

**Enhancement Notes:** ENH-SYS-003 (backup restore operation from a downloaded file).

### 5.2 Multi-Tenancy Scope Note
All System Configuration data lives in the central databases: Platform Settings, Dropdown Needs, Dropdown Values, Backup Runs, and Backup Schedules in the platform database; Navigation Menus and Translations in the global database. No System Configuration table exists in school databases. The central domain boundary means no school user can reach any of these records. The `sys_dropdowns` table also exists in each school database — it is populated from the central registry as a copy for the school's runtime use.

## 6. Workflows

### Workflow 1: Platform Setting Update
**Trigger:** Super Admin clicks "Edit" on a Platform Setting
**End States:** Setting updated + audit log written; or validation failed (no change)
**Actors / Swimlanes:** Super Admin | System

1. [Super Admin] Clicks "Edit" on the desired setting.
   → [System] Checks `system-config.settings.update` permission; renders edit form with current value pre-populated; key field is read-only.
2. [Super Admin] Changes the value using the type-appropriate input; submits.
   → [System] Validates: value matches declared data type. If invalid, returns form with error messages (no save).
3. [System] Strips the key field from the update payload. Saves the new value.
4. [System] Writes audit log entry. If key is sensitive, records "value updated" without the raw value.
5. [System] Redirects to settings list with success flash.

**Exception Paths:**
- Value does not match the declared data type → step 2 returns validation errors; no write occurs.
- User lacks the permission → step 1 returns 403; no form is rendered.

**Notifications Triggered:** None (audit log is the record).

---

### Workflow 2: Menu Synchronisation
**Trigger:** Super Admin clicks "Sync Menus"
**End States:** Database menus match code definitions + audit log written; or confirmation declined (no change); or sync failed (error shown, DB not left in partial state)
**Actors / Swimlanes:** Super Admin | System

1. [Super Admin] Clicks "Sync Menus."
   → [System] Checks `system-config.menu.sync` — Super Admin only. Any other actor receives 403.
2. [System] Presents confirmation prompt.
3. [Super Admin] Confirms.
   → [System] Temporarily suspends foreign-key constraint checking.
4. [System] Removes menu entries for retired/renamed codes; creates entries for new codes; updates changed entries.
5. [System] Re-enables foreign-key constraint checking.
6. [System] Writes single audit entry with Super Admin identity + summary counts (created, updated, removed, unchanged).
7. [System] Redirects to menu tree with success message and summary.

**Exception Paths:**
- Database error mid-sync → System logs failure, ensures FK checks are re-enabled regardless, shows descriptive error. Database is not left in a partially-synced inconsistent state.

**Notifications Triggered:** None.

---

### Workflow 3: Dropdown Value Creation (Platform Path)
**Trigger:** Platform Administrator starts "Add Dropdown Value"
**End States:** Dropdown Value created + linked to Need + ordinal assigned + Need's "has values" flag set + audit log written; or validation failed
**Actors / Swimlanes:** Super Admin / Platform Manager | System

Two entry sub-paths (both converge to the common save step):

**Sub-path A (DB-field path — platform users only):**
1a. [Admin] Selects database tier → table name → column name (cascading selectors drawn from the Dropdown Needs registry).
   → [System] Looks up matching Dropdown Need and pre-fills context; shows error if no Need is found.

**Sub-path B (Menu-navigation path — platform and school users where permitted):**
1b. [Admin] Selects menu category → main menu → sub menu → tab → field name (cascading selectors).
   → [System] Looks up matching Dropdown Need; shows error if not found.

**Common save steps:**
2. [Admin] Enters display text and data type; submits.
3. [System] Validates: display text non-empty; data type valid; display text unique within key group.
4. [System] Derives group key from the Dropdown Need (not from the request body).
5. [System] Auto-assigns next display order number (MAX+1 within key group).
6. [System] Saves the Dropdown Value; creates junction record linking it to the Need; updates Need's "has values" flag.
7. [System] Writes audit log entry.
8. [System] Redirects to values list with success flash.

**Exception Paths:**
- No Dropdown Need found for the selected field → error shown at step 1; no value is created.
- Duplicate display text within key group → step 3 returns validation error; no save.

---

### Workflow 4: Backup Execution
**Trigger:** Super Admin submits "Run Backup" form
**End States:** Backup file stored + status shown as Completed + success notification sent; or job failed + failure notification sent
**Actors / Swimlanes:** Super Admin | System | Background Job

1. [Super Admin] Selects connections/tenant schools; submits form.
   → [System] Validates selections; dispatches background job; creates Backup Run record (status: Queued); redirects to backup history with "queued" confirmation.
2. [Background Job] Picks up the job from the queue; updates Backup Run status to Running.
3. [Background Job] Completes the backup; stores the file; updates status to Completed with file size and completion time.
4. [System] Sends success notification to Super Admin.

**Exception Paths:**
- Background job fails → updates Backup Run status to Failed; sends failure notification to Super Admin with error description.
- Super Admin navigates away before completion → backup still runs in background; status visible on next visit to backup history list.

## 9. Non-Functional Requirements

### 9.1 Performance

| Operation | Target Response Time | Notes |
|-----------|---------------------|-------|
| Platform Settings list | < 200 ms | Small dataset, simple query |
| Navigation Menu tree | < 500 ms | Up to 100 items with eager-loaded children and translations |
| Menu drag-drop reorder | < 300 ms | O(n) sibling renumbering, manageable at 100 items |
| Menu Sync | < 30 s | Execution time limit set in existing code |
| Dropdown Values list | < 300 ms | Grouped, paginated, 20 per page |
| Activity Log list | < 500 ms | Indexed on timestamp and user; 50 rows per page |
| Backup status poll | < 200 ms | Lightweight JSON endpoint querying only active runs |

### 9.2 Security

- All System Configuration routes are accessible only from the central/platform domain; requests from school subdomains must be rejected before reaching any controller.
- Every controller method calls an explicit permission check before executing any logic; route-level authentication middleware is necessary but not sufficient.
- Settings with the confidential flag are excluded from all API responses and non-admin page renders in every context.
- The Menu Sync endpoint performs a destructive operation and requires the Super Admin role — not just authentication.
- All form submissions are CSRF-protected (standard for web routes).
- All controller mutations use only validated request data; raw request data (`$request->all()`) must never be passed to data model update methods.
- The single-Super-Admin constraint is enforced at the database level; no application workaround may bypass it.
- The module's Route Service Provider must use only `['web', 'auth', 'verified']` middleware — never the tenant middleware stack (`InitializeTenancyByDomain`, `PreventAccessFromCentralDomains`, `EnsureTenantIsActive`), which would block the central domain.

### 9.3 Usability

- The settings list renders type-appropriate inline edit inputs (toggle for Yes/No, code editor for JSON, date picker for dates) without a separate edit page where practical.
- The menu tree supports drag-and-drop reordering with visible feedback during the drag; toggle controls have ARIA labels.
- The dropdown creation form uses cascading AJAX selectors that progressively narrow context (category → main menu → sub menu → field).
- Error messages identify the specific field that failed validation and are linked to their input via `aria-describedby`.
- The backup history list refreshes active-run statuses without a full page reload.
