## Section 1 — Module Overview

### 1.1 Purpose

The SmartTimetable module is the AI-assisted, constraint-based scheduling engine for Prime-AI academic platform. It automates the complete timetable lifecycle for Indian K-12 schools — from structural configuration and activity preparation, through algorithm-driven generation with hard and soft constraint enforcement, to manual refinement, approval, publishing, and daily substitution management. It eliminates the 2–4 weeks of manual timetable preparation that schools traditionally spend at the start of each academic term.

### 1.2 Business Value

- Reduces timetable preparation effort from weeks to hours for a typical school with 40–80 staff and 30–100 class sections.
- Enforces 24 hard scheduling constraints automatically, preventing teacher double-booking, room conflicts, and statutory violations.
- Scores soft preferences (teacher workload balance, subject spread, room utilisation) for continuous quality optimisation.
- Provides real-time substitution recommendations when a teacher is absent, drawing on historical pattern data.
- Exposes a REST API so that teacher and student portals, parent apps, and mobile interfaces can consume the published timetable without additional development.

### 1.3 Scope

**In Scope:**
- Timetable configuration, master data, and requirement definition (supported by TimetableFoundation module prerequisites).
- Automated constraint-based timetable generation using FET-inspired CSP backtracking with optional Tabu Search or Simulated Annealing post-optimisation.
- Manual refinement: cell swapping, moving, locking, and batch operations.
- Approval and publishing workflow (DRAFT → GENERATING → GENERATED → APPROVED → PUBLISHED → ARCHIVED).
- Post-generation analytics: teacher workload, room utilisation, constraint violation reporting.
- Daily substitution management: absence recording, candidate scoring, assignment, and completion tracking.
- REST API (16 endpoints, Sanctum-authenticated) for external consumers.
- Class-wise, teacher-wise, and room-wise published timetable views.

**Out of Scope:**
- Manual drag-and-drop timetable builder (that is StandardTimetable module — a separate, planned module).
- Student attendance tracking (Attendance module).
- Exam scheduling and seating arrangements (LmsExam / Examination modules).
- HR leave management integration beyond teacher unavailability flags (HrStaff module).
- Parent notifications for timetable changes beyond substitution alerts (EventEngine module).
- Per-student individual scheduling (not applicable in K-12 group timetabling).

### 1.4 Terminology

| Term | Business Definition |
|------|---------------------|
| Activity | The core scheduling unit: one combination of Class + Section + Subject + Study Format (e.g., "Class 10A — Science — Lecture") that requires N periods per week. |
| Constraint | A rule the timetable must respect. Hard constraints are absolute (no teacher double-booking); soft constraints are preferences scored but not blocking (distribute Maths evenly across the week). |
| Period Set | A template defining which time slots from the school's master period grid a class group attends (e.g., Toddler classes use Slots 3–8; senior classes use all 12 slots). |
| Parallel Group | A set of activities across different sections that must run at exactly the same time slot (e.g., all sections attending elective subjects simultaneously). |
| Generation Run | A single execution of the solver for a timetable. Multiple runs are permitted; each is tracked independently. |
| Soft Score | A numeric quality measure (lower is better) computed as the weighted sum of all soft constraint violations in a generated timetable. |
| Substitution Pattern | A historical record of a teacher's success rate for substituting a particular subject on a particular day, used to rank substitution candidates. |
| Academic Term | A sub-division of the academic year (e.g., Term 1, Quarter 2) for which a timetable is generated. Each timetable is term-scoped. |
| Timetable Cell | A single grid intersection: (Timetable, Day of Week, Period Order, Class Group). Stores the assigned activity, room, and teacher(s). |
| Requirement Consolidation | The master record that captures all scheduling parameters for one Class + Section + Subject + Study Format combination within a term: required weekly periods, minimum/maximum per day, consecutive rules, room type requirement, and spread preference. |

## Section 3 — Functional Requirements

### REQ-STT-001: Foundation Masters Setup
**Priority:** Core (P0) | **Tags:** [CONFIGURATION] [DATA_ENTRY]
**Current Status:** ✅ Implemented (in TimetableFoundation module)

**Description:** Before any timetable can be generated, the school must define its physical scheduling structure. This covers school shifts, day type classifications, period type definitions, teacher assignment roles, school calendar (open days), working day calendar (date-level), centralized period timeslot grid, period sets, and timetable type configurations. These are prerequisite data that the SmartTimetable engine reads at generation time.

**Actors:** Timetable Coordinator initiates and maintains. System enforces prerequisites at generation time.

**Business Rules Applied:** BR-STT-001, BR-STT-002, BR-STT-003, BR-STT-004

**Acceptance Criteria:**
1. YES/NO: Can a Coordinator create a Shift with code, name, start time, end time, and ordinal, and the Shift appears in the generation prerequisites check?
2. YES/NO: Does the system prevent two Timetable Types with overlapping effective date ranges for the same shift?
3. YES/NO: Does the Period Timeslot Master (one fixed grid per shift) drive all period timing, so that period 3 is always 09:30–10:15 for all class groups on that shift?
4. YES/NO: Does the system block timetable generation if prerequisite masters are incomplete (fewer than 1 shift, fewer than 5 school days, or no period set)?
5. YES/NO: Can a Coordinator soft-delete any foundation master, and the deleted record no longer appears in generation prerequisites?

**Integration:** Reads from SchoolSetup (buildings, room types, rooms). Shared `sch_academic_term` managed by SchoolSetup but displayed/edited within timetable configuration.

**Enhancement Notes:** None at V1.0 — foundation masters are fully specified.

4. YES/NO: Does a slot budget recalculate automatically when the academic term changes?
5. YES/NO: Does the system prevent generating a timetable if no Requirement Consolidation records exist for the target term?

### REQ-STT-009: Automated Timetable Generation (Constraint Solver)
**Priority:** Core (P0) | **Tags:** [WORKFLOW] [SCHEDULED]
**Current Status:** 🟡 Partial (~55%) — solver runs but DB constraints not wired (BUG-STT-05)

**Description:** Triggers the AI-assisted generation pipeline as an asynchronous background job. The pipeline executes ten steps: pre-validation, activity scoring (difficulty-first ordering), room pre-allocation, sub-activity decomposition, CSP backtracking solver (up to 50,000 iterations, configurable timeout), post-solver optimisation (Tabu Search or Simulated Annealing), solution evaluation (hard violations + soft score), atomic DB storage of all cells, resource booking creation, and conflict detection. The timetable status progresses to Generating while the job runs, then to Generated (success) or reverts to Draft (failure). The web request thread is never blocked.

**Actors:** Timetable Coordinator triggers generation. System Queue Worker executes.

**Business Rules Applied:** BR-STT-006, BR-STT-007, BR-STT-008, BR-STT-009, BR-STT-017, BR-STT-018, BR-STT-019

**Acceptance Criteria:**
1. YES/NO: Does triggering generation dispatch an asynchronous queue job, returning control to the browser immediately?
2. YES/NO: Does the generation job score and sort activities before placement, placing the hardest-to-schedule activities (fewest eligible teachers) first?
3. YES/NO: Does a hard constraint violation (e.g., teacher double-booking) cause the placement to be retried rather than accepted?
4. YES/NO: If no valid placement exists for an activity after the iteration limit is reached, is the job marked as Failed with a descriptive error, and the timetable status reverted to Draft?
5. YES/NO: Is the complete set of timetable cells stored in a single database transaction, so partial results never appear?
6. YES/NO: Does the system record the number of activities placed, the number failed, hard violations, soft violations, and the soft score for each generation run?
7. YES/NO: Can the Coordinator run generation multiple times on the same timetable (each attempt creates a new generation run record)?

**Gap Note (BUG-STT-05):** Until PrimeConstraintBridge is fixed, the solver enforces only its hardcoded inline checks, not the constraint instances the Coordinator has created in the Constraint Engine. This means the current generation output cannot be considered fully constraint-compliant.

### REQ-STT-015: Substitution Management
**Priority:** Core (P0) | **Tags:** [WORKFLOW] [NOTIFICATION]
**Current Status:** 🟡 Partial (~65%) — core flow implemented; FormRequests missing; no auth; notification unconfirmed

**Description:** Manages the daily process of handling teacher absences. A Coordinator records an absence (with type: Leave / Sick / Training / Official Duty / Other) and period range. When the substitution is completed, the pattern record for that teacher-day-subject combination is updated via a running exponential average.

**Actors:** Coordinator records and approves absences and assigns substitutes. Teacher receives notification. System scores candidates.

**Business Rules Applied:** BR-STT-024, BR-STT-025, BR-STT-026

**Acceptance Criteria:**

2. YES/NO: Does approving an absence trigger automatic generation of ranked substitute candidates for each affected timetable cell?
3. YES/NO: Does the candidate ranking score reflect subject match (40 pts), historical pattern (25 pts), availability (20 pts), and workload balance (15 pts)?
4. YES/NO: Does assigning a substitute insert a new teacher record on the timetable cell with the "Is Substitute" flag, without removing the original teacher record?
5. YES/NO: Does completing a substitution update the historical pattern record for that teacher-day-subject via a running exponential average?

## Section 6 — Workflows

### Workflow 1: Complete Timetable Generation Lifecycle

**Trigger:** Coordinator creates a Timetable record (status: Draft)
**End States:** Published (success path), Draft (failure path), Archived (superseded by new version)
**Actors / Swimlanes:** Timetable Coordinator | System (Queue) | Principal

**Steps:**
1. [Coordinator] Creates Timetable record → status = Draft
2. [Coordinator] Runs pre-generation validation → System returns tabbed validation report
3. Decision: validation result → FAIL: show errors, block generation; PASS: enable generation
4. [Coordinator] Triggers generation → System dispatches GenerateTimetableJob → status = Generating
5. [System Queue] Executes 10-step pipeline (score activities → pre-allocate rooms → decompose sub-activities → PrimeSolver CSP backtracking → post-optimisation → evaluate solution → atomic store → book resources → detect conflicts → update run record)
6. Decision: job outcome → COMPLETED: status = Generated; FAILED: status reverts to Draft, error recorded
7. [Coordinator] Opens Preview screen → reviews grid, analytics, conflict summary
8. [Coordinator] Submits for approval → [Principal] Reviews; Decision: APPROVE (status = Approved) or REJECT (status = Draft + reason)
9. [Coordinator] Publishes approved timetable → status = Published; published_at + published_by recorded; previous Published → Archived
10. [Teachers/Parents/Students] Access published timetable via standard views or REST API

**Exception Paths:**
- Solver timeout (25s per run, 600s job): run status = Failed; timetable → Draft; error_message stored
- Database transaction failure during storage: full rollback; run → Failed
- All activities placed but hard violations remain: partial result stored with violations flagged; coordinator warned on approval

**Notifications Triggered:**
| Step | Recipient | Channel | Message |
|------|-----------|---------|---------|
| Generation completed | Coordinator | In-app / Email | "Timetable [Name] generation completed successfully. [N] activities placed." |
| Generation failed | Coordinator | In-app / Email | "Timetable [Name] generation failed: [error message]" |
| Timetable published | All teachers | In-app / SMS | "The [Term] timetable has been published. View your schedule in the portal." |

---

### Workflow 2: Manual Refinement Workflow

**Trigger:** Coordinator opens the Refinement grid for a Generated or Approved timetable
**End State:** Timetable cells updated; change log entries created
**Actors:** Timetable Coordinator | System

**Steps:**
1. [Coordinator] Opens Refinement grid → System loads paginated cells (max 100 per page) scoped to selected timetable
2. [Coordinator] Clicks source cell → UI highlights it and prompts for target selection
3. [Coordinator] Clicks target cell → System runs pre-swap impact analysis (async fetch to impact endpoint)
4. [Coordinator] Views impact modal (constraint violations, score delta) → Decision: CONFIRM or CANCEL
5. If CONFIRM: [System] swaps activity + room in transaction → updates both cells → records change log (type = SWAP)
6. [System] runs conflict detection on affected cells → updates timetable conflict summary
7. [Coordinator] May lock a cell (preventing future changes) or unlock a previously locked cell

**Exception Paths:**
- Target cell is locked: swap rejected with error "Target cell is locked"
- Swap would create hard constraint violation: modal warns; coordinator may override for soft violations; hard violations may be blocked depending on timetable status
- Batch swap partial failure: rollbackBatch() restores all cells; change log records rollback type

---

### Workflow 3: Substitution Workflow

**Trigger:** Teacher absent; Coordinator records absence
**End State:** Substitute assigned, notified, and substitution completed; pattern updated
**Actors:** Timetable Coordinator | Substitute Teacher | System

**Steps:**
1. [Coordinator] Records Teacher Absence (type, date, period range) → status = Pending
2. [Coordinator] Approves absence → System generates substitute recommendations for each affected timetable cell
3. [System] Scores all eligible substitute candidates (subject match 40 pts + pattern 25 pts + availability 20 pts + workload 15 pts)
4. [Coordinator] Views ranked candidate list for each affected cell → selects manually (POST /assign) or auto-assigns top candidate (POST /auto-assign)
5. [System] Creates cell-teacher record with is_substitute = true; creates substitution log (status = Assigned); sends notification to substitute teacher
6. [Substitute Teacher] Teaches the class
7. [Coordinator] Marks substitution as completed → System updates substitution log (status = Completed); updates historical pattern record for teacher-day-subject via running exponential average

**Exception Paths:**
- No eligible substitute found: system alerts Coordinator; absence remains unresolved; manual escalation required
- Substitute refuses assignment: Coordinator re-runs candidate selection and chooses another

**Notifications Triggered:**
| Step | Recipient | Channel | Message |
|------|-----------|---------|---------|
| Substitute assigned | Substitute Teacher | In-app / SMS | "You have been assigned to substitute for [Period] on [Date] — [Subject] for [Class Section]." |
