## Section 1 — Module Overview

### 1.1 Purpose

TimetableFoundation (TTF) is the mandatory **infrastructure and configuration layer** that every timetable in the Prime-AI platform depends on. Before any timetable — whether AI-generated by SmartTimetable or manually placed by StandardTimetable — can run, the school must complete a six-step setup workflow entirely within TTF. TTF owns all data that answers the scheduler's prerequisite questions:

| Scheduler Question | TTF's Answer |
|--------------------|--------------|
| What time does school happen? | School Shifts and Period Sets (ordered bell schedules) |
| What kind of day is it? | Day Types and the Working Day Calendar |
| What subjects need scheduling? | Requirement Consolidation records |
| Who is available when? | Teacher Availability matrices and Room Availability matrices |
| What algorithm should run? | Generation Strategy configuration |
| What are the rules? | Timetable Configuration key-value store and Constraint Type catalog |

TTF is organised into seven menu pages that a Timetable Manager works through sequentially, culminating in a complete set of Activities that SmartTimetable consumes to run its solver.

### 1.2 Business Value

- **Eliminates scheduling errors at the source.** By capturing all time, resource, and requirement data in structured, validated records before generation, TTF prevents the most common timetable failures — teacher double-booking, period-count mismatches, and unassigned subjects.
- **Enables multi-shift, multi-term schools.** TTF's Shift, Day Type, and Academic Term design accommodates schools with two or three shift operations and quarterly/semester/annual term structures without any customisation.
- **Provides a reusable configuration base.** Master data (shifts, period types, period sets, day types) is defined once and reused across academic years. Only the term-scoped data (activities, availability, consolidation) needs annual refresh.
- **Centralises the solver input contract.** SmartTimetable and StandardTimetable read a single, clean data layer — the `tt_*` tables owned by TTF — rather than querying SchoolSetup, StaffProfile, and Syllabus directly.

### 1.3 Scope

**In Scope**
- Seven menu pages: Pre-Requisites Setup, Timetable Configuration, Timetable Masters, Timetable Requirement, Resource Availability, Timetable Preparation, Reports and Logs
- All master-data management: Shifts, Day Types, Period Types, Period Sets, Period Slots, Timetable Types, School Days, Teacher Assignment Roles
- Calendar management: Working Day Calendar (school-wide and class-specific overrides)
- Requirement pipeline: Slot Requirements, Requirement Groups, Requirement Subgroups, Requirement Consolidation
- Resource availability: Teacher Availability (per-slot matrix), Room Availability (per-slot matrix), Availability Logs
- Activity management: Activity creation, batch generation, teacher assignment, sub-activity planning, activity priorities
- Configuration: Timetable Config key-value store, Generation Strategy master
- Timetable master record management (header records for SmartTimetable and StandardTimetable)
- Read-only display of SchoolSetup and StaffProfile data (Pre-Requisites Setup page)
- Reports reading SmartTimetable analytics output

**Out of Scope**
- Timetable generation, placement, and constraint satisfaction — owned by SmartTimetable
- Manual period-by-period timetable editing — owned by StandardTimetable
- Substitution management for absent teachers — owned by SmartTimetable's SubstitutionService
- Student-to-section assignments — owned by SchoolSetup and StudentProfile
- Leave and attendance records for teachers — owned by HrStaff and Attendance modules
- Cross-tenant timetable sharing or comparison

### 1.4 Terminology

| Term | Business Definition |
|------|---------------------|
| **Activity** | The central scheduling unit: one class-section-subject-teacher combination requiring a fixed number of periods per week that the scheduler must place into time slots. One Activity becomes one or more entries in the generated timetable grid. |
| **Academic Term** | A named time window within an academic session — examples: Quarter 1 (Apr–Jun), Semester 1 (Apr–Sep), Annual (Apr–Mar). All timetable data is scoped to an Academic Term. |
| **Constraint Type** | A named scheduling rule the solver must obey — for example, "A teacher cannot be in two classes at once" (hard) or "Maths should not be scheduled after 3 PM" (soft). The catalog is seeded by SmartTimetable. |
| **Day Type** | Classification assigned to a calendar date — STUDY, HOLIDAY, EXAM, SPECIAL, PTM Day, Sports Day, Annual Day. A date can carry up to four Day Types simultaneously. |
| **Generated Column** | A database field whose value is computed automatically by the database engine from other columns. The application must never attempt to write to these fields; examples are Period Duration and Teacher Full-Timetable Availability flag. |
| **Generation Strategy** | The algorithm configuration record that SmartTimetable reads to decide which solver algorithm to use (Recursive, Genetic, Simulated Annealing, Tabu Search, or Hybrid) and its parameters. |
| **Period Set** | A named daily schedule template — for example, "Standard 8-Period Day" listing eight ordered time slots with start times, end times, and period types (teaching, break, lunch). |
| **Period Slot** | A single entry within a Period Set: a specific time window (e.g., 08:00–08:45) of a defined Period Type. The duration in minutes is computed automatically. |
| **Period Type** | The nature of a period slot — Theory, Teaching, Practical, Break, Lunch, Assembly, Exam, Recess, or Free. Controls whether the solver places a subject in that slot. |
| **Pre-Requisites Setup** | Page 1 of TTF — a read-only dashboard that displays Buildings, Rooms, Teacher Profiles, Classes, Sections, Subjects, and Study Formats pulled from SchoolSetup and StaffProfile, confirming that the required data exists before TTF configuration begins. |
| **Requirement Consolidation** | The normalised, final requirement record for one class-section-subject-study-format combination — "Class 9A needs 5 periods of Mathematics Theory per week in Term 1." This is the exact record the solver reads as its line-item input. |
| **School Shift** | The time window in which a school (or a batch of students) operates: Morning, Toddler (nursery hours), Afternoon, Evening. A school with two batches has two shifts with different period sets. |
| **Slot Requirement** | A computed summary of how many teaching, exam, and free slots are available per class per timetable type per term — derived from Period Set and Class-Timetable-Type assignments. |
| **Timetable Manager** | The school staff member responsible for operating the six-step TTF setup workflow and coordinating with SmartTimetable for generation. Typically the Academic Coordinator or Vice-Principal. |
| **Timetable Type** | The scheduling mode for a given period of the school year — Standard (regular teaching day), Unit Test, Half-Day, Half-Yearly Exam, Final Exam. Each type links to a Shift and a Period Set. |
| **Working Day Calendar** | The date-by-date record of every calendar day in the academic session, tagged with its Day Types (Study, Holiday, Exam Day, etc.) and used to count total teaching, exam, and working days per term. |
| **Class-Timetable-Type** | The assignment that links a specific class (or all sections of a class) to a Timetable Type for a given Academic Term, defining which period set runs for that class. |
| **Teacher Assignment Role** | The role a teacher plays in a specific Activity: Primary Instructor, Assistant, Co-Teacher, Substitute, or Trainee. Each role has a workload factor that adjusts the teacher's effective load calculation. |

### REQ-TTF-008: Period Set Management [CONFIGURATION][DATA_ENTRY]
**Priority:** Core (P0) | **Actors Initiates:** Timetable Manager, School Admin

### REQ-TTF-016: Activity Management [DATA_ENTRY][WORKFLOW]
**Priority:** Core (P0) | **Actors Initiates:** Timetable Manager, Academic Coordinator; **Views:** Teacher (assigned activities only)

**Description:** Activities are the core scheduler input — one Activity = one subject taught to one class-section by one or more teachers, requiring a defined number of weekly periods. Activities can be created individually or batch-generated from Requirement Consolidation. Each Activity has an optional priority (Critical, High, Normal, Low) that influences the solver's placement order. Activities can be split into Sub-Activities for granular period-level planning (e.g., a 5-period Maths activity split into a 3-period lecture sub-activity and a 2-period lab sub-activity). Batch generation runs asynchronously with a progress-polling UI.

## Section 6 — Workflows

### Workflow 1: Six-Step Pre-Generation Setup
**Trigger:** A Timetable Manager begins annual timetable preparation for a new academic year or term.
**End States:** All six steps complete; Activities are in DRAFT status and ready for SmartTimetable to consume.
**Actors:** Timetable Manager | Academic Coordinator | SmartTimetable (consumer)

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Timetable Manager | Opens Pre-Requisites Setup (Page 1); verifies Buildings, Rooms, Classes, Subjects exist | Displays read-only dashboard; flags missing data with links to source modules |
| 2 | Timetable Manager | Opens Timetable Configuration (Page 2); sets Config values; creates Academic Term(s); selects Generation Strategy | Validates and saves; academic term date overlap is checked (gap: not yet enforced) |
| 3 | Timetable Manager | Opens Timetable Masters (Page 3); creates/verifies Shifts, Day Types, Period Types, Period Sets with slots, Timetable Types, assigns Classes to Timetable Types; initialises Working Day Calendar | Saves all master data; calendar bulk-created for session date range |
| 4 | Timetable Manager | Opens Timetable Requirement (Page 4); generates Slot Requirements; generates Requirement Consolidation | System reads class-subject mappings and creates consolidation records |
| 5 | Timetable Manager | Opens Resource Availability (Page 5); generates Teacher Availability; edits per-slot matrix; sets Room Availability | Default availability records created; changes logged |
| 6 | Timetable Manager | Opens Timetable Preparation (Page 6); generates Activities; assigns teachers to activities | Activity records created in DRAFT; SmartTimetable is now ready to generate |

**Exception Paths:**
- Step 1 incomplete: Missing rooms or subjects → Timetable Manager must complete SchoolSetup before proceeding to Step 2.
- Step 4 generates zero records: No class-subject mappings in SchoolSetup → return to SchoolSetup to configure subject allocations.
- Step 5 has teachers with no availability: Solver treats them as fully available (all slots). [Inferred]
- Step 6 batch generation times out (>50 classes): Progress polling shows stuck; Timetable Manager retries individual class generation. Rate limiting not yet applied (gap).

**Notifications Triggered:** None currently defined; ENH opportunity — alert the Timetable Manager when batch activity generation completes.

### Workflow 2: Working Day Calendar Initialisation and Editing
**Trigger:** Timetable Manager initialises the school calendar for a new academic session.
**End States:** All dates in the session date range have a Working Day record with the correct Day Types.
**Actors:** Timetable Manager

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Timetable Manager | Navigates to Working Days tab; clicks "Initialise Calendar" | System creates one Working Day record per calendar date in the session; weekdays default to Study, weekends to Holiday |
| 2 | Timetable Manager | Clicks a date on the FullCalendar display | Modal opens with Day Type picker |
| 3 | Timetable Manager | Selects or changes Day Types for the date | AJAX saves the change; calendar updates in-place |
| 4 | System | Updates Academic Term teaching/exam/working day counters | Not yet implemented — observer missing |

**Exception Paths:**
- Double-initialise: If the calendar is already initialised, the system should confirm before overwriting (current behaviour unverified).
- Date outside session range: Calendar should not allow editing dates outside the academic session.

### Workflow 3: Requirement Consolidation Generation
**Trigger:** Timetable Manager has completed Steps 1–3 and opens Page 4.
**End States:** One Requirement Consolidation record exists per class-section-subject-study-format combination for the selected term.
**Actors:** Timetable Manager | Academic Coordinator

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Timetable Manager | Selects Academic Term and Timetable Type; clicks "Generate Requirements" | System reads SchoolSetup class-subject-study-format mappings |
| 2 | System | Creates one consolidation record per unique combination | Records stored with default required_weekly_periods from curriculum |
| 3 | Timetable Manager | Reviews consolidation grid; identifies over/under-allocated subjects | Grid displays required periods per subject per class-section |
| 4 | Timetable Manager | Inline-edits required periods for specific cells | AJAX saves individual cell changes |
| 5 | Timetable Manager | Clicks "Get Statistics" | Summary panel shows total records, classes covered, subjects covered |

**Exception Paths:**
- No class-subject mappings: Zero records generated; warning message and link to SchoolSetup.
- Regeneration: Existing records for the same term are replaced (not duplicated). [Needs verification]

---

### Workflow 4: Activity Batch Generation
**Trigger:** Requirement Consolidation records exist; Timetable Manager clicks "Generate All Activities."
**End States:** One Activity record per Requirement Consolidation record, status DRAFT, ready for teacher assignment.
**Actors:** Timetable Manager | System

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Timetable Manager | Clicks "Generate All Activities" | POST to batch generation endpoint; background job starts |
| 2 | System | Generates activities class-by-class | Progress counter increments |
| 3 | Timetable Manager | Polls progress endpoint every 2 seconds | Progress bar updates; completion percentage shown |
| 4 | System | Job completes | UI shows "Generation Complete"; activity list refreshes |
| 5 | Timetable Manager | Reviews activity list; assigns teachers to activities | One or more teacher assignments per activity |

**Exception Paths:**
- Batch stalls (>2 min per class): No rate limiting or timeout recovery currently implemented (gap).
- Missing consolidation records: Batch generates only for classes with consolidation records; a warning lists classes skipped.

### Workflow 5: Teacher Availability Generation and Matrix Editing
**Trigger:** Activities have been generated (Step 6 pre-requisite complete).
**End States:** Each teacher referenced in Requirement Consolidation has an Availability record with per-slot details and the slot matrix reflects the teacher's actual availability.
**Actors:** Timetable Manager | Teacher (read-only view)

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Timetable Manager | Clicks "Generate Teacher Availability" | System creates one master Availability record per teacher in Requirement Consolidation |
| 2 | System | Creates per-slot detail records (7 days × N periods) | All slots default to Available |
| 3 | Timetable Manager | Opens a teacher's Availability matrix | 7×N grid displayed with toggle controls |
| 4 | Timetable Manager | Toggles specific slots to Unavailable | AJAX saves; audit log entry created |
| 5 | Timetable Manager | Sets workload parameters (max periods, allocation strictness) | Record updated |

**Exception Paths:**
- Teacher record does not exist in StaffProfile: Availability cannot be generated for that teacher; warning displayed.
- Duplicate slot record (same teacher-day-period): Graceful "Slot already configured" error (gap — not yet validated).
