## Section 1 — Module Overview

### 1.1 Business Purpose

Every Indian K-12 school must configure its organizational skeleton — grades, sections, subjects, staff, rooms, and rules — before any academic activity can begin. School Setup is the first module that must be completed after a school is onboarded to Prime-AI; it provides the shared reference data (classes, sections, subjects, employees, rooms, session mapping) that every other module depends on. Without School Setup being fully and correctly configured, no student can be enrolled, no timetable can be generated, no fees can be assigned, and no report cards can be produced.

The module covers four distinct functional areas: the core school profile and operating calendar; the academic structure (grades, sections, subjects, and their combinations); the physical campus (buildings, room types, rooms); and the employee dimension (staff profiles, teacher capabilities, HR configuration masters, leave management, and attendance). It also owns the school's user-access system — creating user accounts, defining roles, and assigning permissions — making it the security foundation of the entire tenant instance.

### 1.2 Business Value

- **Single source of truth:** Every other module reads school structure data (classes, sections, subjects, employees, rooms) from one place — preventing inconsistency across the platform.
- **Eliminates manual duplication:** HR configuration masters (leave types, attendance types, shift rules) are defined once and consumed automatically by payroll, attendance, and leave management.
- **Accelerates onboarding:** A structured 4-step employee onboarding flow (user account → employee record → profile → teacher profile) brings new staff onto the platform in minutes rather than hours.
- **Role-based access control:** Built-in user account and permission management means every staff member sees exactly the screens and data their role permits — with no manual coding per tenant.
- **Compliance readiness:** Board affiliations, UDISE codes, and affiliation numbers are stored centrally for government reporting; employee documents and leave records support statutory audit trails.
- **Downstream enablement:** Correct class-subject-teacher configuration here directly enables the AI Timetable Generator, the LMS, and HPC (Holistic Progress Card) to function without manual data re-entry.

### 1.3 Scope

#### In Scope

1. School organization profile (name, address, affiliation, board affiliations, logo)
2. Academic session mapping to the school's calendar year
3. Academic term configuration (terms within a session)
4. Holiday calendar management (public, optional, school-specific holidays)
5. Grade (class) master management with ordinal sequencing
6. Section master management
7. Class-section junction configuration (pairing grades with sections, assigning class teachers)
8. Subject master management (subject types, study formats, subject-study-format combinations)
9. Subject groups and class-subject mapping for timetable activity generation
10. Physical infrastructure — buildings, room types, and individual rooms
11. Department and designation master management
12. Employee records — creation, profile, documents, QR/ID card generation
13. Teacher profiles with subject-class capability mapping
14. Employee lifecycle management (role history, transfers, promotions, separations)
15. HR configuration masters (attendance types, leave types, leave entitlements, shift definitions)
16. Multi-level employee leave application and approval workflow
17. Employee attendance recording with biometric punch and correction workflows
18. User account management (creating system accounts for all staff)
19. Role and permission management (Spatie RBAC — role creation, permission assignment)
20. Entity groups (named collections of entities for notifications and events)
21. System dropdown value management (configurable lookup values shared across all modules)
22. School-level configuration key-value settings
23. Employee reports (attendance, leave balance, staffing, compliance, teacher capabilities)

#### Out of Scope

1. Global academic session creation — managed by the Platform Administrator in the Global Master module
2. Student enrollment and student profile management — Student Profile module
3. Biometric hardware integration and real-time punch capture — Attendance module (planned)
4. Payroll processing, salary slips, PF/ESI/TDS — HR & Payroll module (HrStaff)
5. Admission enquiry and application — Admission module
6. Fee head creation and fee invoice generation — Student Fee module
7. Timetable generation — Smart Timetable module (consumes SchoolSetup data)
8. Supplier/vendor management — Vendor module
9. Parent-teacher meeting scheduling — PTM module (uses employee data from this module)

### 1.4 Key Terminology

| Business Term | Meaning |
|---------------|---------|
| Grade (Class) | A year level within the school — e.g., Grade 1, Grade 10. The master record defines the name, short name, and display order. |
| Section | A division within a grade — e.g., Section A, Section B. Sections are defined globally at school level and then paired with grades. |
| Class-Section | The actual teaching unit formed by pairing a grade with a section — e.g., "Grade 6 - A". This is what students belong to, and what the timetable, fee, and LMS modules reference. |
| Subject Type | The classification of a subject: Core, Elective, Activity, Language, or Co-curricular. |
| Study Format | How a subject is taught: Theory, Practical, Project, Tutorial, or Online. |
| Subject-Study-Format Combination | A specific teaching mode for a subject — e.g., "Physics - Lab" (Theory + Practical as distinct timetable activities). |
| Class Group | A mapping that links a class-section to a specific Subject-Study-Format combination, forming the unit used by the AI Timetable Generator to build activity slots. |
| Subject Group | A named bundle of subjects offered to a specific class-section (e.g., "Science Stream" for Grade 11 - A). |
| Employee | Any staff member employed by the school — teaching or non-teaching. |
| Teacher Profile | The teaching-specific extension of an employee record capturing weekly period limits, lab certification, and substitution eligibility. |
| Teacher Capability | A documented association between a teacher and the specific subject-study-format they are qualified and available to teach for a specific grade. |
| Leave Session | An annual container defining the start and end dates of the leave year — holidays and leave balances are scoped to this container. |
| Leave Entitlement Configuration | The rule that specifies how many days of a particular leave type an employee is entitled to annually, based on their employment type, role, department, or designation. |
| Attendance Type | A named status for a working day or absence — e.g., Present, Absent, Half Day, Casual Leave. Drives payroll calculations. |
| Entity Group | A named collection of mixed entity types (employees, students, departments, sections) used to address bulk notifications or supervision assignments. |
| Dropdown Value | A configurable lookup option used across all modules for fields like entity purpose, holiday type, or employee category. |
| School Configuration | A key-value setting that controls module behavior for this school — e.g., academic year start month, grading scheme, SMS defaults. |
| UDISE Code | Unique identifier assigned to each school by the Government of India for census and reporting purposes. |
| Board Affiliation | The educational board (CBSE, ICSE, State Board, etc.) to which the school is affiliated for a given academic session. |
| Multi-Level Leave Approval | A configurable chain of approvers (by role, department, or designation) through which a leave application must pass before it is approved. |
| Flg Single Record | A system-enforced constraint ensuring each school has exactly one organization profile record. |
| Current Session Flag | A system-enforced constraint ensuring exactly one academic session is active as "current" at any given time. |

## Section 3 — Functional Requirements

### 3.1 Organization Profile Management
**Requirement ID:** REQ-SCH-001
**Priority:** Core (P0)
**Category Tags:** [CONFIGURATION] [DATA_ENTRY]

#### Business Description
Every school tenant must define its organization profile before any other configuration can begin. This profile captures the school's legal identity — name, address, affiliation codes, contact details, logo, geographic location, and operating locale. It also records the school's board affiliations for the current academic session. The profile is a singleton record (exactly one per school) enforced by the system. All downstream modules read from this record to display the school name, address, and contact details on letters, certificates, and reports.

#### Actors
- **Initiates:** School Administrator
- **Processes / Approves:** School Administrator
- **Views / Receives notification:** Principal, HR Officer, IT Administrator (read-only)

#### Business Rules

| Rule ID | Business Rule | Rule Type |
|---------|--------------|-----------|
| BR-SCH-001 | Exactly one organization profile record may exist per school. The system enforces this automatically — attempting to create a second record is rejected. | Validation |
| BR-SCH-002 | All data saved for an organization must come from fields the user has explicitly filled in; no unverified or injected field values may be persisted. | Validation |
| BR-SCH-003 | Board affiliations are linked to the school's current academic session — a school may change board affiliations when switching sessions. | Workflow |
| BR-SCH-004 | The school logo is stored in the document management system; a URL reference is kept in the profile. | Validation |
| BR-SCH-005 | Geographic location (city) automatically resolves the associated district, state, and country from the global master. | Calculation |
| BR-SCH-006 | All additions, changes, and removals to the organization profile are recorded in the audit trail with the acting user's identity and timestamp. | Workflow |

#### Acceptance Criteria
This feature is considered complete when:
1. A School Administrator can create the organization profile and the system prevents any second record from being created.
2. Uploading a logo saves the file and displays a preview on the profile page.
3. Selecting a board affiliation links it to the currently active academic session; changing the session updates the affiliation context.
4. Selecting a city automatically populates district, state, and country without manual entry.
5. Any change to the profile is visible in the audit trail with the editor's name and the date and time of the change.
6. Soft-deleting the profile moves it to the trash; it can be restored; a force-delete permanently removes it (for testing/cleanup purposes only).

#### Integration with Other Modules
- Receives from: Global Master — city, state, country lookups; board lookup
- Sends to: All modules that display the school name and logo (Transport, Notification, Certificate, HPC, StudentFee)

#### Enhancement Notes (Future)
- ENH-SCH-001: Support multiple school logos/brand assets (watermark, letterhead, stamp) — ENH
- ENH-SCH-002: Government portal data push (UDISE auto-sync) — ENH

### 3.3 Academic Session Mapping
**Requirement ID:** REQ-SCH-003
**Priority:** Core (P0)
**Category Tags:** [CONFIGURATION]

#### Business Description
A school operates on annual academic sessions (e.g., April 2026 to March 2027). These global session templates are defined once by the Platform Administrator in the Global Master module. Each school must then map the appropriate global session to its own calendar, optionally overriding the start and end dates to reflect the school's specific academic calendar. The system enforces that exactly one session is active as "current" at any time — all other modules use the current session to scope their data.

#### Actors
- **Initiates:** School Administrator
- **Processes / Approves:** School Administrator
- **Views / Receives notification:** Principal, all users (current session shown in header)

#### Business Rules

| Rule ID | Business Rule | Rule Type |
|---------|--------------|-----------|
| BR-SCH-009 | Exactly one academic session may be marked as "current" at any time. Setting a new current session automatically removes the current designation from the previously active one. | Concurrency |
| BR-SCH-010 | A school cannot activate a session that overlaps in date range with another active session. | Validation |
| BR-SCH-011 | Board affiliations for a session are managed through the session record — changing the active session changes the board context. | Workflow |

#### Acceptance Criteria
1. A School Administrator can link a global academic session to the school with an optional date override.
2. Marking a session as current automatically clears the current flag from the previous session — the system does not allow two current sessions simultaneously.
3. The currently active session is displayed consistently across all pages.
4. Sessions can be toggled active/inactive; soft-deleted sessions can be restored.

#### Integration with Other Modules
- Receives from: Global Master — global academic session templates
- Sends to: All modules that filter data by academic year (StudentProfile, StudentFee, Syllabus, LmsExam, LmsQuiz, LmsHomework, Attendance, HPC)

### 3.4 Academic Term Configuration
**Requirement ID:** REQ-SCH-021
**Priority:** Standard (P1)
**Category Tags:** [CONFIGURATION]

#### Business Description
Within each academic session, a school divides the year into terms (e.g., Term 1: April–September, Term 2: October–March, or four quarterly terms). Academic terms define the teaching calendar granularity: total teaching days, periods per day, and the week start day. The active term (marked as "current") is used by the Smart Timetable and LMS modules to scope lesson plans and exam schedules.

#### Actors
- **Initiates:** School Administrator
- **Processes / Approves:** School Administrator
- **Views / Receives notification:** Principal, teachers (read-only)

#### Business Rules

| Rule ID | Business Rule | Rule Type |
|---------|--------------|-----------|
| BR-SCH-012 | Terms within the same academic session must not have overlapping date ranges. | Validation |
| BR-SCH-013 | Exactly one term per academic session may be marked as "current". | Concurrency |
| BR-SCH-014 | A term cannot be deleted while it is referenced by active timetable or lesson plan records. | Validation |

#### Acceptance Criteria
1. A School Administrator can create multiple terms under one academic session.
2. Each term has a unique code within its session, a name, start date, end date, total teaching days, periods per day, and week start day.
3. Setting one term as "current" automatically clears the current designation from any previously current term in the same session.
4. Overlapping date ranges across terms in the same session are rejected.

#### Integration with Other Modules
- Sends to: Smart Timetable, TimetableFoundation, Syllabus (lesson scheduling)

| Rule ID | Business Rule | Rule Type |
|---------|--------------|-----------|

| BR-SCH-019 | Restoring a previously deleted grade also restores all its associated class-sections. | Workflow |

### 3.8 Class-Section Configuration
**Requirement ID:** REQ-SCH-008

**Category Tags:** [CONFIGURATION]

A Class-Section is the pairing of a grade with a section — the actual teaching unit that students belong to (e.g., "Grade 6 - Section A"). Each class-section record carries operational details: student capacity (minimum, maximum, actual count), the assigned class teacher, an optional assistant class teacher, and the default room. #### Actors
- **Initiates:** School Administrator
- **Processes / Approves:** School Administrator
- **Views / Receives notification:** All modules

#### Business Rules

| Rule ID | Business Rule | Rule Type |
|---------|--------------|-----------|
| BR-SCH-022 | When sections are removed from a grade's configuration, the associated class-section records are deactivated (marked inactive) rather than permanently deleted, to preserve historical data. | Workflow |

| BR-SCH-024 | A class teacher may be assigned to only one class-section as primary class teacher at a time within the same academic session. | Validation |

#### Acceptance Criteria
1. Creating or updating a grade automatically updates the associated class-section pairings in the same action.
2. Removing a section from a grade marks the class-section as inactive — it does not permanently delete the record.
3. Class teacher and assistant class teacher assignments are validated against the employee master.
4. The actual student count is kept up to date automatically.

#### Integration with Other Modules
- Sends to: StudentProfile (student assignment), SmartTimetable, Syllabus, LmsExam, LmsHomework, StudentFee, HPC, Library, Recommendation

### 3.11 Infrastructure — Buildings, Room Types, Rooms
**Requirement ID:** REQ-SCH-011
**Priority:** Standard (P1)
**Category Tags:** [CONFIGURATION]

#### Business Description

## Section 6 — Workflows

### 6.1 Employee Onboarding Workflow

**Trigger:** HR Officer decides to add a new employee to the system.
**End State:** The employee has a user account, a complete employee record (with profile and optional teacher profile), uploaded documents, and an active QR code.

#### Steps

1. **Create User Account:** The IT Administrator creates a system user account for the new employee with a username, email, and initial password. The employee's access role is assigned.
   - Decision: If Teacher role is assigned → the system prompts for teacher profile completion (Step 5).

2. **Create Employee Record:** The HR Officer creates the core employment record linking the user account to an employee code and joining date.

3. **Add Employee Profile:** The HR Officer adds the detailed profile — role, department, designation, daily and weekly work hours, preferred shift, core responsibilities.

4. **Upload Documents:** The HR Officer uploads the employee's identity documents, qualification certificates, and employment contract.

5. **[Teachers only] Add Teacher Profile:** The HR Officer or School Administrator completes the teaching-specific profile — period limits, substitution eligibility, lab certification.

6. **[Teachers only] Assign Subject Capabilities:** The HR Officer assigns the subjects, grades, and study formats the teacher is qualified to teach, along with priority rankings.

7. **Generate ID Card / QR Code:** The system generates a QR code (or other ID card format) encoding the employee's unique code.

#### Exception Paths
- If the user account already exists (e.g., re-hire): the HR Officer links the existing user account to the new employee record instead of creating a duplicate.
- If required profile fields are missing: the system saves partial data but flags the profile as incomplete; the employee cannot be assigned to a class until the profile is complete.

#### Notifications Triggered

| At Step | Who Receives | Message Summary |
|---------|-------------|-----------------|
| Step 7 (ID generated) | Employee | "Your employee ID card and QR code are ready — access them from your profile." |

---

### 6.2 Academic Session Setup Workflow

**Trigger:** A new academic year begins; the School Administrator must activate the new session.
**End State:** The new academic session is active and all modules use the new session as their data context.

#### Steps

1. **Select Global Session:** The School Administrator selects the global academic session template matching the new year from the Global Master list.

2. **Map to School Calendar:** The administrator optionally overrides the start and end dates to match the school's specific academic calendar.

3. **Set Board Affiliations:** The administrator selects the boards the school is affiliated with for this session.

4. **Activate Session:** The administrator marks the new session as "current" — the system automatically deactivates the previous current session.

5. **Configure Academic Terms:** The administrator defines the terms within the new session (e.g., Term 1, Term 2) with dates, teaching days, and periods per day.

#### Exception Paths
- If no global session template exists for the new year: the Platform Administrator must create one in the Global Master module first.
- If the date range overlaps with an existing session: the system rejects the activation with an explanation.

#### Notifications Triggered
None — this is a configuration action with no outgoing notifications.

---

### 6.3 Leave Application and Approval Workflow

**Trigger:** An employee submits a leave application.
**End State:** The leave application is approved (leave balance deducted, attendance updated) or rejected (balance unchanged).

#### Steps

1. **Application Submission:** The employee fills in the leave type, dates, reason, and attaches required documents (if applicable) and submits the application.
   - Decision: If leave type requires advance notice → validate that the start date is at least the configured minimum days in the future. Reject if not.
   - Decision: If dates overlap with existing leave → reject with explanation.

2. **Level 1 Approval Routing:** The system routes the application to the first-level approver defined in the applicable Leave Approval Policy. The approver receives a notification.

3. **Level 1 Approver Action:** The approver reviews the application.
   - Decision: Approve → advance to Level 2 (if configured) or go to Step 5 (if Level 1 is final).
   - Decision: Reject → application moves to Rejected state; employee notified.
   - Decision: Auto-timeout expires → application automatically advances to Level 2.

4. **[If multi-level] Level N Approver Action:** Repeated for each subsequent approval level. Same approve/reject/timeout logic.

5. **Final Approval:** The final approver approves the application. The system marks the application as Approved, reduces the employee's leave balance by the approved days, and marks the relevant days in the attendance record.

6. **Completion Notification:** The employee receives a notification confirming approval or rejection.

#### Exception Paths
- If the employee withdraws before any level acts: the application moves to Cancelled state; no balance change.
- If a document is required but not attached: submission is blocked with a validation message.

#### Notifications Triggered

| At Step | Who Receives | Message Summary |
|---------|-------------|-----------------|
| Step 2 | Level 1 Approver | "A new leave application from [Employee Name] is awaiting your review." |
| Step 3/4 (if advance) | Next level approver | "A leave application has been escalated to you for review." |
| Step 5 | Employee | "Your leave application for [dates] has been approved." |
| Step 3 (if rejected at any level) | Employee | "Your leave application for [dates] has been rejected. Reason: [reason]." |

---

### 6.4 Class and Subject Setup Workflow

**Trigger:** A new academic year is configured; the School Administrator sets up the academic structure for the year.
**End State:** All grades, sections, subjects, class-sections, and class groups are configured; SmartTimetable can begin timetable generation.

#### Steps

1. **Configure Sections:** Create or verify the section master list (A, B, C, etc.).

2. **Configure Grades:** Create grades (1–12) with short names and codes; reorder as needed.

3. **Create Class-Sections:** Pair grades with sections to form class-sections; assign class teachers, capacity limits, and default rooms.

4. **Configure Subject Types and Study Formats:** Define or verify the subject type list (Core, Elective, etc.) and study format list (Theory, Practical, etc.).

5. **Create Subjects:** Create all subjects; link each to a subject type; create subject-study-format combinations.

6. **Create Subject Groups:** For each class-section, create a subject group and add the subjects offered to that class-section.

7. **Create Class Groups:** Map each class-section to specific subject-study-format combinations; set ordinal order; configure multiple-options if applicable.

#### Exception Paths
- If a class-section is created without a class teacher: the system allows creation but flags the record as incomplete; SmartTimetable cannot include it in generation.

---

### 6.5 Employee Attendance Recording Workflow

**Trigger:** Daily clock-in/out by employees, or manual entry by HR Officer.
**End State:** All employees have a recorded attendance status for the day; any corrections are approved and reflected.

#### Steps

1. **Punch Recording:** Biometric device records in/out timestamps for the employee (imported nightly) OR HR Officer enters manual attendance.

2. **Status Derivation:** The system calculates attendance status by applying the employee's shift timing, grace period allowances, and half-day threshold.

3. **Attendance Record Creation:** A dated attendance record is created for the employee with the derived status and attendance type.

4. **[If needed] Correction Request:** The employee or HR Officer identifies an incorrect record and submits a correction request with the corrected status and supporting reason/document.

5. **Correction Approval:** The designated approver reviews the correction request and approves or rejects it.

6. **Record Update:** An approved correction overwrites the original status; the audit trail retains both original and corrected values.

#### Exception Paths
- If no punch records exist for an employee on a given day and no manual entry is made: the system marks the employee as absent by default.

---

### 6.6 RBAC Configuration Workflow

**Trigger:** A new staff role is needed, or an existing role's access permissions need to change.
**End State:** The role exists with the correct permissions; all users holding the role have the updated access.

#### Steps

1. **Create Role:** The IT Administrator creates a new role with a descriptive name.

2. **Assign Permissions:** The administrator selects the relevant permission group (e.g., "school-setup.student.*") and toggles individual permissions on or off. Permission groups can also be assigned in bulk.

3. **Save Role:** The role is saved; permission changes take effect immediately for all users holding this role.

4. **Assign Role to User:** In User Account Management, the IT Administrator assigns the role to one or more user accounts.

#### Exception Paths
- If a role to be deleted still has users assigned to it: the system rejects the deletion and lists the affected users; the administrator must reassign those users first.

## Section 9 — Non-Functional Requirements

### 9.1 Performance Expectations

| Requirement | Standard |
|-------------|---------|
| Screen load time | All configuration screens must load within 3 seconds for a school with up to 100 employees and 5,000 students |
| AJAX responses | All AJAX-driven actions (class CRUD, drag-reorder, permission toggles) must respond within 1 second |
| Report generation | Employee attendance and leave balance reports for a full academic year must complete within 15 seconds |
| Bulk operations | Creating 12 grades with 5 sections each (60 class-sections) in a single request must complete within 5 seconds |
| Master data reads | Reads of class, section, and subject lists (used by downstream modules on every page) must complete within 500ms; cache layer required |

### 9.2 Security Requirements

| Requirement | Rule |
|-------------|------|
| Module license gating | No route within School Setup may be accessed by a user whose school has not licensed the School Setup module |
| Role-based access | Every screen requires a specific permission checked at the server before the page is rendered — no client-side-only access control |
| Super-admin privilege | The super-admin flag on a user account may only be set by the Platform Administrator — not by school-level users under any circumstance |
| Sensitive PII encryption | Employee bank account numbers and IFSC codes must be stored encrypted in the database |
| Mass assignment prevention | All server-side data operations must use validated, explicitly-whitelisted input — bulk insertion of arbitrary fields must be blocked |
| Data isolation | Absolutely no data from one school may appear in another school's screens, reports, or exports — enforced by database-per-tenant architecture |
| Audit trail | Every creation, modification, and deletion of a configuration record must record the acting user, the timestamp, the before-value, and the after-value |
| Leave document access | Documents attached to leave applications may only be viewed by the applicant, the HR Officer, and the approvers in the application's policy chain |

### 9.3 Usability Requirements

| Requirement | Standard |
|-------------|---------|
| Drag-and-drop reordering | Grade, section, subject, subject type, and study format ordinal sequences must be maintainable via drag-and-drop without page reload |
| AJAX-driven configuration | Grade CRUD, class-section updates, and permission toggles operate without full page reload — immediate feedback to the user |
| Multi-step employee onboarding | The multi-step employee onboarding flow must preserve progress if the user navigates away — no data loss on mid-flow interruption |
| Mobile screens | The leave application submission and leave approval screens must be fully functional on mobile browsers |
| Empty states | Every list screen must display a clear, actionable empty-state message when no records exist (e.g., "No grades configured yet — click Add Grade to begin") |
| Validation feedback | All form validation errors are surfaced inline next to the relevant field — not as a generic page-level alert |
