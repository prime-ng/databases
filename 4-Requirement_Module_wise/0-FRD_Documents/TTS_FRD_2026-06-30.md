## 1. Module Overview

### 1.1 Purpose

The Standard Timetable module gives a school's Timetable Coordinator a manual drag-and-drop scheduling tool for constructing weekly class timetables by hand. It is the human-guided alternative to the AI generation path offered by the Smart Timetable module. Every period cell in every class's weekly grid is placed deliberately by a staff member, with real-time conflict warnings surfacing teacher clashes, room clashes, and class double-bookings as each slot is filled.

Once a timetable is complete, it passes through an approval workflow — the Coordinator submits it, the Principal approves it, and on approval it is published and becomes visible to all stakeholders: teachers see their personal weekly schedule, class teachers see their class schedule, and the admin sees room-wise utilisation.

### 1.2 Business Value

- Gives schools that prefer human scheduling over algorithmic output a capable first-party tool within the same platform.
- Eliminates the spreadsheet/paper-based timetable process that is the current K-12 industry norm.
- Real-time conflict detection prevents the most common manual scheduling errors (teacher double-booking, lab clashes) before the timetable is published.
- A single published source of truth per academic term reduces the "which version is current?" confusion that plagues email-distributed timetable PDFs.
- The Principal approval step satisfies school governance requirements before a timetable is made live.

### 1.3 Scope

**In Scope:**
- Manual creation, editing, and deletion of draft timetables
- Drag-and-drop period-cell placement with real-time conflict detection (5 check types)
- Cell lock and unlock controls
- Timetable publish workflow (Coordinator submits, Principal approves)
- Copy an existing timetable as a starting point for a new term
- Class-wise, teacher-wise, and room-wise read views of published timetables
- Print-optimised layout and CSV/PDF export of read views
- Per-cell change audit trail
- Granular role-based access control (7 distinct permissions)

**Out of Scope:**
- AI-based timetable generation — owned by Smart Timetable (STT)
- Constraint configuration and period-set setup — owned by Timetable Foundation (TTF)
- Teacher substitution management — owned by Smart Timetable (STT)
- Student and parent portal views of timetables — owned by Student Portal and Parent Portal modules
- Cross-school (cross-tenant) timetable comparison — never applicable (each school is an isolated database)

### 1.4 Terminology

| Term | Business Definition |
|------|-------------------|
| Manual Timetable | A weekly schedule for a school where every period cell is placed by a staff member, as opposed to being generated by the AI solver |
| Activity Card | A schedulable teaching unit for one class-section — it names the subject, study format, teacher(s), and how many periods per week it requires |
| Period Slot | A single intersection of a school day and a period ordinal in the weekly grid (e.g., Monday, Period 3) |
| Conflict | A scheduling violation where two activities share the same teacher, room, or class at the same period slot |
| Activity Palette | The left-side panel on the grid editor listing all Activity Cards for the selected class-section, with their placement progress |
| Draft | The initial status of a new manual timetable — editable but not yet visible to teachers or students |
| Generated | The status a timetable enters after the Coordinator submits it for approval — read-only while awaiting the Principal's decision |
| Published | The approved, live status of a timetable — visible in all read views; no further cell edits are permitted |
| Archived | The status of a previously published timetable that has been superseded by a newer published timetable for the same type and term |
| Locked Cell | A placed period cell that has been explicitly protected against accidental removal or replacement by the Coordinator |
| Period Set | The master list of time slots for a school day — defines how many periods exist, their start/end times, and which are break/lunch periods |
| Academic Term | A segment of the academic year (e.g., Term 1, Term 2) to which a timetable is anchored |
| Timetable Type | A named scheduling configuration (e.g., Regular, Exam Prep) that links to a specific Period Set |
| Cell Audit Trail | A record of every placement, removal, lock, and unlock action performed on the timetable grid |
| Gap Period | A free period that falls between two assigned periods for the same teacher on the same day, shown with a visual indicator in teacher-wise view |

## 3. Functional Requirements

### 3.1 REQ-TTS-001 — Manual Timetable Creation [DATA_ENTRY][CONFIGURATION]
**Priority:** Core (P0)

**Description:** A Timetable Coordinator or Admin can create a new manual timetable by supplying a name, selecting an Academic Term, and selecting a Timetable Type. The system auto-generates a unique reference code and sets the initial status to Draft. It validates that a Period Set is configured for the selected Timetable Type before allowing creation.

**Actors who Initiate:** Timetable Coordinator, School Admin
**Actors who Process:** System (validation, code generation, database record creation)
**Actors who View:** Timetable Coordinator, School Admin, Principal (in selector lists)

| BR | Rule |
|----|------|
| BR-TTS-001 | Only records explicitly designated as Manual Timetables may have period cells placed via this module |
| BR-TTS-006 | A manual timetable can only be deleted while in Draft status |

**Acceptance Criteria:**
1. Given an Admin opens the Create Timetable dialog and supplies a valid name, term, and type, when they submit, then a new Manual Timetable record appears in the list with status Draft and an auto-generated reference code beginning with "MT_".
2. Given no Period Set is linked to the selected Timetable Type and Term, when the Admin submits, then the form returns a validation error "No Period Set is configured for the selected Timetable Type" and no record is created.
3. Given the Academic Year has no active session, when the Admin creates a timetable, then the system creates it without a session link and the coordinator receives a visible warning.

**Integration:** Reads Period Set configuration from Timetable Foundation; reads current Academic Session from system session master.

### 3.2 REQ-TTS-002 — Copy Timetable [DATA_ENTRY][WORKFLOW]
**Priority:** Standard (P1)

**Description:** An Admin or Coordinator can create a new Draft manual timetable by copying an existing timetable (of any type — manual or AI-generated, Published or Archived). All period cells and teacher assignments from the source are duplicated into the new timetable, which is set to Draft and version 1. The original is never modified.

**Actors who Initiate:** Timetable Coordinator, School Admin
**Actors who Process:** System (transactional copy)
**Actors who View:** Timetable Coordinator, School Admin

| BR | Rule |
|----|------|
| BR-TTS-011 | Copy creates a new Draft timetable at version 1; source timetable is unchanged |

**Acceptance Criteria:**
1. Given a Published timetable for Term 1, when the Admin chooses "Copy" and specifies Term 2, then a new Draft timetable is created with all cells and teacher assignments duplicated, and the Term 1 timetable remains unchanged.
2. Given the copy operation fails mid-way due to a system error, when the error occurs, then the partial new timetable is fully rolled back and the Admin sees an error message.
3. Given the source timetable has 150 cells, when the copy completes, then all 150 cells and their teacher assignments are present in the new timetable.

**Integration:** Reads from all timetable tables; writes to timetable and cell records within a single database transaction.

### 3.3 REQ-TTS-003 — Effective Dates and One-Published Rule [CONFIGURATION][WORKFLOW]
**Priority:** Standard (P1)

**Description:** When creating a timetable, the Coordinator may optionally set an effective start date and end date indicating the active period of the timetable within the term. The system enforces that at any time, only one timetable per Timetable Type and Academic Term combination may be in Published status. Attempting to publish a second timetable for the same type and term prompts the Coordinator to archive the currently published one.

**Actors who Initiate:** Timetable Coordinator, School Admin

| BR | Rule |
|----|------|
| BR-TTS-005 | Only one Published timetable per Timetable Type and Academic Term at a time |

**Acceptance Criteria:**
1. Given a Published timetable for Type "Regular" + Term 1 already exists, when the Admin attempts to publish a second timetable for the same type and term, then the system prompts "A published timetable already exists. Archive it and publish this one?" and proceeds only on confirmation.
2. Given the Admin archives the existing published timetable on confirmation, then the previous timetable transitions to Archived status and the new timetable becomes Published.

**Integration:** Checks existing Published records in the timetable registry before each publish action.

### 3.4 REQ-TTS-004 — Timetable Deletion Guard [DATA_ENTRY]
**Priority:** Core (P0)

**Description:** A Manual Timetable in Draft status may be permanently deleted along with all its period cells and teacher assignments, using a database transaction to guarantee atomic removal. Timetables in Published status cannot be deleted. Timetables in Generated (pending approval) or Archived status also cannot be deleted.

**Actors who Initiate:** School Admin

| BR | Rule |
|----|------|
| BR-TTS-006 | Deletion is permitted only for Draft manual timetables |

**Acceptance Criteria:**
1. Given a Draft manual timetable with 80 placed cells, when the Admin confirms deletion, then the timetable, all its cells, and all teacher assignments are permanently removed together; the admin sees a success message.
2. Given a Published manual timetable, when the Admin attempts deletion, then the system returns an error "Cannot delete a published timetable" and no data is removed.
3. Given the deletion transaction fails mid-way, when the error occurs, then all changes are rolled back and the timetable, cells, and teacher assignments remain intact.

**Integration:** None — operates only on data owned by this module's timetable records.

### 3.5 REQ-TTS-005 — Drag-and-Drop Grid Editor [DATA_ENTRY]
**Priority:** Core (P0)

**Description:** The Manual Placement screen presents a two-panel layout. The left Activity Palette lists Activity Cards for the selected class-section, showing subject, study format, weekly periods needed, and current placement progress. The right Period Grid shows days as rows and period ordinals as columns. The Coordinator drags an Activity Card from the palette and drops it onto a grid cell; the system immediately places the activity (via an AJAX call) without a page reload. Placed cells show the subject, teacher initials, and room code. If a cell is already occupied, the new activity replaces it with a warning. Break-period cells must visually indicate they are non-droppable and reject any placement attempt. A placement progress counter tracks cells placed out of total available slots.

**Actors who Initiate:** Timetable Coordinator, School Admin
**Actors who Process:** System (conflict check, cell write, teacher assignment, counter update)
**Actors who View:** Timetable Coordinator, School Admin

| BR | Rule |
|----|------|
| BR-TTS-001 | Only Manual Timetables receive drag-and-drop placements |
| BR-TTS-004 | A Published timetable rejects any further cell placements or removals |
| BR-TTS-008 | Conflicts are warnings that allow placement to proceed, except break periods which hard-reject with an error message |
| BR-TTS-010 | Activity palette placement counters recalculate after every place and remove action |
| BR-TTS-014 | Placing an activity on a break period returns an error; the placement is refused |

**Acceptance Criteria:**
1. Given the grid is loaded for class 10-A and Timetable X, when the Coordinator drops "Mathematics" onto Monday Period 2, then the cell shows "Mathematics / A. Kumar / Rm 101" without a page reload and the palette counter for Mathematics updates from "2 placed" to "3 placed".
2. Given Monday Period 3 is a break period, when the Coordinator attempts to drop an activity onto it, then the system refuses placement and displays "Break periods cannot be scheduled".
3. Given an activity has 5 periods needed and 4 are placed, when the 5th is placed, then the palette marks the activity as fully placed with a visual indicator.
4. Given a Published timetable is selected, when the Coordinator attempts to place any cell, then the system refuses and displays "Published timetables are read-only".

**Integration:** Reads Activity and teacher configuration from Timetable Foundation; reads room data from School Setup.

### 3.6 REQ-TTS-006 — Real-Time Conflict Detection [WORKFLOW]
**Priority:** Core (P0)

**Description:** On every period cell placement, the system runs five conflict checks simultaneously before writing the cell: (1) teacher already teaching another subject to a different class in this timetable at the same slot; (2) teacher already assigned in a different active timetable at the same slot; (3) room already booked in this timetable at the same slot; (4) room already booked in a different active timetable at the same slot; (5) the same class already has a different activity at the same slot (the existing activity is replaced). All conflict findings are warnings — placement proceeds but the cell is highlighted in amber with a conflict badge and the conflict details are stored on the cell record. The conflict message names the conflicting teacher, room, or timetable.

**Actors who Initiate:** System (triggered automatically on each placement)
**Actors who View:** Timetable Coordinator (warnings displayed in real time)

| BR | Rule |
|----|------|
| BR-TTS-007 | Conflict detection covers all five types listed above |
| BR-TTS-008 | Conflict results are warnings except for break-period placement (hard block) |

**Acceptance Criteria:**
1. Given teacher A. Kumar is assigned to Class 9-B Monday Period 1 in Timetable X, when the Coordinator places A. Kumar onto Monday Period 1 in Timetable Y (Class 10-A), then the system allows placement but returns a warning "A. Kumar is busy in Class 9-B Timetable at this slot" and highlights the cell.
2. Given Science Lab is already used in Timetable Z at Tuesday Period 4, when the Coordinator places an activity requiring Science Lab at Tuesday Period 4 in a new timetable, then a warning "Science Lab is occupied in another timetable" is shown.
3. Given no conflicts exist, when the Coordinator places a cell, then the AJAX response returns no warnings and the cell is shown without a conflict indicator.

**Integration:** Reads from all active timetable cells across the school (within the tenant database, current academic term scope).

### 3.7 REQ-TTS-007 — Conflict Persistence and Batch Validate [WORKFLOW][REPORT]
**Priority:** Standard (P1)

**Description:** Every conflict detected during real-time placement must be recorded in the conflict log for audit and later review, stamped as a real-time detection. A "Validate All" button triggers a full batch scan of all cells in the current timetable, recording all detected violations in the conflict log as batch-detection records and displaying a paginated violation list to the Coordinator. A conflict summary badge in the page header shows the current total count of active conflicts for the selected timetable.

**Actors who Initiate:** Timetable Coordinator (Validate All), System (real-time log writes)
**Actors who View:** Timetable Coordinator, School Admin

| BR | Rule |
|----|------|
| BR-TTS-007 | Same five conflict types apply in batch mode as in real-time mode |

**Acceptance Criteria:**
1. Given three conflicts exist in the current timetable, the conflict badge in the page header shows "3 conflicts".
2. Given the Coordinator clicks "Validate All", when the scan completes, then a panel displays a list of all violations with type, affected teacher/room/class, and the conflicting period slot.
3. Given a conflict is subsequently resolved by removing a cell, the conflict count in the badge decrements.

**Integration:** Writes to conflict detection log; reads from all placed cells and teacher/room assignments.

### 3.8 REQ-TTS-008 — Standard Read Views [REPORT]
**Priority:** Standard (P1)

**Description:** Three read-only weekly grid views provide different perspectives on a Published timetable. The class-wise view shows a full weekly grid for a selected class-section with subject, teacher, and room per cell. The teacher-wise view shows a teacher's weekly schedule across all class-sections, with free periods dimmed and gap periods (free periods between two assignments on the same day) shown with a dashed border and a weekly period load summary. The room-wise view shows a room's occupancy grid with booked cells showing class and teacher, and free slots shown in green indicating availability. All three views display only Published timetables. If no published timetable exists, a prompt directs the user to the placement screen. Period type colour coding (teaching, break, exam, locked) is applied across all views.

**Actors who Initiate:** School Admin, Coordinator, Principal (any view), Class Teacher (own class), Subject Teacher (own schedule)
**Actors who View:** As above

| BR | Rule |
|----|------|
| BR-TTS-002 | Read views display only Published timetables |
| BR-TTS-013 | A teacher-role user may only view their own teacher schedule |

**Acceptance Criteria:**
1. Given a Published timetable exists for Class 10-A, when the Principal opens the class-wise view and selects Class 10-A, then a complete weekly grid is displayed showing subject, teacher, and room for every occupied slot.
2. Given no Published timetable exists, when any user opens a read view, then the page shows "No published timetable found. Please publish a timetable first." with a link to the placement screen.
3. Given Teacher A. Kumar opens the teacher-wise view, then only A. Kumar's schedule is accessible; attempting to view another teacher's schedule is denied.
4. Given a class teacher opens the class-wise view, then only their assigned class-section is accessible.

**Integration:** Reads from published timetable cells; uses Smart Timetable Analytics Service for data assembly; renders via shared grid partial from Smart Timetable.

### 3.10 REQ-TTS-010 — Cell Lock and Unlock [DATA_ENTRY]
**Priority:** Standard (P1)

**Description:** A Coordinator can lock any placed period cell to protect it from accidental removal or replacement. A locked cell displays a padlock icon overlay in the grid. Attempting to remove a locked cell returns an error. Attempting to place a new activity on a locked occupied cell is also refused. A locked cell can be unlocked via the same context menu. A "Lock All" action locks every placed cell in the current timetable in a single operation.

**Actors who Initiate:** Timetable Coordinator, School Admin
**Actors who Process:** System (sets lock flag, records who locked and when)

| BR | Rule |
|----|------|
| BR-TTS-003 | Removing a locked cell is refused with an error message |

**Acceptance Criteria:**
1. Given a cell is placed and unlocked, when the Coordinator right-clicks and selects "Lock Cell", then the cell displays a padlock icon and subsequent removal attempts are refused.
2. Given a locked cell exists, when the Coordinator attempts to place a different activity onto the same slot, then the system refuses with "Cell is locked".
3. Given the Coordinator selects "Lock All", when confirmed, then all currently placed cells in the timetable are locked in a single operation.
4. Given a locked cell, when the Coordinator selects "Unlock Cell" from the context menu, then the padlock icon disappears and the cell can once again be moved or removed.

### 3.11 REQ-TTS-011 — Publishing Workflow [WORKFLOW][APPROVAL][NOTIFICATION]
**Priority:** Standard (P1)

**Description:** A Draft timetable moves through an approval chain before it is visible to the school. The Coordinator or Admin submits the completed timetable for approval, which changes its status to Generated and sends a notification to the Principal. The Principal reviews the timetable via the read views and either approves (which publishes it) or sends it back with comments. On approval, the status becomes Published, the publication date and approver are recorded, and any previously Published timetable for the same type and term is automatically Archived. A Published timetable is immutable — no cell additions, changes, or removals are permitted unless it is first reverted to Generated status.

**Actors who Initiate:** Timetable Coordinator, School Admin (submit); Principal, School Admin (approve)
**Actors who Process:** System (status transition, notification, archive of previous)
**Actors who View:** All stakeholders (upon publication)

| BR | Rule |
|----|------|
| BR-TTS-004 | A Published timetable is immutable |
| BR-TTS-005 | Only one Published timetable per type and term at a time |

**Acceptance Criteria:**
1. Given a Draft timetable, when the Coordinator clicks "Submit for Approval", then the status changes to Generated and the Principal receives a notification containing the timetable name and a review link.
2. Given a Generated timetable, when the Principal approves it, then the status becomes Published, the publication date is recorded, and the previous Published timetable (if any) for the same type and term becomes Archived.
3. Given a Published timetable, when the Coordinator attempts to place any cell, then the system refuses with "Published timetables are read-only".
4. Given a Published timetable has been in use for a week, when the Admin reverts it to Generated, then cell editing is re-enabled and a notification is sent to the Coordinator.

**Integration:** Notification module — approval request and status change notifications.

### 3.13 REQ-TTS-013 — Role-Based Access Control [CONFIGURATION]
**Priority:** Core (P0)

**Description:** The module enforces seven distinct permission levels, each assigned to appropriate roles. All module routes require a valid school licence (the module must be enabled for the tenant). The dashboard and placement screens require explicit placement permission. Read views enforce entity-level scoping (class teachers see only their class; subject teachers see only their own schedule). All mutating actions (place, remove, lock, delete, publish) require dedicated permissions distinct from read permissions. The seeder registers all permissions and maps them to default roles on module installation.

**Actors who Initiate:** IT / Platform Admin (during setup); all user roles (at runtime)

| BR | Rule |
|----|------|
| BR-TTS-013 | A teacher-role user is restricted to viewing their own schedule |

**Acceptance Criteria:**
1. Given the Standard Timetable module is not enabled for a tenant, when any user navigates to a Standard Timetable route, then they are redirected with a "Module not available" message.
2. Given a subject teacher is logged in, when they navigate to the teacher-wise view, then only their own weekly schedule is accessible; navigating to another teacher's schedule returns a 403 error.
3. Given a class teacher is logged in, when they navigate to the class-wise view, then only their assigned class-section is accessible.
4. Given the Coordinator has the "manual place" permission and the "view any" permission, but not the "publish" permission, when they attempt to approve and publish a timetable, then the system refuses with a 403 error.
5. Given the permission seeder has run, when the default Coordinator role is checked, then all placement and view permissions (but not publish) are assigned.

### 3.14 REQ-TTS-014 — Cell Audit Trail [SCHEDULED][WORKFLOW]
**Priority:** Enhanced (P2)

**Description:** Every mutation to a period cell — placement, removal, lock, unlock — writes an audit record capturing the action type, the previous cell state, the new cell state, the staff member who made the change, and the timestamp. A read-only change log viewer, accessible to Admins, lists these records for a selected timetable with filters for date range and action type.

**Actors who Initiate:** System (automatic on every mutation)
**Actors who View:** School Admin, Timetable Coordinator (read-only)

| BR | Rule |
|----|------|
| BR-TTS-009 | Every cell mutation writes an audit record |

**Acceptance Criteria:**
1. Given the Coordinator places 10 cells, when the Admin opens the change log for the timetable, then 10 "Placed" records appear with the correct subject, slot, and staff member name.
2. Given the Coordinator removes a cell, when the Admin views the change log, then a "Removed" record appears showing the previous subject that occupied the slot.
3. Given the Admin views the change log with a filter for "today", then only changes made today are shown.

## 6. Workflows

### Workflow 1: Manual Timetable Construction
**Trigger:** Coordinator or Admin decides to build a timetable for a class for the current term.
**End States:** Timetable in Draft status with all required cells placed; or abandoned (deleted).

**Actors / Swimlanes:** Timetable Coordinator | System

1. Coordinator opens the Standard Timetable dashboard and clicks "+ New Timetable".
2. System displays a creation form: name, academic term, timetable type.
3. Coordinator fills the form and submits.
4. System validates: checks that a Period Set is linked to the selected type and term. If not → returns error "No Period Set is configured" → Coordinator corrects or sets up Period Set via Timetable Foundation → returns to step 3.
5. System creates the Draft Manual Timetable with an auto-generated reference code and redirects to the placement screen.
6. Coordinator selects a class-section from the selector. System loads the Activity Palette and an empty grid.
7. Coordinator drags an Activity Card from the palette onto a grid cell.
8. System runs conflict detection (5 checks). Returns conflict warnings if any. Writes the cell record and teacher assignments. Updates the palette counter for that activity.
9. Cell appears in the grid with subject, teacher initials, and room code. Coordinator repeats steps 7-8 for each period in the week.
10. Coordinator repeats steps 6-9 for each class-section.
11. Coordinator optionally locks critical cells via right-click → "Lock Cell".
12. Coordinator clicks "Validate All" to run a full batch conflict scan and reviews the violation list.
13. Timetable is in Draft status, ready for the publishing workflow.

**Exception paths:**
- Step 4 — No Period Set: Coordinator must configure Period Set in Timetable Foundation before proceeding.
- Step 7 — Break period drop: System refuses with "Break periods cannot be scheduled"; Coordinator chooses a different slot.
- Step 8 — System error writing cell: System rolls back the cell write and returns an error toast; Coordinator retries.

**Notifications triggered:** None in the construction phase.

---

### Workflow 2: Timetable Approval and Publication
**Trigger:** Coordinator has completed placing all cells and is ready to make the timetable live.
**End States:** Timetable Published (visible to all stakeholders); or returned to Draft for correction.

**Actors / Swimlanes:** Timetable Coordinator | Principal | System

1. Coordinator clicks "Submit for Approval" on the Draft timetable.
2. System changes status from Draft to Generated (read-only).
3. System sends a notification to the Principal: "Timetable [name] submitted for your review."
4. Principal opens the notification link, reviews the timetable via the class-wise and teacher-wise read views.
5a. (Approval path) Principal clicks "Approve and Publish".
6. System checks the one-published rule. If a Published timetable already exists for the same type and term, system archives it automatically.
7. System sets status to Published, records publication timestamp and approver name.
8. Timetable becomes visible in all read views. All stakeholders with view access can now see it.

5b. (Return path) Principal clicks "Return for Revision" with comments.
6. System changes status back to Draft and notifies the Coordinator: "Timetable [name] returned — [Principal's comments]."
7. Coordinator addresses the issues and re-submits (returns to step 1).

**Exception paths:**
- Principal is unavailable: Timetable remains in Generated status until actioned. A re-notification can be triggered by the Admin.
- Publish fails due to a system error: Status remains Generated; Admin retried manually.

**Notifications triggered:**
| Step | Recipient | Channel | Message |
|------|-----------|---------|---------|
| 3 | Principal | In-App + Email | "Timetable [name] has been submitted for your review and approval." |
| 6b | Coordinator | In-App | "Timetable [name] has been returned for revision. Comments: [text]." |
| 7 | Coordinator + School Admin | In-App | "Timetable [name] has been published and is now live." |

---

### Workflow 3: Copy Timetable
**Trigger:** Coordinator wants to reuse a previous term's timetable as a starting point.
**End States:** New Draft timetable with all cells from the source; source unchanged.

**Actors / Swimlanes:** Timetable Coordinator | System

1. Coordinator selects a source timetable (from any status or generation method) and clicks "Copy".
2. System displays a modal: new name field + academic term selection (defaults to same term as source).
3. Coordinator confirms.
4. System begins a database transaction: creates a new Draft Manual Timetable (version 1); copies all period cells from the source (marking each as Manual placed); copies all teacher assignments from the source cells.
5. Transaction commits. Coordinator is redirected to the placement screen for the new timetable with all cells pre-filled.
6. Coordinator adjusts any cells that differ between terms (adds, removes, replaces as needed).

**Exception paths:**
- Step 4 — Transaction fails: Full rollback; no partial timetable or cells exist; Coordinator sees an error message and retries.

---

### Workflow 4: Standard Read Views Access
**Trigger:** Teacher, Principal, or Admin wants to view the current timetable for a class, teacher, or room.
**End States:** Grid displayed; user prints or exports if needed.

**Actors / Swimlanes:** User (any permitted role) | System

1. User navigates to Class-Wise View, Teacher-Wise View, or Room-Wise View.
2. System checks if any Published timetable exists. If none → shows "No published timetable found" with a link to the placement screen.
3. System pre-selects the most recently published timetable in the selector.
4. User picks a class-section / teacher / room from the entity selector.
5. System applies role-based scoping (teacher users see only their own schedule; class teachers see only their class).
6. System assembles the grid data via the Analytics Service and renders the visual weekly grid with period type colour coding.
7. User optionally prints (window print) or exports CSV/PDF.

## 7. Reporting and Analytics

### RPT-TTS-001 — Class-Wise Timetable Grid
**Purpose:** Show a complete weekly timetable for one class-section.
**Audience:** School Admin, Coordinator, Principal, Class Teacher (own class)
**Frequency:** On-demand
**Contents:** Days as columns, period ordinals as rows; each occupied cell shows subject, teacher name, room; break periods shaded; locked cells show padlock indicator
**Filters:** Timetable selector (Published only), Class, Section
**Export:** Print (PDF-ready layout), CSV (Day, Period, Subject, Teacher, Room, Period Type), PDF (DomPDF)

### RPT-TTS-002 — Teacher-Wise Schedule
**Purpose:** Show one teacher's full weekly teaching schedule across all their classes.
**Audience:** School Admin, Coordinator, Principal, Subject Teacher (own schedule only)
**Frequency:** On-demand
**Contents:** Days as columns, period ordinals as rows; each occupied cell shows class-section, subject, room; free periods dimmed; gap periods (free periods between two assignments same day) shown with dashed border; weekly period load indicator (e.g., 18 / 20 periods)
**Filters:** Timetable selector (Published only), Teacher selector (scoped for teacher-role users)
**Export:** Print, CSV

### RPT-TTS-003 — Room-Wise Utilisation View
**Purpose:** Show a room's weekly occupancy to identify underutilised or fully booked rooms.
**Audience:** School Admin, Coordinator, Principal
**Frequency:** On-demand
**Contents:** Days as columns, periods as rows; booked cells show class-section, subject, teacher; free slots highlighted green
**Filters:** Timetable selector (Published only), Room selector
**Export:** Print

### RPT-TTS-004 — Cell Change Log View
**Purpose:** Audit trail of all changes made to a specific timetable's cells.
**Audience:** School Admin, Timetable Coordinator
**Frequency:** On-demand
**Contents:** Action type, slot (Day × Period), previous state (subject/teacher before change), new state, staff member who made the change, timestamp
**Filters:** Timetable selector, date range, action type (Placed / Removed / Locked / Unlocked)
**Export:** Print

## 9. Non-Functional Requirements

### 9.1 Performance

| Metric | Requirement |
|--------|-------------|
| Manual placement page load | Under 800 ms |
| Place-cell AJAX response (including conflict detection) | Under 200 ms |
| Remove-cell AJAX response | Under 100 ms |
| Class-wise / teacher-wise / room-wise view load | Under 500 ms |
| CSV export | Under 1 second for typical school (up to 50 class-sections) |
| PDF export (DomPDF single class) | Under 3 seconds |
| Copy timetable (up to 500 cells) | Under 2 seconds |
| Batch validate scan | Under 5 seconds for up to 2,000 cells |

### 9.2 Security

- The Standard Timetable module must be explicitly enabled for a school's licence before any user can access any route.
- All routes carry authentication and session verification.
- All write operations (place, remove, lock, delete, publish) require CSRF token protection.
- Seven distinct permission levels are enforced; there are no catch-all "admin sees everything" bypasses for timetable write actions.
- Teacher-role users are restricted to their own data at the application layer, not just the UI — server-side checks apply on every read view request.
- Inline validation in controller methods must be replaced with FormRequest classes that also enforce business-layer authorisation (is the timetable in an editable status?).
- SQL injection is prevented throughout by parameterised queries via the Eloquent ORM.

### 9.3 Usability

- Drag-and-drop must work on mouse (desktop/laptop); touch drag-and-drop on tablets is desirable but not mandatory in the first release.
- The period grid must be horizontally scrollable on screens narrower than 1,024 pixels.
- All AJAX operations must show a loading indicator and disable the triggering element to prevent double-submission.
- All errors returned from AJAX endpoints must appear as toast notifications, not browser alerts.
- Conflict warnings must be visually distinct from errors; amber for warnings, red for hard blocks.
- The Activity Palette must update instantly after each placement so the Coordinator always sees accurate placement progress.
