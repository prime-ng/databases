## Section 1: Module Overview

### 1.1 Purpose

The Student Portal (STP) is the student-facing self-service interface of the Prime-AI platform. It provides enrolled K-12 students — and optionally their parents/guardians — with a unified view of all academic, financial, and communication data through a dedicated portal on the school's tenant domain, fully isolated from the administrative backend. The portal runs under `/student-portal/*` with its own layout, login page, and auth flow.

### 1.2 Business Value

- Reduces administrative counter visits and phone calls by delivering 24/7 self-service access to timetables, results, fee invoices, attendance, and more
- Accelerates fee collection by enabling Razorpay online payment directly from the portal
- Increases parent engagement through real-time visibility into their child's academic and financial standing
- Provides students with a single hub for all LMS activities: homework submission, online exam-taking, quiz/quest play, syllabus tracking
- Enables schools to deliver a NEP-2020-aligned digital learning experience at zero marginal cost per student
- Mobile API tier extends all features to smartphone and PWA interfaces

### 1.3 Scope

**In Scope:**
- Student and parent/guardian authentication via a dedicated portal login page
- Dashboard with real-time academic snapshot (attendance, timetable, homework, exams, fees, notifications)
- Academic information: personal profile, attendance history, timetable grid, syllabus progress, teachers directory
- LMS assessment delivery: homework list and submission, online exam player (with anti-cheat, checkpointing, auto-timeout), quiz player, quest player, exam results, exam grievances
- Financial: fee invoice view, fee payment (Razorpay), fee summary
- Wellbeing and services: health records view, student leave application and status tracking, hostel information display, transport allocation display
- Progress and reports: Holistic Progress Card (HPC) display, performance analytics, personalized recommendations
- Resources: library catalogue browse, physical book reservation/renewal, digital resource access, study notes, prescribed books, notice board, school calendar
- Communications: notifications inbox (mark-read, mark-all-read), complaint submission and tracking
- Profile: student ID card digital view, account settings (password, notification preferences, privacy)
- Mobile API tier (19 controllers, Sanctum-guarded) covering all major features
- Parent/guardian mode: reading linked child's data where `can_access_parent_portal = true`

**Out of Scope:**
- Administrative functions: attendance marking, student record editing, fee structure management (handled by admin backend modules)
- Cross-tenant or cross-school views (each school's data is fully isolated in its own database)
- Staff portal and teacher functions (handled by HrStaff, SmartTimetable admin)
- Parent-Teacher Meeting booking (planned: ParentPortal module)
- Direct parent-teacher messaging (planned: CommonChat / ParentPortal module)
- Certificate generation (Certificate module generates; STP only links to the PDF)
- Admission/enrollment workflow (Admission module)
- Peer feedback on teachers or subjects (Feedback module)

### 1.4 Terminology

| Term | Definition |
|------|-----------|
| Student Portal | The STP module — student-facing web interface on the tenant subdomain at `/student-portal/*` |
| Tenant | A single school instance with its own isolated database (`tenant_{uuid}`); data is never mixed between schools |
| Academic Session | The school year (e.g., 2025-26) that scopes all academic data; a student has one active session per year |
| Fee Assignment | The fee structure allocated to a specific student for an academic session, containing all applicable fee heads |
| Fee Invoice | A bill generated against a student's fee assignment for a billing cycle; can be Pending, Published, Partially Paid, Overdue, or Paid |
| Exam Attempt | A student's active sitting of an online exam paper; carries status, per-question answers, anti-cheat activity logs, and a checkpoint for resumability |
| Attempt Checkpoint | A JSON save-point created during an online exam/quiz/quest attempt enabling the student to resume after a browser crash or network loss |
| IDOR | Insecure Direct Object Reference — a security vulnerability where a student can access another student's data by manipulating an ID in a URL or POST body |
| Progress Card | A published Holistic Progress Card (HPC) report showing a student's holistic assessment across scholastic and co-scholastic domains, generated by the HPC module |
| Guardian Portal Mode | A parent user (Spatie role: Parent) viewing the portal; sees data for their linked child rather than their own account |
| Allocation | A record linking an assessment (exam, quiz, quest, or homework) to a target audience: class-level, section-level, or individual student |
| EnsureTenantHasModule | Custom middleware that verifies the tenant's subscription plan includes the StudentPortal module before serving any portal route |
| Anti-Cheat | Server-side mechanisms enforcing exam integrity: timer enforcement, tab-switch logging, violation counting, auto-submit on timeout |
| Leave Application | A student's formal request for school-approved absence, submitted through the portal and tracked through a status workflow |

### REQ-STP-005: Fee Payment
**Priority:** Core (P0) | **Tags:** [WORKFLOW][INTEGRATION] | **Code Status:** 🟡 Partial — IDOR in payment initiation step (P0 blocker)

**Description:** A student selects a fee invoice, chooses a payment amount (minimum 1, maximum remaining balance), selects an active payment gateway, and is redirected to the Razorpay checkout. On success or failure, the system updates invoice status via the Razorpay webhook only (not via the redirect).

**Actors:** Initiates: Student, Parent (if `is_fee_payer=true`) | Processes: System, Razorpay | Views: System, Payment module

**Business Rules:**
| BR | Statement |
|----|-----------|
| BR-STP-003 | Before creating a Razorpay payment order, the system must verify server-side that the `payable_id` submitted by the student belongs to that student's fee assignment. The client-submitted `payable_id` must never be trusted without this check |
| BR-STP-006 | A student may only initiate payment on invoices in Published, Partially Paid, or Overdue status. Paid and Cancelled invoices must be read-only |
| BR-STP-007 | Payment amount must be between INR 1 and the remaining balance (`total_amount - paid_amount`) inclusive |
| BR-STP-008 | The payment gateway selection list must show only gateways with Active status |
| BR-STP-009 | A failed or cancelled Razorpay transaction must not update the invoice status; only the Payment module's webhook callback triggers status updates |
| BR-STP-010 | Payment initiation is rate-limited to a maximum of 3 attempts per 5 minutes per authenticated user |

**Acceptance Criteria:**
1. When Student A submits a payment request with `payable_id` pointing to Student B's invoice, the system rejects the request with a 403 or 422 response; no Razorpay order is created. YES/NO
2. A disabled or inactive payment gateway does not appear on the payment page. YES/NO
3. When a Razorpay payment is cancelled at the gateway, the invoice status remains unchanged. YES/NO
4. A payment amount of zero is rejected by server-side validation before reaching Razorpay. YES/NO

**Gap:** [SEC-STP-01] `proceedPayment()` method currently accepts `payable_id` from the POST body without ownership check — P0 security blocker.

**Integrations:** StudentFee (fee invoice data), Payment module (PaymentService::createPayment()), Razorpay SDK

## Section 6: Workflows

### Workflow 1: Fee Payment
**Trigger:** Student clicks "Pay Now" on an invoice | **End States:** Payment Initiated (redirect to Razorpay), IDOR Rejected (403), Validation Failed (422)
**Actors/Swimlanes:** Student | System | Razorpay | Payment Module

```
1. [Student] Navigates to fee invoice list; clicks "Pay Now" on a Published/Overdue invoice
2. [System] Verifies invoice ownership via fee assignment chain → if fails: 404
3. [System] Renders payment page with active gateways only
4. [Student] Selects gateway and enters amount (1 ≤ amount ≤ remaining balance)
5. [Student] POSTs to proceed-payment with amount, payable_type, payable_id, gateway
6. [System] *** Server-side verifies payable_id belongs to student's fee assignment *** (P0 fix required)
7. [System] Calls PaymentService::createPayment() → receives Razorpay order ID
8. [System] Redirects to Payment module Razorpay checkout page
9. [Student] Completes card/UPI/netbanking at Razorpay
10. [Razorpay] Fires webhook to Payment module callback URL
11. [Payment Module] Updates invoice status (Partially Paid or Paid)
12. [System] Sends notification to student confirming payment
```

**Exception Path:** If Razorpay is unavailable or returns an error at step 7, the student is shown an error message; no invoice status change occurs.
**Notifications Triggered:** Step 12 — Student receives "Payment Received" notification via Notification module.

---

### Workflow 2: Online Exam Attempt
**Trigger:** Student navigates to an online exam allocation from the exam schedule or learning hub
**End States:** Submitted (normal), Timeout (auto-submit), Abandoned (explicitly left)

```
1. [Student] Views exam in schedule; clicks "Take Online Exam"
2. [System] Checks: is allocation Published? Is student targeted? Is there an existing SUBMITTED attempt? → if already submitted: redirect to result
3. [System] Renders Instructions page (time limit, question count, rules, anti-cheat notice)
4. [Student] POSTs /start
5. [System] Creates lms_exam_attempts record (status: IN_PROGRESS)
6. [System] AllocationService::allocatePaperSet() — assigns randomized paper set
7. [System] Creates initial lms_attempt_checkpoints record
8. [Student] Renders exam attempt: questions from paper set, answer controls, timer
9. [Student] Selects answer; AJAX POSTs /save-answer every answer change
10. [System] Upserts lms_exam_attempt_answers; updates checkpoint.answered_question_ids
11. [System] Auto-save heartbeat (every 60s): POSTs /checkpoint → updates checkpoint.checkpoint_data
12. [Student] Tab-switch event: JS fires /log → logs to lms_attempt_activity_logs; violation_count++
13. [Student] POSTs /submit when done (or timer expires on client)
14. [System] SubmitAttemptRequest validates; updates attempt status = SUBMITTED
15. [System] Redirects to result page: shows score (MCQ auto-evaluated) or "Evaluation Pending"
```

**Exception Path (Browser Crash):** On reconnect, student navigates back to `/online-exam/{id}/attempt`; system loads checkpoint JSON and restores question position.
**Exception Path (Timeout):** `TimeoutStaleAttempts` command detects IN_PROGRESS attempt past time limit; transitions to TIMEOUT; student sees auto-submitted result on next visit.

### Workflow 3: Leave Application
**Trigger:** Student clicks "Apply for Leave" from the services menu
**End States:** Pending (submitted), Approved, Rejected, Cancelled (by student)

```
1. [Student] Navigates to /apply-leave; views existing applications and their statuses
2. [Student] Clicks "Apply New Leave"; fills form (type, start date, end date, reason, optional attachment)
3. [System] StoreLeaveApplicationRequest validates: start_date >= today, end_date >= start_date, reason non-empty
4. [System] Creates leave application record with status: Pending
5. [School Admin] Reviews and approves/rejects via admin backend (out of portal scope)
6. [System] Sends status-change notification to student
7. [Student] Views updated status on /apply-leave list and /apply-leave/{id} detail
8. [Student] Can add remark messages on the detail page; can cancel a Pending application
```

**Exception Path:** If leave dates overlap with an existing leave application, validation error is shown.
**Notifications Triggered:** Step 6 — Student receives "Leave Application Status Updated" notification.

### Workflow 4: Complaint Submission
**Trigger:** Student clicks "Raise a Complaint" from the support menu
**End States:** Submitted

```
1. [Student] Navigates to /complaint/create
2. [System] Loads: complaint categories (active), target types, complainant types from dropdown master by key
3. [Student] Selects category → AJAX: /complaint/ajax/subcategories/{cat} loads subcategories
4. [Student] Fills form: target type, complainant type, description, optional attachment
5. [Student] POSTs /complaint
6. [System] Validates via StoreComplaintRequest; forces complainant_user_id = Auth::id()
7. [System] Creates complaint record; applies Complaint module routing rules
8. [Student] Redirected to /complaint list with success message
```

**Exception Path:** Attachment exceeds 5 MB → validation error; form is shown again with the error message.
