## Section 1 — Module Overview

### 1.1 Purpose

The Syllabus module is the **academic content management backbone** of Prime-AI. It organises curriculum into a hierarchy of Lessons → Topics (configurable depth up to level 9), maps curriculum content to NEP 2020 competencies and Bloom's Taxonomy, plans and tracks syllabus delivery progress by teacher, and automatically controls when students can access study materials (homework, quizzes, and quests) as their teacher completes each topic.

The module directly powers the Question Bank, LMS-Exam, LMS-Quiz, LMS-Homework, LMS-Quests, HPC, and Recommendation modules by supplying the topic-competency-taxonomy graph that governs question selection, assessment quality, and personalised learning interventions.

### 1.2 Business Value

- Reduces curriculum planning effort by 60–70% through structured lesson/topic master templates and bulk import
- Ensures CBSE / ICSE / NEP 2020 compliance by linking every topic to Bloom levels and NCF framework codes
- Prevents assessment-before-teaching by gatekeeping LMS quizzes and homework behind topic completion
- Provides Principal/HOD with real-time visibility into which classes are on-track, delayed, or at risk
- Enables cross-year curriculum continuity via immutable `analytics_code` on every topic

### 1.3 Scope

**In Scope:**
- Lesson and topic hierarchy (create, edit, order, import, archive)
- Competency framework with NEP/NCF alignment tags
- Bloom's Taxonomy, Cognitive Skills, Question Types, Complexity Levels (assessment reference data)
- Syllabus schedule: period allocation, lesson sequencing, date planning, auto-scheduling
- Schedule lock — freeze individual topic schedules from re-dating
- LMS resource release: manual teacher toggle + automated background cron
- Performance categories and grade division masters for marksheet/HPC
- Study notes (upload notes files to lessons and topics)
- Coverage analytics: real-time dashboard, progress tracker, coverage audit, resource matrix, planning accuracy

**Out of Scope:**
- Student portal views (read-only consumption; delivered by StudentPortal module)
- Parent portal syllabus views (delivered by ParentPortal module)
- Lesson version control for system-defined national curriculum content (DDL table exists; implementation pending)
- Study material video/PDF uploads via media library (StudyMaterial model exists; controller/routes not yet built)
- API endpoints for mobile/external consumption

### 1.4 Terminology

| Term | Definition |
|------|-----------|
| Lesson | A chapter or unit of study, the top-level curriculum unit under a Class + Subject + Textbook combination |
| Topic | A sub-unit of a lesson; self-referential tree (level 0 = root Topic, level 1 = Sub-Topic, level 2 = Mini-Topic, etc.) |
| Hierarchy Depth | Configurable per school via Topic Level Types; up to 9 levels (Topic → Sub-Topic → Mini-Topic → Micro-Topic → Nano-Topic…) |
| Materialized Path | A stored string `/1/5/23/` on each topic recording all ancestor IDs, enabling efficient subtree queries without recursion |
| Competency | A measurable skill or knowledge element aligned to NEP 2020 and National Curriculum Framework (NCF) |
| Bloom's Taxonomy | Six cognitive learning levels: Remember (1), Understand (2), Apply (3), Analyse (4), Evaluate (5), Create (6) |
| LOT / HOT | Lower Order Thinking (Bloom levels 1–3) / Higher Order Thinking (Bloom levels 4–6) |
| Syllabus Coverage | Percentage of scheduled topic entries marked as Released in the current academic session |
| Schedule Lock | A per-row flag preventing a scheduled topic's dates from being changed by sequencing or auto-scheduling operations |
| Topic Release | The act of making a topic's linked homework, quiz, or quest visible and accessible to students |
| Performance Category | A score band (e.g., TOPPER = 90–100%) with an AI-recommended intervention action |
| Grade Division | A pass classification system — GRADE (A+/A/B) or DIVISION (First/Second/Third) — applied per board and class group |
| Analytics Code | An immutable unique identifier set on a topic at creation, stable across academic years for longitudinal analytics |
| Period Allocation | A per-day/per-week limit on how many teaching periods are available for a class+subject combination |
| LMS Resource Release | Automatic synchronisation of homework/quiz/quest visibility triggered by teacher completion or scheduled cron |

## Section 3 — Functional Requirements

### REQ-SLB-001: Lesson Management
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]
**Status:** Implemented — ~90%

**Description:** The system allows authorised users to create, edit, reorder, archive, and restore Lessons within the scope of an Academic Session, Class, Subject, and Textbook. Each lesson represents one chapter of the curriculum.

**Actors:** Initiates: School Admin, Academic Coordinator, Subject Teacher | Views: Class Teacher

**Business Rules:** BR-SLB-001 (code uniqueness), BR-SLB-009 (book reference mandatory), BR-SLB-010 (system-defined locks)

**Acceptance Criteria:**
- A lesson can be created only when an Academic Session, Class, Subject, and Textbook are selected
- The system auto-generates the lesson code as `<CLASS_CODE>_<SUBJECT_CODE>_L<NN>` and enforces global uniqueness
- Lessons can be drag-and-drop reordered; the ordinal is unique per class+subject
- Soft-deleted lessons appear in a Trash view and can be restored or permanently removed
- Toggling a lesson to inactive hides it from student and parent views without deleting it
- A two-step bulk import (validate → commit) processes up to 500 lessons per batch with per-row error reporting

**Integration:** Depends on SchoolSetup (classes, subjects, sections) and SyllabusBooks (textbook reference)

**Enhancement Notes:** ENH-SLB-001 (lesson version control for system-defined national curriculum)

### REQ-SLB-002: Topic Hierarchy Management
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY][CONFIGURATION]
**Status:** Implemented — ~85% (destroy() uses forceDelete — P0 bug)

**Description:** The system manages a configurable multi-level topic tree under each lesson. Each school can name the levels (Topic, Sub-Topic, Mini-Topic, etc.) and define up to 9 depth levels. Topics use a materialized path for efficient subtree queries.

**Actors:** Initiates: School Admin, Academic Coordinator, Subject Teacher

**Business Rules:** BR-SLB-002, BR-SLB-003, BR-SLB-005, BR-SLB-012, BR-SLB-014, BR-SLB-020, BR-SLB-024

**Acceptance Criteria:**
- Level-0 topics must have no parent; level N topics must have a parent at level N-1 in the same lesson
- Changing a topic's level when it has children returns a business error
- Force-deleting a topic linked to active quizzes is blocked; soft-delete is always permitted
- After fix: destroy() must call delete() (soft-delete), not forceDelete()
- Drag-and-drop tree reordering persists parent relationships and ordinals atomically
- `analytics_code` is set once at creation and never changes
- Bulk import follows the same two-step validate-then-commit pattern as lessons

**Enhancement Notes:** ENH-SLB-003 (rename Competencie → Competency has no bearing here; separate topic)

### REQ-SLB-006: Syllabus Schedule & Delivery Tracking
**Priority:** Core (P0) | **Tags:** [WORKFLOW][DATA_ENTRY]
**Status:** Implemented — ~85%

**Description:** Teachers and coordinators assign topics to date ranges and periods. As topics are taught, they are marked as Released (active), which records delivery and triggers downstream LMS resource release. The schedule supports per-section, per-academic-session, and per-subject scoping.

**Business Rules:** BR-SLB-016 (period limits), BR-SLB-019 (coverage formula), BR-SLB-021 (mark complete)

**Acceptance Criteria:**
- A schedule entry requires Academic Session, Class, Section, Subject, Lesson, and Topic
- Planned periods are validated against daily and weekly allocation limits drawn from the Periods Allocation table
- Marking a schedule entry as Complete (is_active = 1) records the delivering teacher
- Coverage percentage is computed as: (entries with is_active = 1) ÷ (total entries for the scope) × 100
- Entries can be soft-deleted, restored, and force-deleted independently
- The schedule grid is filterable by Class Section, Subject, and Academic Session

**Note:** V2 specified coverage using `taught_by_teacher_id` and `can_use_for_syllabus_status`. The implemented formula uses `is_active` as the release/completion proxy. This divergence is documented as GAP-SLB-COV-001. [inferred: the intent is the same — topics marked taught are considered released]

**Priority:** Core (P0) | **Tags:** [WORKFLOW]
**Status:** Implemented — ~90% (new feature, June 27 2026)

**Description:** Authorised users can lock individual schedule entries to freeze their date ranges. Locked entries are skipped by save-scheduling and auto-schedule operations, preserving confirmed academic plans while allowing surrounding entries to be adjusted.

**Business Rules:** BR-SLB-017

**Acceptance Criteria:**
- Any schedule entry can be toggled locked/unlocked by users with lesson-update permission
- Locked entries display a visual lock indicator in the scheduling table
- Save Scheduling silently skips locked entries (no error; remaining entries still save)
- Auto-Schedule calculates around locked entries, preserving their existing date range
- Lock state persists across sessions; is_locked flag is stored on the schedule record

### REQ-SLB-008: Lesson Sequencing & Period Allocation
**Priority:** Core (P0) | **Tags:** [WORKFLOW][CONFIGURATION]
**Status:** Implemented — ~85% (new feature since V2)

**Description:** Before date-planning, teachers arrange topics into teaching sequence (ordinal order) and assign planned period counts. The system validates that planned periods per topic do not exceed the daily allocation limit and that total periods do not exceed the weekly allocation limit for the class+subject combination.

**Business Rules:** BR-SLB-016

**Acceptance Criteria:**
- Drag-and-drop reordering of topics in the Lesson Sequencing tab persists ordinals atomically
- Each topic row carries planned_periods (decimal) and priority (HIGH/MEDIUM/LOW)
- System checks planned_periods per row against the daily limit; rejects if exceeded with a clear message
- System checks total planned_periods across all rows against the weekly limit; rejects if exceeded
- If no schedule entries exist yet, the sequencing tab is pre-populated from the topic master (first-time build)
- Planned periods are stored as DECIMAL to support fractional period allocation

### REQ-SLB-009: Auto-Scheduling
**Priority:** Standard (P1) | **Tags:** [WORKFLOW]
**Status:** Implemented — ~80% (new feature since V2)

**Description:** The system calculates start and end dates for each topic in the teaching sequence based on a user-supplied start date and the periods-per-day allocation for the class+subject. Locked entries retain their existing dates; all other entries receive computed dates.

**Acceptance Criteria:**
- User specifies a start date; system distributes topics across working days based on periods-per-day
- Topics with planned_periods = 0 are skipped (no dates assigned)
- Locked schedule entries are returned as-is (their existing dates are preserved)
- Result is returned to the browser as JSON; the user reviews and saves explicitly

### REQ-SLB-010: LMS Resource Release
**Priority:** Core (P0) | **Tags:** [WORKFLOW][SCHEDULED][NOTIFICATION]
**Status:** Implemented — ~75% (new feature since V2)

**Description:** When a topic is marked as taught (Released), the system makes the associated LMS homework, quiz, or quest visible to students in that class section. Release operates at two modes: (1) Manual — teacher toggles a topic release switch; (2) Automated Cron — a nightly background job iterates all tenants and syncs release state based on schedule activity flags.

The release level (which hierarchy level triggers release) is configurable per resource type: homework, quiz, and quest can each be configured to release at Topic, Sub-Topic, Mini-Topic, Micro-Topic, or Nano-Topic level — but each must use a different level (no two resource types can share the same level).

**Business Rules:** BR-SLB-018 (unique release levels), BR-SLB-022 (section-level granularity)

**Acceptance Criteria:**
- Three configurable release levels: Homework Release Level, Quiz Release Level, Quest Release Level
- Each must be set to a different hierarchy level; the system prevents duplicate assignments
- Manual release: toggling a topic's release status in the Topic Release Control tab immediately syncs homework/quiz/quest visibility for that topic's class section
- Automated cron (tenant:syllabus:release-resources) runs across all tenants, reads config, and syncs all active schedule entries
- When a schedule entry becomes inactive (is_active = 0), linked LMS resources are automatically deactivated
- Cron logs processing counts per tenant; errors are caught per-tenant without stopping the batch

**Integration:** LmsHomework (HomeworkAssignment.is_released), LmsQuiz (QuizAllocation.is_active), LmsQuests (QuestAllocation.is_active)

## Section 6 — Workflows

### Workflow 1: Curriculum Setup (Annual — Academic Coordinator)
**Trigger:** New academic session starts | **End State:** Schedule published for all class sections

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Admin | Configures topic level type names for the school | System saves level configurations |
| 2 | Coordinator | Creates lessons for each class + subject + textbook | System auto-generates lesson codes |
| 3 | Teacher | Creates root topics (level 0) under each lesson | System stores with materialized path |
| 4 | Teacher | Adds sub-topics (level 1+) under each root topic | System validates parent-level relationship |
| 5 | Teacher | Maps competencies and Bloom levels to assessable topics | System stores weightage and primary flags |
| 6 | Coordinator | Opens Lesson Sequencing tab; arranges topics in teaching order; sets planned periods | System validates period limits |
| 7 | Coordinator | Opens Lesson Date Planning tab; runs Auto-Schedule from a start date | System distributes topics across working days |
| 8 | Coordinator | Reviews and adjusts dates; locks confirmed entries | System marks is_locked = 1 on locked rows |
| 9 | Coordinator | Saves scheduling | System writes dates and teacher assignments |
| **Exception:** | | Period limit exceeded during sequencing | System returns specific validation error; user reduces planned periods before saving |

**Notifications Triggered:** None in current implementation [ENH: notify teachers when schedule is published]

### Workflow 2: Topic Delivery and Release (Daily — Subject Teacher)
**Trigger:** Teacher finishes teaching a topic in class | **End State:** Topic released; LMS resources visible to students

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | Teacher | Opens Topic Release Control tab; selects Class Section and Subject | System loads release control view filtered by section |
| 2 | Teacher | Finds the taught topic row; toggles release switch from Locked to Released | System identifies linked homework/quiz/quest for the topic at the configured level |
| 3 | System | Calls TopicReleaseControlService to sync homework/quiz/quest visibility | LMS resources marked is_released / is_active = 1 for the class section |
| 4 | System | Schedule entry marked is_active = 1 | Coverage percentage updated in real-time |
| **Exception:** | | Topic has no linked LMS resources at the configured level | System marks topic released; logs that no resources were found (no error to user) |

### Workflow 3: Automated Nightly Resource Release (System Cron)
**Trigger:** Nightly schedule (tenant:syllabus:release-resources) | **End State:** All tenant LMS resources synced to schedule state

| Step | Actor | Action | System Response |
|------|-------|--------|-----------------|
| 1 | System | Iterates all tenants | One iteration per tenant |
| 2 | System | Initialises tenancy context for tenant | Reads homework/quiz/quest release level settings from school config |
| 3 | System | Loads all SyllabusSchedule entries with their level types | Processes each schedule entry |
| 4 | System | For each active entry (is_active = 1) at the configured level | Calls syncHomeworkPublic, syncQuizPublic, syncQuestPublic with is_public = true |
| 5 | System | For each inactive entry (is_active = 0) at the configured level | Deactivates linked LMS resources |
| 6 | System | Ends tenancy context; logs processing count | Moves to next tenant |
| **Exception:** | | Any exception per tenant | Error logged per tenant; batch continues for remaining tenants |
