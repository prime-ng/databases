## Section 1 — Module Overview

### 1.1 Purpose
The Template Management module is the platform-wide visual layout engine for Prime-AI. It gives school administrators the tools to design, configure, and assign print-ready document layouts — marksheets, ID cards, fee receipts, admit cards, and certificates — and exposes a service interface that all other modules call to resolve the correct layout, substitute real data into placeholders, and produce PDF output.

### 1.2 Business Value
Centralising document design in a single engine eliminates redundant layout logic across modules, ensures consistent school branding, and allows a school to switch to a new marksheet or ID card design by activating a new template — without any code change or redeployment.

### 1.3 Scope

**In scope:**
- Template category and purpose configuration
- Visual template design (HTML/canvas) and merge-placeholder variable management
- Scope-based assignment of templates to academic sessions, classes, and class groups
- Runtime resolution of the correct template for a given purpose, session, and class
- Placeholder substitution (text, image, and rich-HTML output types)
- Loop block rendering for repeating rows (e.g., subject tables in a marksheet)
- PDF generation via the layout engine service
- Background branding image upload
- Sample preview during design

**Out of scope:**
- The actual content of documents (marks, attendance, fee totals — these belong to consuming modules)
- WYSIWYG pixel-perfect PDF-builder tooling (canvas is JSON-only; HTML/CSS layout is directly authored)
- Email delivery of generated PDFs (Notification module responsibility)
- Shared template libraries across schools (each school's database is fully isolated)

### 1.4 Terminology

| Business Term | Definition |
|---|---|
| Template Category | A label grouping layouts by document kind (e.g., Marksheet, ID Card, Fee Receipt) |
| Template Purpose | A functional code identifying why a template is used (e.g., MARKSHEET_PRINT) plus its scope rule (Class-Scoped or School-Wide) |
| Layout / Template Design | The HTML/CSS document structure with embedded placeholders, saved as Draft or Active |
| Placeholder / Merge Field | A named marker in the layout (e.g., `{{student_name}}`) replaced at render time with real data |
| Automated Variable | A placeholder whose value the engine fetches from a configured database table and column at render time |
| Manual Variable | A placeholder whose value the requesting module must supply at render time |
| Canvas JSON | A positional data structure recording element coordinates for the visual editor |
| Scope Assignment | A rule linking a layout to a purpose, academic session, and scope target (class, class group, or school-wide) |
| Class Group | A named collection of classes (e.g., "Primary School") used for group-level template assignment |
| Resolution Chain | The priority order the engine follows to find the best-matching scope assignment |
| School-Wide Fallback | An assignment specifying no class or group, acting as the default for all classes |
| Draft State | A saved layout not yet eligible for rendering — activation requires at least one mapped variable |
| Active State | A layout approved for rendering and eligible for scope assignment |
| System Purpose | A seeded purpose record whose code and scope type are locked and cannot be modified or deleted |
| Data Provider | A module-supplied service the engine calls to fetch bulk data (e.g., marks, fee details) before variable substitution |

## Section 3 — Functional Requirements

### 3.1 REQ-TMP-001 — Template Category Management
**Priority:** Core (P0) | **Tags:** [CONFIGURATION]

School Administrators create, maintain, and retire visual categories grouping layout designs by document type. Six categories are installed at setup (Marksheet, ID Card, Fee Receipt, Admit Card, Certificate, Standard Timetable) and are protected from deletion. Administrators may add custom categories for new document types.

**Actors:** Initiates — School Administrator; Processes — System validates uniqueness and deletion eligibility, locks seeded records; Views — School Administrator, Principal.

**Business Rules:** BR-TMP-003, BR-TMP-004, BR-TMP-005

**Acceptance Criteria:**
1. A new category with a unique name and optional description can be created and appears active. (YES/NO)
2. Creating a category with a name matching an existing one (case-insensitive) returns a validation error. (YES/NO)
3. Deactivating a category hides it from template-creation dropdowns but does not remove its templates. (YES/NO)
4. Soft-deleting a seeded category is blocked with an appropriate error message. (YES/NO)
5. Soft-deleting a custom category that has any templates (active or trashed) is blocked. (YES/NO)
6. A custom category with no templates can be soft-deleted and later restored. (YES/NO)
7. Hard-deleting a seeded or in-use category is blocked. (YES/NO)

**Integration:** Template Variable Registry (variables scoped per category); Visual Template Designer (category selector).

### 3.2 REQ-TMP-002 — Template Purpose Registry
**Priority:** Core (P0) | **Tags:** [CONFIGURATION]

School Administrators maintain a registry of functional output purposes. Each purpose carries a unique machine code and specifies whether its layouts target specific classes (Class-Scoped) or the whole school (School-Wide). Six system purposes are installed at setup and are fully protected. Custom purposes may be registered for new document workflows.

**Actors:** Initiates — School Administrator; Processes — System validates code uniqueness, enforces system-record protection, cascades deactivation on soft-delete; Views — School Administrator, Principal.

**Business Rules:** BR-TMP-006, BR-TMP-007, BR-TMP-008

**Acceptance Criteria:**
1. A custom purpose with a unique code, scope type, and display order can be created. (YES/NO)
2. Creating a purpose with a code that already exists returns a validation error. (YES/NO)
3. Attempting to change the code or scope type of a system purpose is rejected. (YES/NO)
4. Soft-deleting or hard-deleting a system purpose is rejected. (YES/NO)
5. Soft-deleting a custom purpose marks all related scope assignments inactive. (YES/NO)
6. Restoring a soft-deleted purpose does not automatically re-activate its cascaded assignments. (YES/NO)

**Integration:** Template Scope Assignment (purpose drives scope eligibility); Template Engine (purpose code identifies which assignment to fetch); sys_dropdowns (scope type lookup source).

### 3.3 REQ-TMP-003 — Template Variable Master Registry
**Priority:** Core (P0) | **Tags:** [CONFIGURATION]

School Administrators maintain a central register of all merge placeholders. Each placeholder is linked to one template category, carries a unique name per category, and is configured in Automated Mode (engine fetches value from a specified source table and column) or Manual Mode (calling module supplies the value). Common placeholders (student name, roll number, school name, logo) are seeded.

**Actors:** Initiates — School Administrator; Processes — System validates naming format, uniqueness, and mapping completeness; cascade-removes junction records on delete; Views — School Administrator, Principal, variable picker in canvas editor.

**Business Rules:** BR-TMP-009, BR-TMP-010, BR-TMP-011, BR-TMP-021

**Acceptance Criteria:**
1. A new automated variable with valid name, category, source table, and source column can be created. (YES/NO)
2. A new manual variable with valid name and category but no database mapping can be created. (YES/NO)
3. Submitting a variable with source table but no source column (or vice versa) is rejected. (YES/NO)
4. A variable name with uppercase letters, spaces, or characters other than underscore is rejected. (YES/NO)
5. Submitting a variable name already used in the same category is rejected. (YES/NO)
6. Soft-deleting a variable removes all its template-variable junction records. (YES/NO)
7. Toggling a variable to inactive hides it from the canvas variable picker. (YES/NO)

**Integration:** Visual Template Designer (variable picker); Template Engine (reads configuration and resolves values at render time).

### 3.4 REQ-TMP-004 — Visual Template Designer
**Priority:** Core (P0) | **Tags:** [DATA_ENTRY]

The system provides a design workspace where School Administrators and the Principal author or paste an HTML/CSS document layout, assign a unique machine code and display name, select a template category, and optionally embed a branding background image. Element coordinates can be recorded in canvas JSON for visual editing. New templates start in Draft state and can only be activated after at least one merge variable is mapped.

**Actors:** Initiates — School Administrator, Principal; Processes — System normalises HTML, validates code uniqueness and activation prerequisites, syncs mapped variables, logs the action; Views — School Administrator, Principal.

**Business Rules:** BR-TMP-001, BR-TMP-002, BR-TMP-016, BR-TMP-017, BR-TMP-018

**Acceptance Criteria:**
1. A template with a unique code, name, and category can be saved in Draft state with no mapped variables. (YES/NO)
2. Attempting to activate a template with no mapped variables is rejected with a clear message. (YES/NO)
3. Submitting a template with a duplicate code is rejected. (YES/NO)
4. Soft-deleting a template marks all its scope assignments inactive. (YES/NO)
5. Restoring a soft-deleted template does not automatically re-activate its scope assignments. (YES/NO)
6. Hard-deleting a template that has active scope assignments is rejected. (YES/NO)
7. A template with no active assignments can be hard-deleted after soft-deletion. (YES/NO)

**Integration:** Variable-to-Template Mapping (REQ-TMP-005); Background Image Upload (REQ-TMP-007); Template Engine (consumes html_content for rendering).

### 3.5 REQ-TMP-005 — Variable-to-Template Mapping
**Priority:** Core (P0) | **Tags:** [CONFIGURATION]

During template design, School Administrators select registered merge placeholders from the variable registry and link them to the current layout. Each link specifies a display order and an optional default value used when neither the database nor the calling module supplies a value.

**Actors:** Initiates — School Administrator; Processes — System synchronises junction records, preserving display order; Views — School Administrator.

**Business Rules:** BR-TMP-001 (mapping count gates activation), BR-TMP-011 (variable delete cascades junctions)

**Acceptance Criteria:**
1. Selecting and saving variables during template creation creates one junction record per variable. (YES/NO)
2. Removing a variable during edit deletes its junction record. (YES/NO)
3. Display order is preserved and reflected in the rendering sequence. (YES/NO)
4. A default value on a junction record is used when no data source returns a value. (YES/NO)
5. Deleting a variable from the master registry removes all its junction records across all templates. (YES/NO)

**Integration:** Visual Template Designer (REQ-TMP-004); Template Engine variable substitution (REQ-TMP-009).

### 3.6 REQ-TMP-006 — Template Scope Assignment
**Priority:** Core (P0) | **Tags:** [CONFIGURATION]

School Administrators link an active template to a purpose for a given academic session at one of three scope levels: a specific class (highest priority), a class group (second priority), or school-wide (fallback). The combination of purpose, session, and scope target must be unique. School-Wide purposes cannot have a class or class group specified.

**Actors:** Initiates — School Administrator; Processes — System validates mutual exclusivity, scope-hash uniqueness, and purpose-scope compatibility; logs the action; Views — School Administrator, Principal.

**Business Rules:** BR-TMP-012, BR-TMP-013, BR-TMP-014

**Acceptance Criteria:**
1. An assignment for a specific class, purpose, and session creates the record with the correct scope identifier. (YES/NO)
2. A second assignment with identical purpose, session, and class is rejected as a duplicate scope. (YES/NO)
3. Submitting an assignment with both class and class group set is rejected with a validation error. (YES/NO)
4. Submitting an assignment for a School-Wide purpose that specifies a class or group is rejected. (YES/NO)
5. Toggling an assignment to inactive removes it from the resolution pool without deleting the record. (YES/NO)
6. Soft-deleting a template cascades its assignments to inactive status. (YES/NO)

**Integration:** SchoolSetup (academic sessions, classes); MarksheetGeneration (class groups); Purpose Registry (REQ-TMP-002); Template Engine scope resolution (REQ-TMP-008).

4. The uploaded image renders as the canvas background in the preview. (YES/NO)

**Integration:** Template Designer (REQ-TMP-004); tenant file storage (isolated per school via FilesystemTenancyBootstrapper).

### 3.8 REQ-TMP-008 — Template Engine — Scope Resolution
**Priority:** Core (P0) | **Tags:** [INTEGRATION]

When a consuming module requests a rendered document, the Template Engine resolves which layout to use following a three-step priority chain: (1) assignment matching the exact class, (2) assignment matching a class group containing the requested class, (3) school-wide fallback assignment. If no eligible active assignment exists at any step, the engine raises a structured exception. Only active templates linked to active assignments are eligible.

**Actors:** Initiates — System Engine (called by consuming module); Processes — System queries assignments in priority order, raises a structured exception on no match.

**Business Rules:** BR-TMP-015

**Acceptance Criteria:**
1. A request with a direct class assignment resolves to that class template — not the school-wide one. (YES/NO)
2. A request with no direct class assignment but a class group assignment resolves to the group template. (YES/NO)
3. A request with no class or group assignment resolves to the school-wide fallback. (YES/NO)
4. A request matching no assignment at any level raises a structured exception (not a PHP error or null return). (YES/NO)
5. Inactive templates and inactive assignments are excluded from resolution. (YES/NO)

**Integration:** All consuming modules (MarksheetGeneration, Certificate, StudentFee, StudentProfile, LmsExam); Scope Assignment store (REQ-TMP-006); MarksheetGeneration class group data.

### 3.9 REQ-TMP-009 — Template Engine — Variable Substitution
**Priority:** Core (P0) | **Tags:** [INTEGRATION]

After the layout is selected, the engine replaces all placeholder markers in the HTML with resolved values. The engine calls the registered Data Provider (if any) first, then merges in caller-supplied values (caller wins on conflict). Each active mapped placeholder is resolved — automated variables fetch from their configured database table and column; manual variables use the merged payload. Unresolved placeholders fall back to the junction default, then to an empty string. Values are formatted by declared output type before substitution.

**Actors:** Initiates — System Engine; Processes — System merges data, resolves each placeholder, formats output by type, returns rendered HTML.

**Business Rules:** BR-TMP-019, BR-TMP-020

**Acceptance Criteria:**
1. A placeholder with an automated database mapping resolves to the correct field value. (YES/NO)
2. A placeholder with no database mapping resolves to the calling module's supplied value. (YES/NO)
3. When provider and caller both supply a value for the same key, the caller's value is used. (YES/NO)
4. A placeholder with no value from any source resolves to the junction default (or empty string). (YES/NO)
5. Text-type variables are HTML-escaped in the output. (YES/NO)
6. Image-type variables produce an HTML image element. (YES/NO)
7. Rich-HTML-type variables render as trusted unescaped HTML. (YES/NO)
8. An unrecognised placeholder in the HTML with no mapped variable produces an empty string (not an error). (YES/NO)

**Integration:** DataProviderInterface implementations (consuming modules); tenant database auto-resolution tables.

---

### 3.10 REQ-TMP-010 — Template Engine — Loop Block Rendering
**Priority:** Standard (P1) | **Tags:** [INTEGRATION]

The engine supports repeating sections (e.g., one row per subject) using named LOOP/ENDLOOP markers in the HTML. The engine repeats the inner block for each row item in a caller-supplied named array. Legacy marker formats from earlier template versions are automatically translated. An empty or absent data array produces empty output without raising an error.

**Actors:** Initiates — System Engine; Processes — Translates legacy markers, expands loop blocks, substitutes per-row variables.

**Acceptance Criteria:**
1. A loop block with three data rows expands into three repetitions. (YES/NO)
2. A loop block with no matching data array renders as empty string. (YES/NO)
3. Legacy SUBJECT_TABLE_START/END markers translate correctly before expansion. (YES/NO)
4. Nested loops are not supported (out of scope for current release). (YES/NO)

**Integration:** Template Engine rendering pipeline (REQ-TMP-009); DataProvider supplies loop arrays.

### 3.11 REQ-TMP-011 — PDF Output Generation
**Priority:** Core (P0) | **Tags:** [INTEGRATION]

Consuming modules request a PDF from the engine by supplying a purpose, context IDs (student, class, session), and optional data overrides. The engine resolves the template, renders the HTML, converts it to a PDF with configurable paper size and orientation, and returns the PDF object for the caller to stream or save.

**Actors:** Initiates — System Engine (invoked by consuming module's user-triggered action); Views — Consuming module's user (downloads or views the PDF).

**Acceptance Criteria:**
1. A PDF is returned for any purpose+class+session combination with a valid active assignment. (YES/NO)
2. Paper size and orientation are configurable per call. (YES/NO)
3. A request failing template resolution raises a structured exception (not a blank PDF). (YES/NO)
4. All placeholders and loop blocks render correctly in the PDF output. (YES/NO)

**Integration:** DomPDF library; all consuming modules.

### 3.12 REQ-TMP-012 — Sample Preview
**Priority:** Standard (P1) | **Tags:** [DASHBOARD]

From the template detail view, administrators can render a browser-based preview of the layout using synthetic data generated from the registered Data Provider's schema. The preview represents a faithful visual approximation of the final printed output without accessing or modifying real school data.

**Actors:** Initiates — School Administrator, Principal; Processes — Engine calls schema() on registered provider, builds synthetic payload, renders via renderById(); Views — School Administrator, Principal.

**Acceptance Criteria:**
1. Preview renders for a template that has a registered purpose and Data Provider. (YES/NO)
2. Preview renders for a template without a provider, showing empty-string placeholders. (YES/NO)
3. Preview does not create or modify any database records. (YES/NO)
4. Preview displays in the browser (not as a file download). (YES/NO)

**Integration:** DataProviderInterface (schema method); Template Engine renderById.

## Section 6 — Workflows

### Workflow 1: Create and Activate a Template Design
**Trigger:** School Administrator initiates "Add Template."
**End State:** Template is Active and eligible for scope assignment.
**Actors:** School Administrator | System

1. Administrator opens the Template Designer and enters machine code, display name, and category.
2. Administrator authors the HTML/CSS layout with placeholder markers.
3. [Optional] Uses the variable picker to link registered placeholders with display order and optional defaults.
4. [Optional] Uploads a background branding image.
5. Administrator saves — system validates code uniqueness, normalises HTML, saves as Draft.
6. Administrator ensures at least one variable is mapped.
7. Administrator sets status to Active — system checks ≥1 variable mapped (BR-TMP-001).
8. Template is Active and visible in scope assignment selectors.

**Exception — duplicate code:** Validation error; user corrects and resubmits.
**Exception — activate without variables:** Blocked; user maps at least one variable first.
**Notification:** None (configuration action).

---

### Workflow 2: Template Scope Assignment
**Trigger:** School Administrator creates a scope assignment.
**End State:** One scope assignment is active and available to the engine.
**Actors:** School Administrator | System

1. Administrator selects "New Assignment."
2. Selects an Active template, purpose, and academic session.
3. Selects scope level: Specific Class, Class Group, or School-Wide.
4. [System guard] If purpose is School-Wide scope type, class/group selectors are disabled; backend rejects non-null values.
5. System computes scope identifier; checks for duplicates (BR-TMP-013).
6. If no duplicate, assignment is saved and immediately active.

**Exception — duplicate scope:** User prompted to update existing assignment.
**Exception — both class and class group submitted:** Rejected; user selects one.

---

### Workflow 3: Template Engine Render Cycle
**Trigger:** Consuming module calls the engine's render or PDF method.
**End State:** Rendered HTML string (or PDF) returned to consuming module.
**Actors:** System Engine | Consuming Module

1. Consuming module calls render(purpose, data, studentId, classId, sessionId, ...).
2. Engine calls registered Data Provider for the purpose (if any).
3. Engine merges caller data with provider data — caller wins on conflict (BR-TMP-019).
4. Engine resolves template via 3-step fallback chain (BR-TMP-015):
   - Step 1: Active assignment — purpose + session + specific class.
   - Step 2: Active assignment — purpose + session + class group containing the class.
   - Step 3: Active assignment — purpose + session + school-wide.
   - No match → raises TemplateNotFoundException.
5. Engine loads HTML content; translates legacy loop markers.
6. Engine expands loop blocks from named array data in merged payload.
7. Engine substitutes all active placeholder markers with resolved values, formatting by output type (BR-TMP-020).
8. Returns rendered HTML string.

**Exception — no assignment found:** TemplateNotFoundException; consuming module handles it.
**Exception — HTML content blank:** TemplateRenderException raised.

---

### Workflow 4: Template Soft-Delete Cascade
**Trigger:** School Administrator soft-deletes a template.
**End State:** Template in trash; related scope assignments inactive.
**Actors:** School Administrator | System

1. Administrator soft-deletes the template.
2. System soft-deletes the template record.
3. System sets all related scope assignments to inactive (BR-TMP-016).
4. Template is recoverable; restoring it does not re-activate assignments.

---

### Workflow 5: Purpose Soft-Delete Cascade
**Trigger:** School Administrator soft-deletes a custom purpose.
**End State:** Purpose in trash; related scope assignments inactive.

1. System verifies purpose is not system-protected (BR-TMP-007).
2. System soft-deletes the purpose.
3. System sets all related scope assignments to inactive (BR-TMP-008).

---

### Workflow 6: Background Image Upload
**Trigger:** School Administrator uploads a branding image.
**End State:** Image stored; path available for embedding.

1. Administrator selects JPEG or PNG ≤ 2 MB.
2. System validates type and size (BR-TMP-018).
3. System stores file in school's isolated file storage.
4. System returns the public URL and path.

**Exception — wrong type or oversized:** Rejected; administrator selects a valid file.

---

### Workflow 7: PDF Generation
**Trigger:** Consuming module calls toPdf().
**End State:** PDF object returned to caller.

1. Engine runs the full render cycle (Workflow 3).
2. Engine converts the rendered HTML to a PDF using DomPDF with specified paper size and orientation.
3. Returns the PDF object for the caller to stream or save.

**Exception — template resolution or render failure:** Exception propagated to caller.
