# Fee Log — Requirement Document

## 1. Screen Purpose & Overview

The Fee Log screen provides a read-only, immutable audit trail of all financial transactions related to student transport fees. It aggregates logs covering fee creations, collections, waivers, and reversals, allowing accountants to compile daily cash summaries and trace payment anomalies.

---

## 2. Common Business Use Cases

1. **Daily Cash Summary Audits:** An auditor reviews all transport collections recorded on a specific date to verify cash balances in the safe.
2. **UPI Reference Verification:** Searching for a transaction reference code to resolve a parent payment dispute.
3. **Transaction Audit Trail Check:** Reviewing who authorized a specific late fee waiver and when it was completed.

---

## 3. Database Schema & Data Dictionary

All fields map to the general payments log table `std_student_pay_log`:

* `id` (INT UNSIGNED): Primary Key, Auto-increment.
* `student_id` (INT UNSIGNED): FK to `std_students`. Student identifier.
* `academic_session_id` (INT UNSIGNED): FK to `sch_org_academic_sessions_jnt`. Mapped academic session.
* `module_name` (VARCHAR(50)): Module context (fixed to 'Transport' for transport records).
* `activity_type` (VARCHAR(50)): Transaction category ('Collection', 'Waiver', 'Reversal').
* `amount` (DECIMAL(10,2)): Transaction monetary amount.
* `log_date` (DATETIME): Timestamp of log entry (defaults to current system time).
* `reference_id` (INT UNSIGNED): FK to `tpt_student_fee_collection.id` (or waiver record ID).
* `reference_table` (VARCHAR(100)): Target source table (e.g., 'tpt_student_fee_collection').
* `description` (VARCHAR(512)): Description of transaction details (e.g. 'UPI payment confirmation').
* `triggered_by` (INT UNSIGNED): FK to `sys_users`. Mapped to the cashier/accountant who triggered the transaction.
* `is_system_generated` (TINYINT): 0 = Manual operator entry, 1 = Auto-generated by system processor.
* `created_at` (TIMESTAMP): Creation date-time.
* `deleted_at` (TIMESTAMP): Set for soft deletes.

---

## 4. Screen Fields & Input Rules

The screen presents a read-only auditing list grid:

| Field Name (Screen Label) | UI Control Type | Validation Rules & Constraints | Source Database Mapping |
| :--- | :--- | :--- | :--- |
| **Date Range** | Datepicker Range| Required. Filters transaction list by date. | `log_date` |
| **Activity Type** | Dropdown | Optional. Filters by `Collection`, `Waiver`, `Reversal`.| `activity_type` |
| **Search Keyword** | Text Input | Optional. Filters by Student Name or Ref ID. | Wildcard string match. |
| **Export Ledger** | Button | Downloads filtered audit grid as Excel/PDF. | Local utility generation. |

---

## 5. Business Logic & Validation Policies

### Transaction Immutability
* All entries in the payments log are strictly read-only:
  $$\text{AllowEdits} = \text{False} \quad \land \quad \text{AllowDeletes} = \text{False}$$
* Any corrective adjustments require logging a new compensation record with `activity_type = 'Reversal'` and negative balance adjustments.

## 6. Detailed Step-by-Step Manual Testing Plan

### Test Case 1: Search Ledger Logs (Happy Path)
1. Go to `/transport/fee-collection` and select the **Fee Log** tab.
2. Select Date Range: Today. Select Activity Type: `Collection`. Click search.
3. Verify that the grid displays:
   - Student Name, Session, Module (Transport), Activity (Collection), Amount, Date, Reference Table, and cashier User Name.
4. Verify that double-clicking a row displays transaction details but disables edits.

### Test Case 2: Verify Log Entry Integrity
1. Complete a transport payment of ₹1,800.00 in the Fee Collection screen.
2. Open the Fee Log screen, search for today's logs.
3. Locate the transaction in the list. Verify that the Amount is exactly `1800.00`, Activity is `Collection`, and the Triggered By column displays your username.

### Test Case 3: Reversal compensating Record Check
1. Process a transaction refund or correction.
2. Verify that a new log entry is created in `std_student_pay_log` with `activity_type = 'Reversal'`, a negative Amount `-1800.00`, and a description detailing the correction remarks.

### 2. Dusk Integration Test Code Block

```php
namespace Tests\Browser;

use Tests\DuskTestCase;
use Laravel\Dusk\Browser;
use App\Models\User;

class TransportFeeLogTest extends DuskTestCase
{
    public function testFeeLogReadOnlyAuditFilters()
    {
        $this->browse(function (Browser $browser) {
            $browser->loginAs(User::find(1))
                    ->visit('/transport/fee-collection')
                    ->click('@fee-log-tab')
                    ->waitFor('@fee-log-table')
                    
                    // Filter logs
                    ->select('activity_type', 'Collection')
                    ->type('search_query', 'Bobby')
                    ->pause(1000)
                    
                    // Assert row is read-only and displays correct value
                    ->assertSee('Transport')
                    ->assertSee('Collection')
                    ->assertSee('1800.00')
                    
                    // Trigger PDF export
                    ->click('@export-pdf-btn');
        });
    }
}
```
