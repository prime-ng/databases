# Orders — Requirements

## Parent Tab: Orders & Attendance

## What It Does
Student meal pre-order system with cutoff enforcement, payment modes, and order lifecycle tracking. Students place orders before cutoff time; kitchen sees confirmed orders for preparation.

## Tables Covered

1. `caf_orders` — Order headers
2. `caf_order_items` — Order line items with price snapshot

---

## Entity: Orders (`caf_orders`)

### Database Fields

| Field | Type | Conditions |
|---|---|---|
| `id` | INT UNSIGNED PK | Auto-increment. |
| `order_number` | VARCHAR(30) | Required. Unique. Auto-generated: `CAF-YYYY-XXXXXXXX`. |
| `student_id` | INT UNSIGNED FK → std_students | Required. |
| `meal_card_id` | INT UNSIGNED FK → caf_meal_cards | Nullable. NULL if cash/counter. ON DELETE SET NULL. |
| `order_date` | DATE | Required. Calendar date the meal is ordered for. |
| `meal_category_id` | INT UNSIGNED FK → caf_menu_categories | Required. ON DELETE RESTRICT. |
| `total_amount` | DECIMAL(10,2) | Required. Sum of all line item totals. |
| `payment_mode` | ENUM('MealCard','Cash','Counter','Subscription') | Default 'MealCard'. |
| `status` | ENUM('Pending','Confirmed','Served','Cancelled') | Default 'Confirmed'. |
| `cancelled_at` | TIMESTAMP | Nullable. |
| `cancellation_reason` | VARCHAR(255) | Nullable. |
| `notes` | TEXT | Nullable. |
| `is_active` | TINYINT(1) | Default 1. |
| `created_by` | INT UNSIGNED FK → sys_users | Nullable. |
| `created_at` / `updated_at` | TIMESTAMP | Laravel standard. |
| `deleted_at` | TIMESTAMP | Nullable. Soft delete. |

### Business Rules

#### Order Number Generation

- The order number is never entered by the user — it is automatically generated by the system in the format `CAF-YYYY-XXXXXXXX` (e.g., `CAF-2026-00000001`).
- The year is locked to the year the order is created. An 8-digit sequence number follows, starting over from 1 each year.
- A locking mechanism prevents two orders from accidentally receiving the same order number, even if placed simultaneously.

#### Student & Payment Rules

- Every order must be linked to a valid existing student.
- A meal card is required when paying with MealCard mode, optional otherwise.
- The total amount is read-only and automatically calculated as the sum of all line item totals — never entered manually.

#### Pre-Order Cutoff Rule

- By default, orders must be placed by 10:00 PM the day before the meal date.
- This cutoff time can be adjusted per meal category (e.g., breakfast may have a different cutoff than lunch).
- If a student tries to order after the cutoff has passed, the system shows: "Order cutoff time has passed for {meal category} on {order date}."
- Cutoff rules only apply to new orders — existing orders are not affected.

#### Order Date Restriction

- Orders can only be placed for today or a future date. Past dates are not allowed — the system shows "Cannot order for a past date."

#### Order Lifecycle State Machine

An order moves through the following statuses, with specific transition rules:

| Current Status | Next Status | Conditions | What Happens |
|---|---|---|---|
| Pending | Confirmed | Payment is confirmed. | Order is locked and sent to the kitchen for preparation. |
| Confirmed | Served | Must be on or after the order date. | Meal has been handed to the student. |
| Confirmed | Cancelled | Must be before the meal's start time. After that, the system shows "Cannot cancel order — meal service has already started." | The cancellation time and reason are recorded. If the order was paid by meal card, the balance is refunded. |
| Pending | Cancelled | Always allowed (payment failed or student chose to cancel). | Same actions as cancelling a confirmed order. |
| Cancelled | Any other status | Not allowed. | Once cancelled, an order cannot be changed to any other status. |

**What happens when an order is cancelled:**
1. The cancellation time is recorded automatically.
2. The cancellation reason is captured from the person cancelling the order.
3. If the payment method was 'MealCard', the full amount is refunded back to the student's meal card balance.
4. A refund transaction record is created in the meal card transaction log.
5. An activity log entry is created: "Order {order number} was cancelled. Reason: {reason}."

#### Duplicate Order Guard

- A student can place orders for different meal categories on the same day (e.g., Breakfast and Lunch separately).
- However, a student can only have **one** order per meal category per day. If they try to place a second order for the same meal on the same day, the system shows: "You already have an order for {meal category} on {order date}."

#### Deleting and Restoring an Order

- Only orders with a status of 'Pending' or 'Cancelled' can be deleted.
- Orders that are 'Confirmed' or 'Served' cannot be deleted. If someone tries, the system shows: "Cannot delete a confirmed or served order."
- When an order is deleted, it is hidden from active use but kept in the system for record-keeping.
- If an order was deleted by mistake, it can be restored. The restored order keeps the same status it had before deletion.

#### List View

- Controller: OrderController@index. Gate: `tenant.cafeteria.order.viewAny`.
- Pagination: 15 per page, sorted by `order_date DESC, created_at DESC`.
- Columns: Order Number, Student Name, Date, Meal Category, Total Amount, Payment Mode, Status (badge), Actions.
- Filters: search by order number or student name, date range, status dropdown, meal category dropdown.
- Kitchen view: separate route `cafeteria.orders.kitchen` — shows all Confirmed orders grouped by date/meal_category for kitchen prep.

## Entity: Order Items (`caf_order_items`)

### Database Fields

| Field | Type | Conditions |
|---|---|---|
| `id` | INT UNSIGNED PK | Auto-increment. |
| `order_id` | INT UNSIGNED FK → caf_orders | Required. ON DELETE CASCADE. |
| `menu_item_id` | INT UNSIGNED FK → caf_menu_items | Required. ON DELETE RESTRICT. |
| `quantity` | TINYINT UNSIGNED | Default 1. |
| `unit_price` | DECIMAL(8,2) | Required. Price snapshot at order time. |
| `line_total` | DECIMAL(10,2) | Required. `quantity × unit_price`. |
| `created_at` / `updated_at` | TIMESTAMP | Laravel standard. |

### Business Rules

- Once an order is placed, the items within it cannot be changed or edited in bulk.
- The price of each item is captured at the moment the order is placed. If the menu price changes later, existing orders are not affected.
- The line total for each item is calculated as quantity multiplied by the unit price at the time the order is created. This is stored as a fixed value (not calculated on the fly) so it can be adjusted later if needed — but any adjustment would require an audit trail.
- The same menu item cannot appear more than once in an order. If a student wants more than one of the same item, they should increase the quantity instead.
- Order items are purely transactional records — they do not have status flags, creator tracking, or soft delete.
