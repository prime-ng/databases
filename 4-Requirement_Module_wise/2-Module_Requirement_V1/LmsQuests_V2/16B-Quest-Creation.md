# Business Requirements Document (BRD)
## Module: LMS Quests
### Screen: Quest Creation (Master)

---

## 1. Executive Summary & Business Motive
### 1.1 The Core Motive
The **Quest Creation** screen is a two-step wizard designed to capture both the academic metadata (Basic Info) and the pedagogical rules (Configuration) of a practice assessment. 

### 1.2 Why is this necessary? (Business Justification)
- **Standardized vs Flexible Practice:** Dividing the form into two tabs prevents cognitive overload for the teacher. They first define "What is this test?" (Tab 1) and then "How will it behave?" (Tab 2).

---

## 2. Document Scope
- **In-Scope:** Creation, Editing, Soft Deletion, Restoration, and Force Deletion of `lms_quests`. The 2-Tab UI workflow and all 12 configuration switches.
- **Out-of-Scope:** Adding actual physical questions.

---

## 3. User Personas
1. **Teacher:** Creates a quest via the wizard, sets limits, and applies rules.

---

## 4. Detailed Functional Requirements (FR)

### FR-01: Tab 1 - Basic Information (`?tab=basic-info`)
- **Action:** Open the create page. The "Basic Information" tab is active by default.
- **Fields & Validations:**
  - **Academic Session:** Read-only (auto-populated with current session).
  - **Class:** Dropdown. Selecting a class triggers AJAX `syllabus.get-subject`.
  - **Subject:** Dropdown (populated via AJAX based on Class). Selecting a subject triggers AJAX `lms-quize.get-lessons` to load lessons internally.
  - **Quest Type:** Required. Pulled from `lms_assessment_types`.
  - **Status:** Dropdown (`DRAFT`, `PUBLISHED`, `ARCHIVED`).
  - **Quest Title:** Required text field.
  - **Description & Instructions:** Optional Textareas.
- **Interactivity:** A button labeled **"Next: Configuration"** uses JavaScript to programmatically switch the view to Tab 2 (`#quest-settings`).

### FR-02: Tab 2 - Quest Configuration (`?tab=quest-settings`)
- **Action:** Navigate to the second tab to define test rules.
- **Numerical Boundaries & Inputs:**
  - **Duration (Minutes):** Min 1, Max 600.
  - **Total Marks:** Required. Min 0, Max 999999.99.
  - **Total Questions:** Required. Min 0, Max 9999.
  - **Passing Percentage:** Required. Min 0, Max 100. Default is 33.00.
  - **Negative Marks:** Min 0, Max 10. Only positive numbers allowed in input.
  - **Maximum Attempts:** Min 1, Max 10. Default 1.
  - **Difficulty Configuration:** Dropdown pulled from `lms_difficulty_distribution_configs`.

### FR-03: The 12 Quest Features & Options (Toggle Switches)
Tab 2 contains exactly 12 critical boolean switches that define the behavior of the Quest.
- **1. Allow Multiple Attempts:** 
  - *Logic:* If toggled ON, the `max_attempts` input is enabled. If OFF, `max_attempts` is disabled and reset to 1.
- **2. Randomize Question Order:** 
  - *Logic:* If ON, questions will be shuffled randomly for each student during the attempt, ignoring the set ordinal sequence.
- **3. Show Question Marks:** 
  - *Logic:* If ON, the marks allotted for each individual question are visible to the student during the test.
- **4. Is System Generated:** 
  - *Logic:* Flags whether this quest was auto-generated by the system (AI/Auto-pick) or manually curated by a teacher.
- **5. Auto Publish Result:** 
  - *Logic:* If ON, the final grade is immediately published to the student upon submission. If OFF, it requires manual "Publish" action by the teacher from the Summary Tab.
- **6. Enforce Timer:** 
  - *Logic:* If toggled ON, the `duration_minutes` input is enabled and a countdown timer will force-submit the quest when time is up. If OFF, duration is disabled/blank.
- **7. Show Correct Answer:** 
  - *Logic:* If ON, students can see the correct answer immediately after submitting or completing the quest.
- **8. Show Explanation:** 
  - *Logic:* If ON, the detailed solution/explanation attached to the question is revealed to the student after submission.
- **9. Ignore Difficulty Configuration:** 
  - *Logic:* If toggled ON, the `difficulty_config_id` dropdown is disabled and cleared. The system will skip the Easy/Medium/Hard ratio validation when adding questions.
- **10. Only Unused Questions:** 
  - *Logic:* If ON, when adding questions in the Question Tab, the system automatically filters out any questions that have been used in previous Quests for this class.
- **11. Only Authorised Questions:** 
  - *Logic:* If ON, the system restricts the question pool to only those questions that have an "Approved" status in the Question Bank.
- **12. Quest Active:** 
  - *Logic:* Master toggle to Soft-Deactivate the quest (`is_active` boolean).

### FR-04: Backend Processing (`QuestRequest` & Controller)
- **Auto-Code Generation:** If `quest_code` is not explicitly provided, the system auto-generates it on save: `QUEST_{SESSION}_{CLASS}_{SUBJECT}_{LESSON}_{RANDOM_6_CHARS}`.
- **Form Submission Validations:** 
  - All 12 toggles are merged as booleans via `prepareForValidation()` in `QuestRequest`.

### FR-05: Protection Against Modification (Usage Check)
- **Action:** Edit, Soft-Delete, Restore, or Force Delete a Quest.
- **System Behavior (`QuestUsageCheckService`):**
  - If the Quest is linked to active `allocations`, `questions`, or `student attempts`, standard actions are **blocked** with an error to preserve data integrity.

## 5. Agile User Stories & Acceptance Criteria
#### Story 1: Configuring Toggles
**As a** Teacher,
**I want to** configure my Quest in Tab 2 with specific features,
**So that** it acts as a strict test instead of casual practice.

**Acceptance Criteria:**
- **Given** I am on the "Quest Configuration" tab, **When** I turn ON `Enforce Timer` and OFF `Show Correct Answer`, **Then** the `duration_minutes` field is enabled for me to set a 30-minute limit, and the system saves these boolean states to restrict post-test visibility.
