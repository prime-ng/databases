# Business Requirements Document (BRD)
## Module: LMS Examination
### Sub-Module: Logs & Grievance
### Screen: Tab 3: Event Log (Pending Checkpoints)

---

## 1. Executive Summary & Business Motive
### 1.1 The Core Motive
The **Event Log (Pending Checkpoints)** tab provides a live, real-time snapshot of students who are *currently* taking an online exam. It reads from the auto-save checkpoints generated by the student's browser.

### 1.2 Why is this necessary? (Business Justification)
- **Live Proctoring:** Allows the admin to see exactly where a student is in the exam (e.g., "Student is on Question 14, has answered 10, flagged 2").
- **Disaster Recovery:** If a student's PC crashes, the checkpoint data is what allows them to resume exactly where they left off. Admin visibility into this confirms that data is saving properly.

---

## 2. Document Scope
- **In-Scope:** Viewing live/pending `IN_PROGRESS` exam attempt checkpoints.
- **Out-of-Scope:** Modifying checkpoint data.

---

## 3. User Personas
1. **Exam Proctor:** Wants to see the live progress of a class currently sitting in the computer lab taking an exam.

---

## 4. Detailed Functional Requirements (FR)

### FR-01: Filtering Active Attempts
- **Action:** Filter the checkpoints.
- **UI/JS Logic:**
  - Cascading AJAX dropdowns: `Class -> Section -> Student`.
  - Only fetches records from `lms_exam_attempt_checkpoints` where the parent attempt is not yet submitted.

### FR-02: Live Progress Visualization
- **Action:** View the checkpoint metrics.
- **System Behavior:**
  - Displays the `Last Saved` timestamp (down to the second).
  - Displays the `current_question_idx` (+1 for human readability).
  - Calculates and displays the count of `answered_question_ids` array and `flagged_question_ids` array.

### FR-03: Raw Data Inspection
- **Action:** Click the Database icon in the Action column.
- **System Behavior:**
  - Triggers a JavaScript alert that stringifies the raw `checkpoint_data` JSON. This is an advanced technical feature to verify the exact state payload.

---

## 5. Agile User Stories & Acceptance Criteria

#### Story 1: Live Monitoring
**As an** Exam Proctor,
**I want to** see the checkpoint log during the 10:00 AM exam,
**So that** I know if any student's auto-save mechanism has stopped working (indicating internet loss).

**Acceptance Criteria:**
- **Given** students are taking the exam, **When** I refresh the Pending Checkpoints tab, **Then** I see the "Last Saved" timestamp updating to reflect their browser's auto-save pings.

---

## 6. Business Data Dictionary & Validations
| Field | Validation Rules |
|-------|------------------|
| **Checkpoint Arrays** | `answered_question_ids` and `flagged_question_ids` are stored as JSON arrays and counted via PHP `count()`. |

---

## 7. Exception & Error Handling Scenarios
- **Scenario:** The exam finishes and all students submit.
  - *Response:* The table becomes empty, showing: "No active/pending exam attempts found."

---

## 8. Dependency & Impact Mapping
### 8.1 Incoming Dependencies

### 8.2 Outgoing Dependencies
