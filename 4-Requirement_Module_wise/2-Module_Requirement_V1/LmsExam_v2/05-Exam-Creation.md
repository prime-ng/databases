# Business Requirements Document (BRD)
## Module: LMS Examination
### Sub-Module: Exam Creation & Allocation 
### Screen: Exam Creation (Tab 1)

---

## 1. Executive Summary & Business Motive
### 1.1 The Core Motive
The **Exam Creation** screen is the origin point for any assessment lifecycle. It acts as the parent container that houses all subsequent configurations (papers, sets, questions, allocations). Without defining the overarching "Exam Event" (e.g., *Annual Examination 2025-26*), schools cannot group subject papers logically.

### 1.2 Why is this necessary? (Business Justification)
- **Centralized Administration:** Schools need to define the start and end dates for a major exam period globally. Instead of setting dates individually for 50 papers, the parent Exam dictates the boundary.
- **Reporting Aggregation:** When report cards are generated, they aggregate marks based on this specific `lms_exams` record. 
- **Automated Result Publishing:** The module introduces automated result publishing logic (`IMMEDIATE`, `SCHEDULED`, `MANUAL`), removing the burden from teachers to manually release results at midnight.

---

## 2. Document Scope
- **In-Scope:** Creation, modification, searching, and archiving of the parent Exam records. UI behavior of Result Publication triggers and schedule datetime inputs.
- **Out-of-Scope:** Creating subject-specific papers or allocating students.

---

## 3. User Personas
1. **Examination Head:** Sets up the main exam events at the start of the term.
2. **System Administrator:** Oversees the active exams and toggles statuses if workflows get stuck.

---

## 4. Detailed Functional Requirements (FR)

### FR-01: Initialization & Core Metadata
- **Action:** An authorized user fills out the Exam creation form.
- **Fields Required:**
  - **Exam Title:** E.g., `First Terminal Examination 2024`.
  - **Academic Session:** Auto-populated, read-only.
  - **Class:** Dropdown to select the target class.
  - **Exam Type:** Selects from `lms_exam_types` (e.g., Term Exam).
  - **Exam Code:** Read-only (Auto-generated by backend).
  - **Date Boundaries:** `start_date` and `end_date`.

### FR-02: Status & Grading Configuration
- **Fields Required:**
  - **Exam Status Event:** Pulled from `lms_exam_status_events` (defaults to DRAFT).
  - **Grading Schema:** Pulled from `slb_grade_division_master` (e.g., CBSE 100-point scale).

### FR-03: Result Publication Logic (JavaScript UI Dynamics)
- **Action:** The user configures how results should be released to students.
- **System Behavior (`create.blade.php`):**
  - **Result Published Dropdown:** Contains three options: `MANUAL`, `IMMEDIATE`, and `SCHEDULED`.
  - **If SCHEDULED is selected:** JavaScript dynamically reveals the `scheduled_result_at` datetime input field and marks it strictly as `required`.
  - **If MANUAL is selected:** JavaScript reveals a separate boolean toggle switch (`is_result_published` labeled "Publish Result Now"). The `scheduled_result_at` field is hidden and cleared.
  - **If IMMEDIATE is selected:** Both the datetime field and the toggle switch are hidden. The toggle is checked internally by the system.

### FR-04: Editing Constraints
- **Action:** Modifying an exam.
- **Critical Business Constraint:** If the exam has live student attempts, modifying the `Grading Schema` or `Exam Type` is strictly blocked by the backend service to prevent altering past calculations.

## 5. Agile User Stories & Acceptance Criteria

#### Story 1: Scheduling Result Publication
**As an** Examination Head,
**I want to** set the result publication to `SCHEDULED` for `2025-03-31 08:00 AM`,
**So that** I don't have to wake up early to manually click a button to release report cards.

**Acceptance Criteria:**
- **Given** I select "Scheduled" in the dropdown, **When** I do so, **Then** the "Scheduled Result Time" input field instantly appears. **And** if I try to submit without filling it, the form prevents submission and focuses on the field.

---

## 6. Business Data Dictionary & Validations

| Field | Validation Rules |
|-------|------------------|
| **Session / Class / Type** | Must enforce unique composite `(academic_session_id, class_id, exam_type_id)`. Cannot create duplicate exams for the same Class and Session. |
| **Dates** | `end_date` MUST be `after_or_equal:start_date`. |
| **Result Config** | If `SCHEDULED`, `scheduled_result_at` is heavily validated on the backend. |

---

## 7. Dependency & Impact Mapping
- **Incoming Dependencies:** `glb_academic_sessions`, `sch_classes`, `lms_exam_types`, `slb_grade_division_master`.
- **Outgoing Dependencies:** `lms_exam_papers`, `lms_exam_allocations`. Deleting an Exam destroys the entire tree of papers beneath it.
