# Known Test-Failure Constraints — EVIDENCE APPENDIX (on-demand)

**This is the full rationale + evidence for each rule. It is NOT read on every run.** The always-read operative list is `05_Known_Test_Failure_Constraints.md` (the **Rule Card**). Read a rule's entry HERE only when you need its justification, an exact code snippet, or the file/line evidence behind a Rule-Card line. Rule numbers, sections (A–G), and imperatives match the Rule Card exactly — this file adds the *why* and the *Evidence:* notes.

**Provenance:** distilled from a peer test agent's hard-earned constraints, then **verified against this codebase** (`prime_ai`, `prime_testing`, consolidated DDLs) on 2026-07-09, extended by the 2026-07-14 test-quality reviews (F/G sections). See `Testing_Prompt/Phase1_Verification_Harness_Results.md` for the original evidence table. **Only verified items are stated as rules.** Two peer-agent constraints were found FALSE here and are inverted (marked ⚠️).

> Golden principle: these are guardrails against *false* test failures (tests that fail for environmental/harness reasons, not real defects). When a constraint below conflicts with what you observe in the real source at generation time, trust the source and note the discrepancy.

## A. Tenancy & test style  *(verified: H1, H10)*

1. **Follow the module's committed sibling for style AND tenancy helper.** Browser-Dusk features (e.g. `Class`) use a private `initializeTenantContext()`; HTTP feature-test features (e.g. `HrStaff`) use `initTenant()` + `DatabaseMigrations` + `actingAs()`. The `DuskTestCase` base class provides **no** init method — the test file defines its own. Mirror the nearest same-module sibling. **Use exactly ONE test style per file — never mix `$this->browse(...)` Dusk flows and `$this->actingAs(...)->post()` HTTP tests in the same file** (they follow redirects and run JavaScript differently, and the mix hides which path actually exercised the code). If a file must use HTTP tests, initialize the tenant context (rule #2) BEFORE `actingAs()`, or the request hits the wrong database. *(Evidence: Hostel `hst_RoomChange`/`hst_IncidentWarnings` mixed both styles — test-quality review 2026-07-14, Mistake #20.)* `[Codebase-verified]`
2. **Resolve the tenant via `Modules\Prime\Models\Domain`** (host → `tenancy()->initialize($domain->tenant)`). **Never** use `$this->artisan('tenancy:init')` (does not work in tests) and **never** `\App\Models\Tenant` (class does not exist — the model is `Modules\Prime\Models\Tenant`, table `prm_tenant`).
3. **Always guard teardown:** `if (function_exists('tenancy') && tenancy()->initialized) { tenancy()->end(); }`.
4. **Prime-side vs tenant-side (toggle tenancy scaffolding):** determine from the DDL header comment (`Database: tenant_db` vs `prime_db`) and table prefix — central `prm_*` and central `sys_*` live in `prime_db` (no tenant init needed); module-prefixed tables (`bha_`, `acc_`, `hrs_`, `sys_*` tenant copy, etc.) are per-tenant (require tenant init). Emit tenancy `setUp/tearDown` **only** for tenant-side features.

## B. Users & factories  *(verified: H2, H2b [corrected at Gate 4], H3)*

5. **Tests run in the `prime_testing` runner, which HAS `App\Models\User`** — and this is the model the golden `Class` reference, the `DuskTestCase` base class, and the committed `HrStaff` sibling all use. It has `HasFactory` + a dynamic `$table` bound to `sys_users` in testing, and a runner `UserFactory` at `prime_testing/database/factories/UserFactory.php`. **Default to `use App\Models\User;` + `User::factory()->create([...])` to match the sibling.** *(Correction: the earlier "App\Models\User does not exist" note was based on checking the APP repo `prime_ai` — but tests execute in the RUNNER repo `prime_testing`, where it exists. The peer agent's "never App\Models\User" rule does not apply here.)*
6. **Use a module User model only when the feature's service/type-hints require it.** `Modules\Prime\Models\User` and `Modules\SchoolSetup\Models\User` exist in `prime_ai` (both have `HasFactory` and `password` fillable). Switch to one of these only if a Service or Policy type-hints it; otherwise stay on `App\Models\User` to match the sibling.
7. ⚠️ **`password` IS fillable here** on every User model (cast `'password' => 'hashed'`). *(The peer agent's "password not fillable → use direct assignment" rule is FALSE in this codebase — do not apply it.)* Create users via the factory or mass-assignment.
8. **`sys_users` real columns (verified):** `emp_code VARCHAR(20) NOT NULL UNIQUE`, `short_name VARCHAR(30) NOT NULL` (no default), `prefered_language INT UNSIGNED NOT NULL` (FK → `glb_languages`; note the misspelling "prefered"), and ⚠️ **`user_type ENUM('PRIME','EMPLOYEE','TEACHER','STUDENT','PARENT','OTHER') NOT NULL` DOES exist** in tenant `sys_users` *(the peer agent's "user_type does not exist" is FALSE here)*. The runner `UserFactory` sets `emp_code` + `prefered_language` but **may not set `short_name`/`user_type`** — when hand-building a `User::create([...])` (not via the factory) you MUST supply every NOT-NULL-no-default column (`short_name`, `emp_code`, `prefered_language`, and `user_type` where required), or MySQL strict mode rejects the insert with `SQLSTATE 1364: Field '…' doesn't have a default value`. Prefer `User::factory()->create([...])` (rule #5) so these are filled for you; only override the columns the factory omits. Where a feature ties users to a session (enrollment/admission flows), also provide a valid `academic_session_id` when the target table requires it. *(Evidence: `_prime_db_v4.sql` `sys_users.short_name varchar(30) NOT NULL` line 123; test-quality review 2026-07-14, Mistake #14 — Admission Allotment/Vendor Invoice missing `short_name`, StudentProfile missing `prefered_language`, Admission Enrollment/FollowUp missing `academic_session_id`.)* `[Codebase-verified]`
9. **`emp_code` ≤ 20 chars.** Unique suffix pattern: `'_' . uniqid()` (~14 chars). Never `uniqid().'_'.date('YmdHis')` (~28 chars — overflows VARCHAR(20)).
10. **`glb_languages` is a VIEW** (`CREATE VIEW glb_languages AS SELECT * FROM global_master.glb_languages`) referenced by `prefered_language`. Ensure a valid language id exists before creating users, or the FK insert fails.

## C. Soft-delete, media & typed properties  *(verified: H5, U2)*

11. **`forceDelete()` may hit the media table.** Models with `InteractsWithMedia` (spatie/medialibrary) query the media table on force-delete; **this project uses `sys_media`** (INT UNSIGNED PK), not the default `media`. Always wrap cleanup: `try { $m->forceDelete(); } catch (\Throwable) {}`. **The media table may also be ABSENT from the test database entirely** — if the target model uses `InteractsWithMedia`, any media-touching operation (attach, `getMedia()`, force-delete) can throw `Base table or view not found`. Detect media usage up front (`in_array(\Spatie\MediaLibrary\InteractsWithMedia::class, class_uses_recursive(Model::class))` or the `HasMedia` interface), guard media operations in `try/catch`, and **document the `sys_media` migration as an environment prerequisite in the Validation Report** — do NOT add the migration from a test and do NOT edit `prime_testing`. *(Evidence: test-quality review 2026-07-14, Mistake #8 — 8+ StudentProfile/Hostel/Vendor files crash on a missing media table.)* `[Codebase-verified]`
12. **`withTrashed()`/`onlyTrashed()`/`forceDelete()` only if the model uses `SoftDeletes`.** Verify with `in_array(SoftDeletes::class, class_uses_recursive(Model::class))`; otherwise it throws `BadMethodCallException` — document as a DDL/model gap, don't add the trait in the test.
13. **Initialize all typed properties with defaults** (`private ?User $userA = null;`) — `tearDown()` accesses them and throws "must not be accessed before initialization" otherwise.

## D. Assertions & HTTP  *(verified: U1, U3, U4, H8)*

14. **Dusk `Browser` has NO `assertStatus()`.** For status codes use Laravel HTTP test methods (`$this->getJson()/postJson()/putJson()/deleteJson()` → `assertStatus/assertOk/assertForbidden/assertNotFound`). For browser flows verify via `assertPathBeginsWith`, `assertSee`, success/error banners. Dusk also cannot do `.post()/.put()/.delete()` — use HTTP test methods for API/AJAX endpoints.
15. **Always authenticate before validation/negative tests** (`$this->actingAs($user)` before POST) — unauthenticated posts redirect to login and produce no validation errors.
16. **Browse closures don't capture outer variables** — pass them: `$this->browse(function (Browser $b) use ($record) { ... })`.
17. **MySQL 8 `COLUMN_TYPE` variance:** assert schema types with `assertStringContainsString('int', ...)` (or an accepted-types array), never `assertEquals('int unsigned', ...)` — MySQL 8 may report `int` / `binary(16)` etc.
18. **Respect column limits in generated data:** TINYINT ≤ 127; ENUM values must match the DDL **exactly and case-sensitively** (`'text'` ≠ `'Text'` — cross-check FormRequest `in:` against DDL `ENUM`); VARCHAR within declared size. **This is about not overflowing your OWN seed/fixture data — it is the complement of the over-length *coverage* obligation in rule #45, which requires you to deliberately submit an OVER-length value and assert the app rejects it. Keep the two distinct: valid fixtures stay within size (here); a boundary negative test intentionally exceeds it (#45).**

## E. Environment prerequisites  *(verified: H6, H7)*

19. **⚠️ Target module must be ENABLED.** `prime_testing/modules_statuses.json` currently has **nearly every module `false`** (only `Syllabus` true). A disabled module returns **404 on all routes** (Dusk and HTTP). Before generating runner/prereq notes, state that the target module must be enabled in `modules_statuses.json`; document this as an environment prerequisite in the Validation Report, **not** a test-code fix.
20. **`APP_ENV=testing` for Dusk runs** (bypasses CSRF; else state-changing requests get 419). The runners set it; keep asserting authenticated flows. The `DuskTestCase` base warns when `APP_ENV != testing`.
21. **Prime/central features run on `http://127.0.0.1:8000`, NOT `test.localhost`.** The committed base `PrimeDuskTestCase` (`prm_PrimeDuskTestCase_TestCas.php`) hardcodes `$primeBaseUrl='http://127.0.0.1:8000'` and calls `$this->fail(...)` in `setUp()` if the host isn't `127.0.0.1`. Prime-side (central `prm_*`/`sys_*`, `prime_db`) browser features must extend the module's central base (e.g. Billing → `BillingDuskTestCase`) and use its `authenticateCentral()`/`visitAuthenticated()`/`centralUrl()` chain — do NOT use the tenant `DUSK_TENANT_URL`/`initializeTenantContext()` scaffolding. *(Evidence: prm_PrimeDuskTestCase_TestCas.php:9,18-20.)* `[Codebase-verified]`
22. **Module-local test base classes are filename↔classname-mismatched and only resolve via the preloader.** `tests/Browser/Modules/preload.php` builds `class_alias` from the filename-derived name (e.g. `prm_BillingDuskTestCase_TestCas`) and also stubs missing parents, so a subclass may `extends BillingDuskTestCase` (short alias) even though the physical class is `prm_..._TestCas`. Mirror the sibling's `use ...\BillingDuskTestCase;` + `extends BillingDuskTestCase` verbatim; `php -l` passes regardless (syntax-only), and the alias resolves at runtime. *(Evidence: preload.php:212-241; prm_ConsolidatedPaymentTab_TestCas.php:6-8.)* `[Codebase-verified]`
23. **A module's `routes/api.php` is NOT necessarily registered — verify the module's `RouteServiceProvider::map()` before asserting any module API route exists.** Some modules override `map()` to call only `mapWebRoutes()` (no `mapApiRoutes()`), so a module `apiResource(...)` in `routes/api.php` is never registered even though the file exists. A test assuming such an endpoint is live gets a 404 for a wiring reason, not a defect. When probing a module API, assert with `Route::has('<name>.index')` and/or `method_exists(Controller::class, 'index')` rather than assuming registration; use `$this->getJson()` and accept the dead-route status set `{401,403,404,405,500}` when proving a dead API. *(Evidence: MarksheetGeneration `RouteServiceProvider::map()` calls only `mapWebRoutes()`; `Modules/MarksheetGeneration/routes/api.php` apiResource is unregistered AND the controller lacks index/store/show/update/destroy — audit BUG-MSH-001.)* `[Codebase-verified] [Per-feature-verify]`
24. **Prime/central modules register their WEB routes in the central app `routes/web.php`, NOT in the module's own `Modules/{Module}/routes/web.php` (which may be an empty central-domain stub).** Do not conclude a central module's routes are missing just because its module `routes/web.php` is empty — grep the app-level `prime_ai/routes/web.php` for the route group and assert with `Route::has('<group>.<name>')`. *(Evidence: `Modules/Billing/routes/web.php` only contains an empty `central_domains` group loop; every Billing route — `billing.invoicing-payment.*`, `billing.payment-details`, `billing.consolidated.store`, `billing.billing-cycle.*` — is registered under the `billing.` group in `prime_ai/routes/web.php:322-421`.)* `[Codebase-verified]`

25. **The `activityLog()` helper routes by tenancy state — assert the RIGHT sink for the feature's DB scope.** `app/Helpers/activityLog.php` writes to `Modules\Prime\Models\ActivityLog` (table **`sys_central_activity_logs`**, connection `mysql`) when `tenancy()->initialized` is false (prime/central features), and to `Modules\GlobalMaster\Models\ActivityLog` (tenant table **`activity_logs`**) when tenancy is initialized. Both share the columns `subject_type, subject_id, user_id, event, properties(json), ip_address, user_agent, timestamps` (no soft-delete on either). For **prime-side** features (central `prm_*`/`sys_*`, no tenant init) assert activity via `sys_central_activity_logs`; for tenant-side features use the tenant `activity_logs`. `sys_central_activity_logs` has **no consolidated DDL** in `2-DDL_Tenant_Consolidated/` — its schema comes from a central migration only, so assert it with `Schema::hasTable('sys_central_activity_logs')` (fail-soft guard) plus the model `$fillable`, not a DDL-file `assertStringContainsString`. *(Evidence: app/Helpers/activityLog.php:35-39; Modules/Prime/app/Models/ActivityLog.php:17-32; no `sys_central_activity_logs` CREATE TABLE in `_prime_db_v4.sql`.)* `[Codebase-verified]`

26. **A module's own `Modules/{Module}/database/migrations/` may be EMPTY — real tenant migrations live in `prime_ai/database/migrations/tenant/`.** For MarksheetGeneration the module-local migrations dir holds only `.gitkeep`; all 23 `create_msh_*` migrations are in `database/migrations/tenant/2026_06_16_115725…115747`. Do NOT assert a module-local `MIGRATION_FILE` exists or `assertStringContainsString('Schema::create', …)` against it in `test_01` — it false-fails. Derive schema truth from `Schema::hasTable/hasColumns` + `SHOW INDEX`/`SHOW COLUMNS` against the live tenant DB (and the consolidated DDL), plus the FormRequest file (which does exist under the module). If you want migration-content asserts, resolve the file from `base_path('database/migrations/tenant')` by glob, not the module path. *(Evidence: `Modules/MarksheetGeneration/database/migrations/` = only `.gitkeep`; 23 files under `prime_ai/database/migrations/tenant/`.)* `[Codebase-verified] [Per-feature-verify]`

27. **A migration whose FILENAME says "rename X to Y" may be a no-op — read its BODY, never trust the name.** `database/migrations/tenant/2026_06_15_145407_rename_sys_dropdown_table_to_sys_dropdowns.php` renames `sys_dropdown_table` → `sys_dropdown_table` (same name) under an always-false guard, with a docblock stating the table stays `sys_dropdown_table`. The real runtime table is **`sys_dropdown_table`**, confirmed by `Dropdown::$table`, msh FK `->on('sys_dropdown_table')`, and FormRequest `exists:sys_dropdown_table,id`. This directly contradicts audit note DOC-MSH-002 (which claimed `sys_dropdowns` from the filename alone). Rule: assert the status/dropdown FK target as `sys_dropdown_table`, and generally verify any "renamed" table by its migration body + the Eloquent model `$table`, not the audit or the filename. *(Evidence: rename migration body is `Schema::rename('sys_dropdown_table','sys_dropdown_table')`.)* `[Codebase-verified]`

28. **Some `glb_*` models (global_master tables) are owned by the Prime module but bind to a NON-default connection `global_master_mysql`, and physically live in the `global_master` database — NOT `prime_db`/`mysql`.** Assert their schema truth with `Schema::connection('global_master_mysql')->hasTable/hasColumn(...)` and query/seed them via `Model::on('global_master_mysql')` (or `DB::connection('global_master_mysql')`), or the default-connection lookups return empty/false and the test false-fails. Example: `Modules\Prime\Models\Menu` sets `protected $connection = 'global_master_mysql'; protected $table = 'glb_menus';` while the controller/routes live under the Prime module and central `central.system-config.menu.*` group. Central activity for such features still routes to `sys_central_activity_logs` on the default `mysql` connection (see #25) because tenancy is not initialized. Also note the **consolidated DDL can lag the runtime schema**: `_global_db_v4.sql` `glb_menus` omits `menu_for` and `permission`, yet the model fills and the controller filters on them — use fail-soft `hasColumn` guards rather than DDL-file `assertStringContainsString` for such columns. *(Evidence: Modules/Prime/app/Models/Menu.php:15-17,20-34; `_global_db_v4.sql` glb_menus lines 119-139 has no `menu_for`/`permission`.)* `[Codebase-verified] [Per-feature-verify]`

29. **The runner (`prime_testing`) does NOT contain the app's `Modules/*` PHP SOURCE on disk — app classes autoload via a path mapping, but raw source files are not under the runner root.** So a test that proves a defect by scanning source TEXT (e.g. a stray `// dd($request->all());s` debug comment, a MISSING `in:` enum rule in a controller method, a not-implemented notification) cannot `File::get(base_path('Modules/...'))` — that path does not exist in the runner. Resolve the separate app repo path instead: try `env('MAIN_PROJECT_PATH')`, then `base_path('../prime_ai/<relative>')`, then `dirname(base_path()).'/prime_ai/<relative>'`, and **fail-soft `markTestSkipped()` if none is readable** so partial/CI environments stay green. (Class existence / route registration is still assertable directly — `class_exists()`, `method_exists()`, `Route::has()` — because those resolve through the autoloader; only raw file-text reads need the app-repo path.) *(Evidence: `ls prime_testing/Modules/StudentProfile/app/Http/Controllers/AttendanceController.php` → No such file; the same class is nonetheless usable as `Modules\StudentProfile\...` at runtime.)* `[Codebase-verified]`

30. **The consolidated DDL can diverge from the live migration in BOTH directions for soft-delete and GENERATED columns — always assert these against the live schema (`Schema::hasColumn` / `information_schema`), never the DDL file.** In StudentProfile the DDL spec (`StudentProfile_DDL_v1.6.sql`) OMITS `deleted_at` on `std_health_profiles`/`std_vaccination_records`/`std_student_documents`/`std_student_attendance`, yet the real create-migrations add `$table->softDeletes()` (so the column DOES exist) — while the Eloquent models do NOT use the `SoftDeletes` trait (so `->delete()` still hard-deletes). Conversely the DDL declares `std_student_academic_sessions.current_flag` as `INT GENERATED ALWAYS AS (...) STORED`, but the migration creates a plain `integer('current_flag')->nullable()` (audit BUG-STD-11). Rule: to prove a "generated" column, read `information_schema.COLUMNS.EXTRA` (expect it to NOT contain `GENERATED` when the migration made it plain); to prove soft-delete, combine `Schema::hasColumn(table,'deleted_at')` with `in_array(SoftDeletes::class, class_uses_recursive(Model::class))` and report the two independently — the column and the trait can disagree. Do NOT `assertStringContainsString` against the consolidated DDL for these facts, and do NOT add the trait/generated-column in the test. *(Evidence: `database/migrations/tenant/2026_06_15_151303_create_std_health_profiles_table.php:36` softDeletes; `..._151307_create_std_student_academic_sessions_table.php:19` plain `integer('current_flag')->nullable()`; `StudentProfile_DDL_v1.6.sql` health/vaccination tables have no `deleted_at`, line 222 declares current_flag GENERATED STORED.)* `[Codebase-verified] [Per-feature-verify]`

31. **`Gate::before` grants ALL abilities to Super Admin — authorization NEGATIVE tests must use a NON-super-admin, unpermissioned user or they FALSE-PASS.** `app/Providers/AppServiceProvider.php` registers `Gate::before(fn($user,$ability) => ($user->is_super_admin && $user->super_admin_flag) || $user->hasRole('Super Admin') ? true : null)`. The default Dusk admin (`root@tenant.com`) is typically a Super Admin, so ANY `Gate::authorize(...)`/`->can(...)` check is bypassed for it — a "limited user is blocked" test that logs in as the admin will wrongly report the gate as enforced (403 never fires because the controller was never reached OR the gate short-circuits to allow). To exercise a permission gate, create a fresh user, clear `is_super_admin`/`super_admin_flag` (force-fill 0) AND `syncRoles([])`/`syncPermissions([])`, then `loginAs()` it. Also note: string abilities like `tenant.<res>.<action>` resolve to Spatie-registered permission gates (not the model Policy) — an ability with no matching permission row and no Policy method is DENIED by default, so a limited user gets 403 whether the permission is missing or merely un-granted. When an audit claims a controller's `Gate::authorize` is "commented out", verify against the CURRENT source before asserting 403 — the calls may have been restored since the audit (e.g. StudentProfile GAP-STD-06: audit 2026-06-30 said `StdLeaveController` gates were commented out, but current source has active `Gate::authorize` on all 8 methods). Probe the observed status against a documented set rather than hard-asserting 403. *(Evidence: app/Providers/AppServiceProvider.php:64-73; Modules/StudentProfile/app/Http/Controllers/StdLeaveController.php gates active on index/review/updateReview/edit/update/getStudentsBySection/getApplicationsByStudent/storeRemark.)* `[Codebase-verified]`

32. **To assert real APP source content (gate strings, blade partials, `.bkp`/backup files, FormRequest presence) from the `prime_testing` runner, resolve the file via reflection — `base_path()` points at the RUNNER, not `prime_ai`.** In the runner `base_path()` = `prime_testing`, but application source lives in `prime_ai` (autoloaded via a composer path repo). Guessing the app path or globbing `base_path()` false-fails. Instead anchor on an already-loaded class: `(new \ReflectionClass(Modules\...\SomeController::class))->getFileName()` returns the absolute `prime_ai/Modules/{Module}/app/Http/Controllers/...php`; derive the module root with `dirname($file, 4)` and the app root with `dirname($file, 6)`, then `File::get()`/`glob()` under those. Always wrap in `try/catch` + `markTestSkipped` when the class/file is absent so partial checkouts stay green. This is the robust way to prove source-level audit findings (e.g. `Gate::authorize('tenant.student.*')` present / `school-setup.student.*` absent, `is_super_admin` absent from the edit `_student-login.blade.php`, `edit.blade.bkp` present, only `StudentLeaveTypeRequest.php` under `app/Http/Requests`) — and, combined with #26, to locate central tenant migrations at `dirname($controller,6).'/database/migrations/tenant'` when the module-local `database/migrations/` is empty. *(Evidence: StudentProfile StudentEdit tests `_52/_54/_80/_82/_83` use `ReflectionClass(StudentController::class)->getFileName()` → `Modules/StudentProfile/app/Http/Controllers/StudentController.php`; module-local `database/migrations/` empty, migrations resolved from the app-root tenant dir.)* `[Codebase-verified]`

## F. Assertion completeness & test hygiene  *(from the 2026-07-14 test-quality review of generated Hostel/Inventory/StudentProfile/Admission/Vendor suites — every item below verified against those files and/or the framework)*

33. **NEVER write a hollow test — every test method MUST contain at least one real assertion.** `$this->addToAssertionCount(1)` is BANNED: it satisfies PHPUnit's "risky test" check without verifying anything, producing a green test that proves nothing. An empty method body (or one whose only statement is `addToAssertionCount`) is likewise banned. If a test is intentionally pending, use `$this->markTestIncomplete('reason')` or `$this->markTestSkipped('reason')` — never a hollow pass. A permission/negative test in particular MUST assert the observed outcome (e.g. `assertForbidden()`/`assertStatus(403)`, `assertSee('...')`, a DB row present/absent), not merely "visited the page." *(Evidence: `addToAssertionCount` found across 20+ Hostel files — `hst_LeavePass` ×10, `hst_Incidents` ×10, `hst_SickBay` ×6, `hst_Bed` ×6, `hst_VisitorLog` ×6 — and many Inventory files; test-quality review Mistakes #1 & #15.)* `[Codebase-verified]`

34. **Use the correct framework method names — verify before using.** There is **no `isCasted()`** on Eloquent models in Laravel 12; the method is **`hasCast()`** (`$model->hasCast('is_active')`). There is **no `isActive()` instance method** on Eloquent models either — `active` is a query *scope*: call `Model::active()->get()` to use it, and to check a single record's flag read the attribute/cast directly (`$model->is_active`), not a nonexistent `isActive()`. Calling either nonexistent method throws `BadMethodCallException` and the whole test errors before asserting. Before using any Eloquent/framework method in a test, confirm it exists in Laravel 12. *(Evidence: `isCasted(` in `hst_BedType`/`hst_RoomType`/`hst_StatusMaster`/`hst_WardenDutyRoster`/`hst_Vitals`/`hst_MessOptOuts`; `->isActive(` in `hst_RoomType`:71 and `hst_RoomInventory`:82; test-quality review Mistakes #2 & #13.)* `[Laravel-12] [Codebase-verified]`

35. **Call `->refresh()` after `->create()` before asserting DB-populated values.** After `Model::create([...])`, the in-memory instance does NOT contain columns the database filled in — DB-level defaults (`is_active` default 1, `created_at`), DB-side computed/generated columns, or trigger-set values are still `null`/absent on `$model` until reloaded. Assert them only after `$model->refresh()` (or re-fetch via `Model::find($id)`). Attributes you passed into `create()` are already present and need no refresh. *(Evidence: test-quality review Mistake #3 — Room/Floor/VisitorLog/Housekeeping/StockItem/Quotation asserted a DB default on the un-refreshed create() result and false-failed.)* `[Laravel-12]`

36. **Use `assertGreaterThanOrEqual()` (not `assertEquals`) for seed/reference-data counts.** A test that asserts an exact row count (`assertEquals(5, BedType::count())`, "30 floors") false-fails the moment another test — run earlier in the same suite — leaves extra rows behind, since these suites do not all reset the DB between tests. Assert the minimum invariant instead: `$this->assertGreaterThanOrEqual(5, BedType::count())`. Reserve exact-count assertions for counts you fully control within the same test (created N, expect N) after cleanup. *(Evidence: test-quality review Mistake #5 — 12+ Inventory files: StockLedger/StockIssue/IssueRequest/Adjustment/AssetRegister/GRN/Quotation/PurchaseRequisition/PurchaseOrder/Uom/StockGroup/Maintenance.)* `[Codebase-verified]`

37. **Permission/authorization negatives MUST assert the denial AND flush the permission cache.** After removing access (`revokePermissionTo()`, `syncPermissions([])`, `syncRoles([])`), you MUST call `app(\Spatie\Permission\PermissionRegistrar::class)->forgetCachedPermissions()` — Spatie caches permissions, so without the flush the "revoked" user still passes the gate and the test false-*passes*. Then visit the protected route and **assert the actual status** (`assertForbidden()`/`assertStatus(403)` via an HTTP test method — Dusk `Browser` has no `assertStatus`, see rule #14) or assert the control is hidden. This composes with rule #31: use a fresh **non-super-admin** user (clear `is_super_admin`/`super_admin_flag`, `syncRoles([])`) or `Gate::before` grants everything and the 403 never fires. *(Evidence: test-quality review Mistakes #1 & #4 — 12+ Hostel 403 tests removed the permission, visited the page, restored it, then `addToAssertionCount(1)` without ever asserting 403 or flushing the cache.)* `[Codebase-verified]`

38. **Every record a test creates MUST be cleaned up.** Left-behind rows accumulate across runs and break later count/uniqueness assertions (feeds rule #36) or cause duplicate-key errors. Prefer the sibling's mechanism: if the module's committed tests use `DatabaseMigrations`/`RefreshDatabase`, mirror that; otherwise delete created rows in a `try/finally` (cleanup in `finally` so it runs even when an assertion fails), keeping the `try { $m->forceDelete(); } catch(\Throwable){}` guard from rule #11 (and only `forceDelete` when the model uses `SoftDeletes`, rule #12). Do not rely on manual ordering — teardown must be unconditional. *(Evidence: test-quality review Mistake #7 — nearly all Inventory/Hostel files created data with no cleanup.)* `[Codebase-verified]`

39. **Browser-side AJAX must carry the CSRF + XHR headers — but prefer HTTP test methods for endpoint checks.** For endpoint status/payload assertions, use Laravel HTTP test methods (`postJson()/putJson()/deleteJson()`), per rule #14 — Dusk `Browser` cannot `.post()`. When a test genuinely issues a `fetch()`/XHR *from the rendered page* (via `sendJsonRequestFromBrowser(...)`), it MUST include `'X-CSRF-TOKEN': <token>` and `'X-Requested-With': 'XMLHttpRequest'` or Laravel rejects it (419/500). Note this composes with rule #20: under `APP_ENV=testing` CSRF is bypassed for Dusk, so this bites mainly non-testing-env or mixed-header AJAX — include the headers regardless so the call is correct in every env. *(Evidence: test-quality review Mistake #11 — StudentProfile/Inventory AJAX calls omitted the CSRF token and got 500.)* `[Codebase-verified]`

40. **Never hand-write a URL path or a selector — derive both from the real source.** URL paths: module routes are prefixed (`/hostel/fee-structures`, NOT `/fee-structures`); a wrong prefix returns 404 and every test in the file fails. Resolve paths from `php artisan route:list | grep <module>`, the module `routes/*.php`, or `Route::has('<name>')` — never guess the prefix (this restates HARD RULE #1; it is the single most common mass-failure cause). Selectors/labels: read the actual Blade view / rendered HTML for the element type (`<table>` vs `<div class="card">`), the real button text (`Save` vs `Submit`/`Create`), and real field `name`/`id` (a `<select name="vendor_id">` may actually be an autocomplete `<input>`). *(Evidence: test-quality review Mistakes #6 & #16 — `hst_FeeStructures`:19 `INDEX_PATH='/fee-structures'` and `hst_FeeDemands`:21 `'/fee-demands'` both 404 (real prefix `/hostel/…`), ~20 tests down; Inventory StockItem waited for `table` on a card page and pressed `Save` where the button says `Submit`.)* `[Codebase-verified]`

41. **Some failures are runner/infrastructure, not test-code — assert tolerantly and document as prerequisites; never edit `prime_testing`.** These do NOT get "fixed" in a generated test file:
    - **Validation status 500 vs 422 (Mistake #19):** an invalid-payload test may observe 500 instead of 422 depending on the runner's `bootstrap/app.php` exception rendering (the current `withExceptions` only sets `shouldRenderJsonWhen`, with no explicit `ValidationException`→422 render). Assert a tolerant set (`$this->assertContains($status, [422, 500])`) with a note, OR document the desired handler fix as an environment prerequisite — do NOT hard-assert 422 and do NOT edit the runner's `bootstrap/app.php`. *(Evidence: `prime_testing/bootstrap/app.php:72-77` withExceptions has no ValidationException render callback; review Mistake #19.)*
    - **Stale route cache (Mistake #18):** `Route::has(...)` can false-fail against a stale `bootstrap/cache/routes-*.php`. State "run `php artisan route:clear` before route assertions" as a runner prerequisite in the Validation Report; do NOT shell out to `route:clear` from inside a test method.
    - **ChromeDriver/WebDriver curl timeouts (Mistake #17):** `Curl error … Operation timed out` is browser-session flakiness, not a defect — wrap fragile browser interactions in a `retry()` where the sibling does, note ChromeDriver/Chrome version alignment as infra, and never assert on the timeout.
    *(All three: test-quality review 2026-07-14; the loader marks `prime_testing`/`prime_ai` read-only — the only permitted external write is appending to THIS file.)* `[Codebase-verified] [Env-verified]`

42. **Shared helpers must be correct and identical to the module sibling — mirror them verbatim, do not paraphrase.** The one-file-per-screen contract (each `{prefix}_{Feature}_TestCas.php` carries its own private helper library) means a helper bug (e.g. a `responseStatusCode()` cURL fallback that drops the session cookies and misreports the status, or a divergent `initializeTenantContext()`) silently propagates or diverges across files. Copy the nearest committed sibling's helpers **exactly** rather than re-deriving them, so a later fix to the sibling can be re-applied uniformly. Prefer Laravel HTTP test methods over a raw-cURL status fallback (rule #14). *(Note: a proposal to extract a single shared `TenantTestSetup` trait — test-quality review Mistake #10/#12 — would change the artifact contract and is a design decision for the maintainer, NOT something to adopt unilaterally mid-generation.)* `[Codebase-verified]`

## G. DDL-derived coverage obligations  *(from the 2026-07-14 test-quality review, batch 2 — the agent must GENERATE these tests, not merely avoid failures; each keys off the DDL, verified against `Hostel_DDL_v4.sql`/`Inventory_DDL_v1.sql`)*

> These are **coverage** rules (make the test EXIST), not just guardrails. Derive every obligation from the **DDL**, not the form. For every "app rejects it" assertion below, tolerate this codebase's verified quirks: the rejection may surface as **500 not 422** (rule #41) and enforcement may live in the DB, the FormRequest, or both — so assert the **observed outcome** (row refused / duplicate not inserted / value not persisted) or the tolerant status set, never a brittle exact `422`. Where the DDL is known to lag the live schema (rules #28, #30), assert schema truth against the **live** schema. When only one layer enforces a constraint (DB has `UNIQUE`/`NOT NULL` but the FormRequest lacks `unique:`/`required`, or vice-versa), record it as a `DEV-###`/audit-equivalent via the Cross-Reference Defect Scan — do NOT "fix" it in the test.

43. **Every DDL `UNIQUE` key MUST have a duplicate-rejection test.** For each `UNIQUE` column and each composite `UNIQUE KEY` on the feature's table(s): create the first record successfully, then attempt a second with the **same** unique value(s) and assert it is refused. For composite keys, vary only the keyed columns (hold them equal, change a non-keyed column) so you exercise the *composite* uniqueness, not an incidental collision. **Pass** = duplicate rejected (validation error, DB `1062`/tolerant status, or "second row not inserted"); **fail** = duplicate inserted successfully. Never assume uniqueness is enforced — prove it. *(Evidence: `hst_room_types` has `UNIQUE KEY uq_hst_room_type_code (code)` on `code VARCHAR(20) NOT NULL`; review batch-2 Mistake #1.)* `[Codebase-verified]`

44. **Every DDL NULL/NOT NULL constraint MUST be exercised — derive required/optional from the DDL, not the form.** For each **NOT NULL, no-default** column: attempt to create/update the record with that value missing/null and assert rejection. For representative **nullable** columns: create/update with the value omitted and assert success. Cross-check the DDL against the FormRequest (`required` vs nullable) — a divergence (DB `NOT NULL` but FormRequest allows null, or DB nullable but FormRequest `required`) is a `DEV-###` candidate. **Pass** = behaviour matches the DDL; **fail** = a NOT NULL field accepts null, or a nullable field is wrongly rejected. (Columns with a DB default are NOT "required" from the user's side — don't demand a value for them; see rule #35 on reading defaults back with `->refresh()`.) *(Evidence: `hst_room_types.code`/`.name` are `NOT NULL` no-default, `is_active TINYINT(1) NOT NULL DEFAULT 1` is NOT-NULL-WITH-default; review batch-2 Mistake #2.)* `[Codebase-verified]`

45. **Every sized string column MUST have an over-length boundary test.** For each `VARCHAR(n)`/`CHAR(n)`: submit a value of length `n+k` (e.g. `n+3`) and assert the app rejects it, AND submit a value of exactly length `n` and assert it succeeds. Cross-check the DDL size against the FormRequest `max:` — a mismatch (`max:` larger than the column, or absent) is a `DEV-###` candidate (silent truncation / DB `1406`). This is the coverage complement of rule #18 (keep your *own* valid fixtures within size; here you *intentionally* exceed it in a dedicated negative test). *(Evidence: `hst_room_types.code VARCHAR(20)`, `.name VARCHAR(100)`; review batch-2 Mistake #3.)* `[Codebase-verified]`

46. **`test_01` MUST assert the FULL DDL↔app alignment matrix, and soft-delete column-vs-trait INDEPENDENTLY.** Beyond "table/columns exist", the schema-truth method asserts: every DDL column exists in the model/migration; no app field (fillable/form/request) references a non-existent column; NULL/NOT NULL matches; data types are handled; field lengths match; defaults are respected; UNIQUE keys validated (→ #43); FKs/relationships correct; and column **names are consistent** across DDL, model, FormRequest, controller, and test. **Soft-delete:** assert `Schema::hasColumn(table,'deleted_at')` and `in_array(SoftDeletes::class, class_uses_recursive(Model::class))` **separately** — they can genuinely disagree in this codebase (rule #30); report a mismatch as a defect, do NOT force them to match, and only use `assertSoftDeleted()`/`onlyTrashed()` when the model actually soft-deletes (rule #12). Where the consolidated DDL is known to lag (rules #28, #30), assert against the **live** schema (`Schema::hasColumn`/`information_schema`/`SHOW INDEX`), not `assertStringContainsString` on the DDL file. **Pass** = fully consistent with the DDL/live schema; **fail** = any missing field, wrong type/length, unrespected default, or bad FK — captured as a `DEV-###`. *(Evidence: soft-delete column↔trait divergence already proven in StudentProfile per rule #30; review batch-2 Mistake #4.)* `[Codebase-verified] [Per-feature-verify]`

47. **CRUD MUST run through the correct, verified Eloquent model.** Before generating operations, confirm from the real source (controller/service usage + DDL primary table): the model exists and is imported; its `$table` matches the DDL table/prefix; `$fillable`/`$guarded` support the fields under test; the relationships used are valid. Route ALL create/read/update/delete through that model — a wrong/missing/misconfigured model silently exercises the wrong data or fails for the wrong reason. If the *application's* model is wrong (e.g. mapped to the wrong table, missing a fillable column), that is a `DEV-###`, not something to paper over in the test. *(Evidence: review batch-2 Mistake #5; composes with rule #6 on which User model to use.)* `[Codebase-verified]`

48. **Test the CODE, not the UI — programmatically-managed fields are auto-behaviour, NEVER form inputs.** Before writing cases, review the controller, FormRequest, model, service, routes, and business logic — not the Blade form alone (this is HARD RULE #1/#2, restated because the review found it violated). Fields set in code — an auto-assigned `ordinal`, an auto-generated code/name, a server-set default, a computed/generated column, a status set by a workflow transition — MUST be tested as **auto-managed behaviour** (assert the controller/service assigns the expected value; assert the user CANNOT override it where that's the design), and MUST **NEVER** be proposed as a form field or a user-editable input. Canonical failure: a generated test suggested adding the controller-managed `ordinal` to the form — a tell that the test was written from the UI, having never read the controller. *(Evidence: `ordinal` is code-managed across app controllers/services (e.g. Accounting `AccountGroupController`, ordered/assigned in code, not user-entered); review batch-2 Mistake #6.)* `[Codebase-verified]`
