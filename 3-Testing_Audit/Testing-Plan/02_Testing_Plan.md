# Prime-AI — Testing Plan (Execution)

**Version:** 1.0
**Date:** 2026-07-09
**Companion docs:** `00_..._Conventions.md`, `01_Testing_Strategy_Report.md`, `03_..._Agent_Prompt.md`

This plan operationalises the strategy: **what gets tested, in what order, by whom/what, and how we know it's done.** The unit of work is a **feature**; the unit of delivery is the **7-artifact set**; the unit of review is the **Validation Report**.

---

## 1. Work Breakdown

```
Program
 └─ Module (45)                         ← e.g. HrStaff
     └─ Feature (1..n)                  ← e.g. SalaryComponent, LeaveApplication, Payslip
         └─ Artifact set (7 files)      ← TcList, MANUAL, GAP, TestCas.php, Validation, .ps1, .sh
             └─ Test methods            ← test_{feature}_NN_*
```

**Feature discovery** (per module, done first): enumerate features from the DDL primary tables + controllers in `APP_CODE_DIR/{Module}/app/Http/Controllers` + the module requirement doc. One primary CRUD table + controller ≈ one feature. Produce a `Feature Inventory` for the module before generating.

---

## 2. Per-Feature Workflow (the core loop)

The `Testcase_Creator` agent executes this loop for each feature. Humans review at the ✅ gates.

| Step | Action | Output | Gate |
|------|--------|--------|------|
| 1 | **Ingest** DDL, FRD, Requirement V1, Audit, and **actual** Controller/Request/Model/Routes/Views | Working notes | — |
| 2 | **Decompose** into Business Conditions (BC-DB/VAL/AUTH/BIZ/REF/AUTO) | BC tables | — |
| 3 | Write **TcList** (BC + TC-P/N/D list + Test Method index skeleton) | Artifact 1 | ✅ review BC completeness |
| 4 | Write **MANUALTESTING** (feature info + BC + step-by-step TCs w/ DB + activity-log checks) | Artifact 2 | — |
| 5 | Generate the single comprehensive **Dusk test file** (every TC + helpers) | Artifact 4 | `php -l` |
| 6 | Finalise **GAPANALYSIS** (map every manual TC ↔ method, coverage %) | Artifact 3 | ✅ Neg 100%, Pos ≥90%, Dep ≥90%, Tenancy 100% (P0/P1); every TC-ID↔≥1 method & every method↔TC/BC |
| 7 | Generate **runners** `.ps1` + `.sh` | Artifacts 6,7 | — |
| 8 | Write **Validation Report** (existence, naming, structure, coverage, defects, verdict) | Artifact 5 | ✅ PASS / PASS-WITH-NOTES |
| 9 | (Optional) **Execute** the test file, capture proof, attach results | proof file | ✅ green or documented-known-fail |

**Iteration:** if step 6 shows a gap or step 8 fails a check, loop back to step 5.

## 3. Phased Rollout (risk-tiered)

Ordering follows the risk tiers from Strategy §7. Each phase = a set of modules; within a module, features are done highest-fan-out-first.

### Phase 0 — Foundation & Pattern Lock (already largely done)
- Golden reference (`Class&SubjectMgmt/Classes`) and `HrStaff` (23 features) validated.
- **Deliverable:** conventions frozen (this folder), agent prompt deployed, one dry-run feature regenerated by the agent and diffed against the golden reference to confirm fidelity.

### Phase 1 — P0: Money & Identity
Modules: **Accounting, Billing, Payment, StudentFee, HrStaff/Payroll (remaining).**
- Emphasis: financial correctness, audit-log integrity, tenancy isolation (`TC-T`), security pack (`TC-S`), FK integrity.
- **Exit:** 100% negative + 100% tenancy coverage on every feature; all audit `DEV-###` documented.

### Phase 2 — P1: Academic Spine
Modules: **SchoolSetup (Class/Section/Subject/Rooms), StudentProfile, Admission, TimetableFoundation + Standard/Smart Timetable, LmsExam, MarksheetGeneration.**
- Emphasis: referential integrity (RESTRICT/SET NULL), cross-module impact (`TC-D` cat E), lifecycle.
- **Exit:** dependency coverage ≥ 90%; cross-module auto-update tests present.

### Phase 3 — P2: Engagement & Operations
Modules: **LmsHomework, LmsQuiz, LmsQuests, QuestionBank, Library, Hostel, Transport, Inventory, Cafeteria, PTM, Complaint, Notification, Recommendation, Feedback, BehaviouralAssessment, Hpc, Certificate, EventEngine.**
- Emphasis: breadth; standard functional + security smoke.

### Phase 4 — P3: Supporting / Read-mostly
Modules: **Dashboard, Documentation, ParentPortal, StudentPortal, GlobalMaster, SystemConfig, Template, Scheduler, FrontOffice, CommonChat, Vendor, Syllabus, SyllabusBooks, Prime.**
- Emphasis: composite/read views, integration smoke, permission/visibility.

### Phase 5 — Roll-ups & Hardening
- Generate module dashboards, RTMs, program Defect Register & Test Summary.
- CI integration; nightly full runs; flake triage.

---

## 4. Sequencing Rules

1. **Dependencies before dependents** — SchoolSetup (classes/sections/rooms/teachers) and StudentProfile before anything that references them, so cross-module tests have real targets.
2. **Within a module** — the primary/parent entity first, then children, then junctions, then reports/composite screens.
3. **Defect-carrying features first** within a tier — features with open `DEV-###` audit findings are escalated.
4. **Regenerate downstream** when a shared entity's schema changes (its `test_01` will catch it; dependents may need re-run).

---

## 5. Estimation & Throughput (planning aid)

Per-feature agent generation is the fast part; **human review at the 4 gates** is the throughput constraint. Rough guide (calibrate after Phase 0):

| Feature complexity | Signals | Test file size | Review effort |
|--------------------|---------|-----------|---------------|
| Simple master (dropdown/lookup) | 1 table, few fields, no FK fan-out | ~25 | Low |
| Standard CRUD | 1 table + a couple FKs, modal CRUD | ~50 | Medium |
| Complex (junctions, cross-module, money) | Multiple tables, RESTRICT/SET NULL, model events, financial | ~78+ | High |

Plan capacity by **review-hours**, not generation time. Batch simple masters; reserve senior review for P0 complex features.

## 7. Tracking

- **Master tracker** (spreadsheet or `_Program_Test_Summary.md`): row per feature — Module, Feature, prefix, #methods, coverage %, Validation verdict, last run pass/fail, open DEV defects, owner, phase.
- **Per-module dashboard** (`_MODULE_Coverage_Dashboard.md`): generated in agent `report` mode.
- **Status values:** `Not started → Generating → In review → Passing → Passing-with-notes → Blocked(defect)`.
- **Cadence:** update on each feature completion; weekly roll-up regeneration during active phases.

---

## 8. CI / Automation Integration

| Trigger | Suite | Purpose |
|---------|-------|---------|
| PR to a module | That module's **test suites** (`--filter ...TestCas`) | Fast correctness gate |
| Nightly | Full **test suite** per completed module | Regression |
| Pre-release | Full program suite + roll-up dashboards | Release gate |
| On schema/DDL change | Affected `test_01` config tests | Catch drift immediately |

**Gates in CI:** `php -l` on generated PHP; Validation Report present & PASS; test suite green mandatory (known-fails must reference a `DEV-###`).

---

## 9. Exit Criteria (program-level)

The program is "test-complete" when:
1. Every feature in Phases 1–4 has a passing 7-artifact set (or a documented, defect-linked exception).
2. Program-wide: Negative = 100%, Positive ≥ 90%, Dependency ≥ 90%; Tenancy = 100% on P0/P1.
3. Program Defect Register is current; every open `DEV-###` has a proving test.
4. CI runs the tiered suites automatically and publishes roll-ups.
5. Program Test Summary shows ≥ target % features automated & passing.
