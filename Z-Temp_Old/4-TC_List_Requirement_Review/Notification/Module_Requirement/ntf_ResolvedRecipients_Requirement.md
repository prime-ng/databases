# Resolved Recipients — Business Requirements

## What This Screen Does
The Resolved Recipients screen displays the final, resolved list of individual recipients for a notification after the dispatch pipeline has processed all targets, groups, conditions, and user preferences. Each record represents one person who will receive (or has received) the notification on a specific channel, with personalized content already rendered. This is a read-mostly, derived-data screen — records are generated by the dispatch pipeline, not created manually.

## When This Screen Is Used
- When reviewing who will receive a notification before dispatch is triggered
- When auditing the resolved recipient list for accuracy
- When checking if a specific user is included in a notification's audience
- When re-processing failed recipients via the bulkProcess endpoint
- When an administrator needs to manually mark a recipient as processed (admin override)
- When viewing delivery history per recipient

## Default Data Load
On page load, the screen displays a paginated list of resolved recipients filtered by notification_id (defaulting to the most recent notification for the current admin). Critical fields shown: recipient name, channel, personalized_subject snippet, priority, batch_id, is_processed status, and processed_at timestamp. Filters for channel, is_processed status, and priority are provided.

## Business Rules and Conditions
- **Read-only / derived records:** Records are generated by the dispatch pipeline, not created manually through the UI. The CRUD exists for exceptional admin override scenarios only.
- **Processed recipients cannot be edited or deleted:** Once `is_processed = true`, the record is locked. Any attempt to edit or delete returns an error.
- **Updates notification counters:** Creating or processing recipient records updates `total_recipients` and `sent_count` on the parent notification.
- **One recipient per channel per user:** A single user may appear multiple times if the notification is sent via multiple channels (e.g., email + SMS), but only once per channel.
- **Has delivery logs relationship:** Each resolved recipient has one or more delivery log records documenting the delivery attempt lifecycle.
- **batch_id and batch_sequence** allow tracking of bulk dispatch batches for monitoring and retry.

## Workflow Steps
1. Administrator dispatches a notification. The dispatch pipeline runs:
   a. Resolves all notification targets → produces raw recipient set.
   b. Applies user preferences (opt-out, quiet hours, digest).
   c. Renders personalized content using the assigned template.
   d. Generates resolved_recipient records per user per channel.
2. Administrator views the resolved list to confirm accuracy.
3. For unprocessed records, admin can use `bulkProcess()` to trigger batch dispatch.
4. For individual unprocessed records, admin can use `markAsProcessed()` to manually mark as sent (counts as dispatch).
5. Post-dispatch, each recipient links to delivery logs showing delivery status.

## Example Scenario
The school dispatches an exam schedule notification to "All Class 10 Students" via Email and SMS. The dispatch pipeline runs:
- Target resolution finds 85 students in the group.
- User preference check: 2 students have opted out of SMS → only Email for them.
- Quiet hours check: 1 student has quiet hours active → queued for deferral.
- Personalization: Each student's name, class, and exam subjects are merged.
Result: 85 Email records and 83 SMS records are created in ntf_resolved_recipients, all linked to the same notification. The admin views 168 total records across two channels.

## Requirements

### REQ-RR-01: Pipeline-Generated Records
Resolved recipient records must be generated automatically by the dispatch pipeline, not manually created via standard CRUD operations.

### REQ-RR-02: Processed Record Locking
Once `is_processed = true`, the record must be locked against edits and deletion. The controller must check this flag before allowing any modify operation.

### REQ-RR-03: Admin Override CRUD
Despite the read-only nature, the CRUD routes exist for exceptional admin overrides. The create route allows manually adding a recipient, and the delete route works only for unprocessed records.

### REQ-RR-04: Mark As Processed
Administrator must be able to mark a single unprocessed recipient as processed via `markAsProcessed()`, which sets `is_processed = true` and `processed_at = now()`.

### REQ-RR-05: Bulk Process
Administrator must be able to process multiple unprocessed recipients in a batch via `bulkProcess()`. This endpoint accepts an array of IDs or a batch_id.

### REQ-RR-06: Get By Batch
Administrator must be able to retrieve all recipients belonging to a specific batch_id via `getByBatch()` for monitoring and retry workflows.

### REQ-RR-07: Notification Counter Updates
Creating a resolved recipient must increment `total_recipients` on the parent notification. Marking as processed must increment `sent_count`.

### REQ-RR-08: Toggle Active Status
Administrator must be able to toggle `is_active` on unprocessed records. Active status on processed records cannot be changed.

### REQ-RR-09: Soft Delete and Restore
Resolved recipients must support soft delete, restore, and force delete — but only for unprocessed records.

## Logic Flow

### Dispatch Pipeline (Generation)
```
Resolve targets → Get raw user list → 
For each user+channel:
    Check user preference (opt-out = skip channel)
    Check quiet hours (defer if applicable)
    Render personalization from template
    Create resolved_recipient record
    Update notification.total_recipients
    Assign batch_id and batch_sequence
```

### Mark As Processed Flow
```
User selects unprocessed recipient →
Check is_processed (reject if already true) →
Set is_processed = true →
Set processed_at = now() →
Increment notification.sent_count →
Return success
```

### Delete Flow (Unprocessed Only)
```
User clicks delete →
Check is_processed (reject if true) →
Apply SoftDeletes →
Set is_active = false →
Return success
```

## Success Scenarios

- **View List:** Resolved recipients displayed with filters and pagination.
- **Mark As Processed:** Recipient marked as processed. sent_count updated.
- **Bulk Process:** X recipients processed successfully. Notification counters updated.
- **Get By Batch:** All recipients in batch returned successfully.
- **Create (Admin Override):** Resolved recipient created. total_recipients updated.
- **Toggle Status (unprocessed):** Status changed successfully.
- **Delete (unprocessed):** Recipient soft-deleted successfully.
- **Restore:** Recipient restored successfully.

## Failure Scenarios

- **Processed record modification:** 422 error. No changes applied.
- **Invalid batch_id:** 404 error. No recipients found for batch.
- **User lacks permission:** 403 Forbidden. No operation performed.
- **Database error:** 500 Internal Server Error. Transaction rolled back.
- **Recipient not found:** 404 Not Found. No operation performed.
