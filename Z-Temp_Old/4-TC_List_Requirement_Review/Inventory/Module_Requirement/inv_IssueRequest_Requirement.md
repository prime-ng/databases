# Issue Requests — Business Requirements

## What This Screen Does

The Issue Requests screen enables staff to request stock items from a godown. Each Issue Request (IR) specifies items, quantities, UOMs, and a required date. IRs follow a lifecycle: Submitted → Approved → Issued/Partial (or Rejected). Approval sets approved issuance quantities per item, which are then fulfilled by Stock Issues.

This is the first tab (`?tab=issue-requests`) of the Stock Movement page at `/inventory/stock-movement`.

## When This Screen Is Used

- **Material Requisition**: Department staff request materials from the store/godown
- **Approval Workflow**: Submitted requests go through approval/rejection process
- **Issue Planning**: Approver specifies how much of each requested item is approved for issuance

## Key Fields

### Issue Request Header
- **Request Number** (auto-generated) — Format: IR-YYYY-NNNN (e.g., "IR-2026-0001")
- **Requested By** (auto-set) — Current authenticated user
- **Department** (auto-set from user or default)
- **Required Date** (required) — Must be today or future
- **Status** (auto-managed) — Enum: `submitted`, `approved`, `issued`, `partial`, `rejected`
- **Remarks** (optional) — Purpose description, max 2000 chars

### Issue Request Items
- **Stock Item** (required) — FK to `inv_stock_items.id`
- **Requested Quantity** (required) — DECIMAL(15,3), min 0.001
- **UOM** (required) — FK to `inv_units_of_measure.id`
- **Issued Quantity** (auto-updated) — Set during approval; incremented by StockIssueService during issue execution

## Business Rules

### Status Lifecycle
```
submitted ──[approve]──→ approved ──[execute issue]──→ issued (or partial)
    │
    └──[reject]──→ rejected
```
- **submitted**: Default after creation; editable, deletable; awaiting approval
- **approved**: Approved by authorized staff; ready for stock issue execution
- **issued**: All items fully issued (issued_qty ≥ requested_qty for all lines) — auto-set by StockIssueService
- **partial**: Some items issued, some pending — auto-set by StockIssueService
- **rejected**: Rejected with reason; editable

### Create Behavior
IRs are created as `submitted` by default (no draft status). This means the IR goes directly into the approval queue.

### Edit Guard
IRs can be edited only when status is `submitted` or `rejected`. Edits replace all items (delete + recreate).

### Approval Process
When approving:
1. Approver specifies `issued_qty` for each item (can be less than requested_qty)
2. Each item's `issued_qty` is updated
3. IR status changes to `approved`
4. `approved_by` is recorded

### Rejection
Rejected IRs require a mandatory `remarks` field (max 500 chars) as the rejection reason.

### Delete Guard
Only `submitted` IRs can be deleted. Items cascade delete via DB FK.

### Auto Status Transition (by StockIssueService)
After a Stock Issue is executed against an approved IR:
- If all items have `issued_qty ≥ requested_qty` → status = `issued`
- If some items remain unfulfilled → status = `partial`

### Number Generation
Request numbers generated by `StockIssueService::generateRequestNumber()`: `IR-YYYY-NNNN` (sequential per year).

### Service Layer
`StockIssueService` is used for:
- `generateRequestNumber()`: IR number generation
- `updateIssueRequestStatus()`: Auto-transitioning to issued/partial after stock issue execution

### Cross-Module Dependencies
- `requested_by` references `sys_users` (System/Auth module)
- `department_id` references `sch_department` (SchoolSetup module)
- `item_id` references `inv_stock_items` (Inventory module) — hard FK
- `uom_id` references `inv_units_of_measure` (Inventory module) — hard FK

## Workflow

1. Staff navigates to Inventory → Stock Movement → Issue Requests tab
2. Staff clicks "Add Issue Request" to open create modal
3. Staff enters required date, remarks/purpose, and at least one item with qty and UOM
4. Staff submits → IR created as Submitted, appears in the approval queue
5. Authorized approver reviews and approves the IR, setting issued quantities per item
6. Approved IR moves to Stock Issues tab for execution
7. Storekeeper executes the issue, which updates IR status to Issued or Partial

## Requirements

- MUST display paginated IRs in a table with search and status filter
- MUST authorize via `tenant.inventory.stock-issue.*` policy gates (6 gates including approve)
- MUST validate store with 6+ rules including nested items (min:1)
- MUST generate unique request_number in format IR-YYYY-NNNN
- MUST create IR with status=submitted by default
- MUST create nested items with issued_qty=0 during store
- MUST guard edit: only submitted or rejected IRs can be edited
- MUST guard approve: only submitted IRs with items array can be approved
- MUST update per-item issued_qty during approval
- MUST record approved_by on approval
- MUST guard reject: only submitted IRs with required remarks can be rejected
- MUST guard delete: only submitted IRs can be deleted
- MUST support soft-delete lifecycle
- MUST auto-transition IR status to issued/partial via StockIssueService
- MUST show IR detail page with header info and items table
- MUST show Approve/Reject inline actions on submitted IRs in list
- MUST show Edit/Delete actions only on editable IRs
- MUST support edit modal with JS pre-fill
- MUST log all CRUD and lifecycle operations via activityLog()
