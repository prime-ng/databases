# Stock Adjustments — Business Requirements

## What This Screen Does

The Stock Adjustments screen manages physical count corrections to inventory. Each adjustment records the system quantity and physical (counted) quantity for items in a specific godown. The variance (physical - system) is automatically calculated. Adjustments follow a lifecycle: Draft → Submitted → Approved (with ledger posting) or Rejected. Variances within configured thresholds are auto-approved; variances exceeding thresholds require manual approval.

This is the third tab (`?tab=adjustments`) of the Stock Movement page at `/inventory/stock-movement`.

## When This Screen Is Used

- **Periodic Stock Count**: End-of-month or annual physical inventory counts
- **Damage/Expiry**: Writing off damaged or expired stock
- **Theft/Loss**: Adjusting for missing stock
- **Correction**: Fixing data entry errors in stock balances
- **Opening Balance**: Setting initial stock quantities during implementation

## Key Fields

### Adjustment Header
- **Adjustment Number** (auto-generated) — Format: ADJ-YYYY-NNNN (e.g., "ADJ-2026-0001")
- **Adjustment Date** (required) — Physical count date
- **Godown** (required) — FK to `inv_godowns.id`
- **Reason** (required) — Enum: `periodic_count`, `damage`, `expiry`, `theft`, `correction`, `opening_balance`
- **Status** (auto-managed) — Enum: `draft`, `submitted`, `approved`, `rejected`, `posted`
- **Approved By** / **Approved At** (set on approval)

### Adjustment Items
- **Stock Item** (required) — FK to `inv_stock_items.id`
- **System Quantity** — Current system balance (optional, for reference)
- **Physical Quantity** (required) — Actual counted quantity, min 0
- **Variance Quantity** (auto-computed) — `physical_qty - system_qty`; GENERATED ALWAYS AS stored column in DB; positive = surplus, negative = deficit
- **Unit Cost** (optional) — Valuation rate per unit

## Business Rules

### Status Lifecycle
```
draft ──[submit]──→ submitted ──[approve]──→ approved (ledger posted)
                          │
                          └──[reject]──→ rejected
```
- **draft**: Editable, deletable; items can be modified
- **submitted**: Pending manual approval (or auto-approved)
- **approved**: Ledger entries posted, stock balances updated
- **rejected**: Rejected with reason

### Submit with Auto-Approve (Threshold Check)
When `StockAdjustmentService::submit()` is called:
1. Guards: status must be `draft`, items must exist
2. For each item, checks `variance` against `stockItem.variance_threshold`
3. If ALL variances are within threshold → auto-approves (calls `approve()` directly)
4. If ANY variance exceeds threshold → status = `submitted` (needs manual approval)

### Approve with Ledger Posting
`StockAdjustmentService::approve()` inside a DB transaction:
1. Guards: status must be `submitted`
2. For each item with meaningful variance (abs > 0.001):
   - Positive variance → inward ledger entry (stock surplus)
   - Negative variance → outward ledger entry (stock deficit)
3. Posts entry to `inv_stock_entries` via `StockLedgerService`
4. Sets status = `approved`, records approved_by + approved_at
5. Fires `StockAdjusted` event

### Delete Guard
Only draft adjustments can be deleted. Non-draft adjustments throw DomainException.

### Update Guard
Only draft adjustments can be updated (abort 422). Update replaces all items.

### Variance Column
`inv_stock_adjustment_items.variance_qty` is a `GENERATED ALWAYS AS (physical_qty - system_qty) STORED` column — it is DB-computed and must not be manually inserted or updated.

### Number Generation
Adjustment numbers generated by `StockAdjustmentService::generateAdjustmentNumber()`: `ADJ-YYYY-NNNN`.

### Service Layer
`StockAdjustmentService`:
- `create()`: Generates number, sets status=draft, creates items, logs activity
- `submit()`: Guards draft + items>0, auto-approves if within threshold, else sets submitted
- `approve()`: Guards submitted, posts ledger entries, updates status, fires event
- `reject()`: Guards submitted, sets status=rejected
- `delete()`: Guards draft, soft-deletes items + header

### Cross-Module Dependencies
- `godown_id` references `inv_godowns` (Inventory) — hard FK
- `item_id` references `inv_stock_items` (Inventory) — hard FK
- `stockItem.variance_threshold` — per-item threshold for auto-approval logic
- Stock ledger entries reference `inv_stock_entries` (append-only, BR-INV-014)

## Workflow

1. Staff navigates to Inventory → Stock Movement → Adjustments tab
2. Staff creates a new adjustment (draft) with date, godown, reason, and items with counted quantities
3. Staff submits the adjustment
4. System checks variances against thresholds:
   - If all within threshold → auto-approved, ledger updated immediately
   - If any exceed threshold → submitted for manual approval
5. Authorized staff approves the adjustment → ledger entries posted, stock corrected
6. Staff can view adjustment details with variance impact

- MUST authorize via `tenant.inventory.stock-adjustment.*` policy gates (6 gates including approve)
- MUST validate store with 9+ rules including nested items (min:1)
- MUST generate unique adjustment_number in format ADJ-YYYY-NNNN
- MUST create adjustment with status=draft by default
- MUST calculate variance_qty as physical_qty - system_qty (GENERATED ALWAYS column)
- MUST guard submit: only draft adjustments with ≥1 items can be submitted
- MUST support auto-approve when all variances are within stockItem.variance_threshold
- MUST require manual approval when any variance exceeds threshold
- MUST guard approve: only submitted adjustments can be approved
- MUST post inward/outward ledger entries on approval based on variance sign
- MUST skip zero-variance items during ledger posting
- MUST guard reject: only submitted adjustments can be rejected
- MUST guard update: only draft adjustments can be updated
- MUST guard delete: only draft adjustments can be deleted (DomainException)
- MUST support soft-delete lifecycle
- MUST fire StockAdjusted event on approval
- MUST log all CRUD and lifecycle operations via activityLog()
