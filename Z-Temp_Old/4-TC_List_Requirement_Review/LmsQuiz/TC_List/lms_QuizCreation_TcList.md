## 2. Pre-conditions

- Required permission: `tenant.quiz.viewAny` (to view list)
- Required seed data: Assessment Types, Difficulty Configs, Classes, Subjects, Lessons, Topics, Academic Sessions, Question Usage Types
- Quiz code is auto-generated from Academic Session + Class + Subject + Lesson + Topic codes + random 4 chars
- Form uses 2-tab layout (Basic Information → Quiz Configuration) with JS-driven cascading dropdowns (Class → Subject → Lesson → Topic hierarchy)

## 4. Test Data Strategy

- **Quiz Code**: Verify auto-generated code follows format: `QUIZ_{SESSION}_{CLASS}_{SUBJECT}_{LESSON}_{TOPIC}_{RANDOM4}` — generated by both controller `store()` and model `boot() creating()` (duplicate logic)
- **Status Field**: Status is a free-form select on create/edit form (DRAFT/PUBLISHED/ARCHIVED). `publish()` action enforces DRAFT→PUBLISHED and requires `total_questions > 0`
- **Difficulty Config Cascade**: Ignore Difficulty Config toggle disables dropdown. Config dropdown is static (all active configs)
- **Soft Delete + Restore**: `destroy()` sets `is_active=false` and `status='ARCHIVED'` before `delete()`. `restore()` calls `restore()` then sets `is_active=true`
- **Usage Check**: `QuizUsageCheckService` checks `QuizAllocation::where('quiz_id',$id)->count()`. Used in edit/update/destroy to block actions when allocations exist
- **Force Delete**: `forceDelete()` checks allocations, attempts, results dependencies before allowing
- **Boolean Switches**: 10 boolean toggle fields, all converted via `prepareForValidation()` using `$this->boolean()`
- **Topic Hierarchy**: 4-level cascading dropdowns (Topic → Sub-Topic → Mini Topic → Micro Topic) driven by AJAX
- **Academic Hierarchy**: Academic Session → Class → Subject → Lesson → Topic

### 5.4 Business Logic

| BC ID | Condition | Expected Behavior |
|-------|-----------|-------------------|
| BC-BIZ-01 | Create quiz — all required fields | Quiz created; quiz_code auto-generated as `QUIZ_{session}_{class}_{subject}_{lesson}_{topic}_{random4}` |
| BC-BIZ-02 | Create quiz — code generation in store() and boot() | Both controller `store()` and model `boot() creating()` generate code — potential duplicate. Model boot runs after controller sets it |
| BC-BIZ-03 | Publish quiz — total_questions=0 | Blocked: "Cannot publish a quiz with no questions." (check: `!$quiz->total_questions \|\| $quiz->total_questions < 1`) |
| BC-BIZ-04 | Publish quiz — already PUBLISHED | Redirect back with info: "Quiz is already published." |
| BC-BIZ-05 | Publish quiz — success | Status changed to PUBLISHED; activity log "Published" event |
| BC-BIZ-06 | Edit quiz — has allocations (any status) | Edit form redirects with error: "cannot be edited" via `QuizUsageCheckService::isUsed()` |
| BC-BIZ-07 | Edit quiz — no allocations | Full edit form rendered; all fields available |
| BC-BIZ-08 | Update quiz — has allocations | Update blocked with error via `QuizUsageCheckService::isUsed()` |
| BC-BIZ-09 | Update quiz — no allocations | Update proceeds; changes logged via activityLog with before/after values |
| BC-BIZ-10 | Destroy quiz — has allocations | Destroy blocked with error via `QuizUsageCheckService::isUsed()` |
| BC-BIZ-11 | Destroy quiz — no allocations | Soft delete: sets `is_active=false`, `status='ARCHIVED'`, calls `$quiz->delete()` |
| BC-BIZ-12 | Restore deleted quiz | `$quiz->restore()`, then sets `is_active=true`; activity log "Restored" |
| BC-BIZ-13 | Force delete — has allocations/attempts/results | Blocked: "Cannot permanently delete quiz because it has associated allocations or student attempts." |
| BC-BIZ-14 | Force delete — no student data | `$quiz->quizQuestions()->forceDelete()` then `$quiz->forceDelete()` in transaction |
| BC-BIZ-15 | Quiz code auto-generation format | `QUIZ_{SESSION_CODE}_{CLASS_CODE}_{SUBJECT_CODE}_{LESSON_CODE}_{TOPIC_CODE}_{RANDOM4}` — all upper, random is `Str::random(4)` |
| BC-BIZ-16 | Form: Class → Subject cascading | On class_id change, AJAX call to `getSubjectsByClass()` loads subjects filtered by class |
| BC-BIZ-17 | Form: Subject → Lesson cascading | On subject_id change, AJAX call to `getLessons()` loads lessons filtered by class+subject |
| BC-BIZ-18 | Form: Lesson → Topic hierarchy | 4-level cascading (Topic/Sub-Topic/Mini Topic/Micro Topic) via `getTopicHierarchy()` AJAX |
| BC-BIZ-19 | timer_enforced toggle hides duration_minutes | When unchecked, duration_minutes field hidden via JS |
| BC-BIZ-20 | allow_multiple_attempts toggles max_attempts | When unchecked, max_attempts disabled; when checked, enabled |
| BC-BIZ-21 | ignore_difficulty_config disables difficulty_config_id | When checked, difficulty_config_id disabled |
| BC-BIZ-22 | publish() uses `tenant.quiz.update` gate | Not the dedicated `tenant.quiz.publish` gate (Policy defines it but controller doesn't use) |
| BC-BIZ-23 | toggleStatus() uses `tenant.quiz.update` gate | AJAX endpoint for active/inactive toggle |
| BC-BIZ-24 | show() displays usage details | Calls `QuizUsageCheckService::getUsageDetails()` and displays allocations count in warning card |
| BC-BIZ-25 | show() only shows Edit button when no allocations | `@can('tenant.quiz.update')` AND `empty($usageDetails['Allocations'])` |
| BC-BIZ-26 | Status field is free-form in create/edit | User can set any status (DRAFT/PUBLISHED/ARCHIVED) directly in the form |

## 8. Known Issues

| # | Issue | Severity | Details |
|---|-------|----------|---------|
| KI-01 | Duplicate quiz_code generation logic | Medium | Both controller `store()` and model `boot() creating()` generate quiz_code. Model boot runs after controller sets it, potentially generating a different code than what controller prepared. Recommend removing one. |
| KI-02 | Unused Policy gates (`status`, `publish`) | Low | QuizPolicy defines `status()` and `publish()` methods checking `tenant.quiz.status` and `tenant.quiz.publish`, but controller uses `tenant.quiz.update` for publish() and toggleStatus(). These gates are dead code. |
| KI-03 | Status field allows any transition via edit form | Medium | The status field in create/edit form allows selecting any value (DRAFT/PUBLISHED/ARCHIVED) without validation. User can change PUBLISHED→DRAFT or ARCHIVED→PUBLISHED directly, bypassing publish() business rules. |
| KI-04 | QuizUsageCheckService counts allocations without status filter | Low | `isUsed()` checks for ANY allocation regardless of allocation status. A cancelled/inactive allocation still blocks edit/delete. |
| KI-05 | No `is_system_generated` edit protection | Medium | Despite the field existing on the model, there is NO gate or check preventing edit/delete of system-generated quizzes. The old TC assumed a `isSystemGeneratedNotEditable` gate that doesn't exist in code. |
| KI-06 | toggleStatus() lacks existence check | Low | If quiz ID doesn't exist, `withTrashed()->findOrFail($id)` throws ModelNotFoundException → 500 error instead of 404. |
| KI-07 | duration_minutes nullable in validation, integer in DB | Low | DB allows NULL, validation allows nullable. If form submits without duration and timer_enforced=false, DB gets 0 (migration default). Edge case: NULL vs 0 behavior. |
| KI-08 | QuizRequest reused for both store and update | Low | Same validation rules apply for both methods. `sometimes` rule not used; all fields are `required` for both POST and PUT, forcing all fields to be submitted on update. |
| KI-09 | No dedicated archive route | Low | No `POST /quize/{quiz}/archive` endpoint. Archiving done by setting status field directly via edit form or through destroy() which always sets ARCHIVED. |
| KI-10 | show() loads QuizUsageCheckService before Gate authorize | Low | `$usageCheck = new QuizUsageCheckService(); $usageDetails = $usageCheck->getUsageDetails($id);` runs BEFORE `Gate::authorize('tenant.quiz.view')`. Unnecessary DB query if user lacks permission. |
