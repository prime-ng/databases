# Compliance — Business Requirements

## What This Screen Does

The Compliance screen manages statutory compliance records for employees across five types: Provident Fund (PF), Employee State Insurance (ESI), Tax Deducted at Source (TDS), Gratuity, and Profession Tax (PT). It also provides two aggregated register reports showing the PF and ESI contribution registers for a selected month/year, consolidating all employees' contribution details.

## When This Screen Is Used

- When HR Manager enrolls a new employee in PF scheme and records their UAN
- When HR Manager sets up ESI coverage for eligible employees
- When HR Manager configures TDS parameters (tax regime, 80C, HRA, LTA)
- When HR Manager records gratuity nominee details
- When HR Manager configures Profession Tax applicability per state
- When the Payroll Manager views the PF contribution register aggregated by month
- When the Payroll Manager views the ESI contribution register aggregated by month

## Default Data Load

Compliance has two entry points:

**Employee-Level Compliance:** Loaded by `ComplianceController::show()` at `GET /hr-staff/employees/{employee}/compliance/{type}`. The URL parameter `{type}` must be one of: `pf`, `esi`, `tds`, `gratuity`, `pt`. The controller validates the type via `validateComplianceType()`. The `ComplianceService::getByType()` returns the active record matching employee_id + compliance_type, or null if none exists. The view renders the form with the existing data or an empty form for creation.

**Register Reports:** Loaded by `ComplianceController::pfRegister()` at `GET /hr-staff/compliance/pf-register` and `esiRegister()` at `GET /hr-staff/compliance/esi-register`. Default month = current month, year = current year from `$request->input('month', now()->month)` and `$request->input('year', now()->year)`.

## Key Fields at a Glance

**Compliance Record (per employee per type)**
- `compliance_type` — One of: pf, esi, tds, gratuity, pt
- `reference_number` — Encrypted identifier: UAN for PF, IP number for ESI, PAN for TDS (encrypted via SafeEncrypted cast)
- `enrollment_date` — Date the employee was enrolled in the statutory scheme
- `applicable_flag` — Boolean: whether this compliance type applies to the employee
- `nominee_json` — JSON array of nominees: each with name, relationship, and share percentage (for PF and Gratuity)
- `details_json` — Type-specific extras: TDS → {regime, 80C, HRA, LTA}; PT → {state_code}; ESI → {dispensary}

**PF Contribution Register (aggregated)**
- Employee details, basic wage, employee PF contribution (12%), employer EPF (3.67%), employer EPS (8.33%), NCP days, status (computed/submitted/challan_generated)

**ESI Contribution Register (aggregated)**
- Employee details, gross wage, employee ESI contribution (0.75%), employer contribution (3.25%), status (computed/submitted/challan_generated)

## Business Rules and Conditions

**Compliance Type Validation.** The `{type}` route parameter is validated against a whitelist: `pf`, `esi`, `tds`, `gratuity`, `pt`. Any other value returns 404 "Invalid compliance type: {type}".

**One Record Per Type Per Employee.** Each employee can have at most one compliance record per type. The UPSERT logic in `ComplianceService::upsert()` uses `updateOrCreate()` with the composite key `[employee_id, compliance_type]`, and the database enforces a UNIQUE constraint on `(employee_id, compliance_type)`.

**Upsert Behaviour.** The `store()` and `update()` methods both call the same `ComplianceService::upsert()` method. `update()` is an alias that delegates to `store()`. The `upsert()` method runs within a DB transaction and uses `updateOrCreate()` with `compliance_type`, `employee_id` as the match keys, merging `is_active = true`, `created_by`, `updated_by` into the data.

**Reference Number Encryption.** The `reference_number` field uses the `SafeEncrypted` cast, ensuring sensitive identifiers (UAN, IP, PAN) are encrypted at rest.

**Register Reports Are Read-Only.** The PF and ESI register pages display aggregated computed data from `hrs_pf_contribution_register` and `hrs_esi_contribution_register` tables. These records are generated by the payroll computation engine and are not editable from the compliance screens.

**Store/Update Redundancy.** Both `store()` and `update()` methods exist on the controller, but `update()` simply delegates to `store()`. Both use the same `StoreComplianceRecordRequest` and the same upsert logic.

## Workflow Steps

**Recording PF Compliance for an Employee**
1. HR Manager navigates to Employee → Payroll → Compliance, selects type "PF"
2. If no record exists, an empty form is shown
3. HR Manager enters the employee's UAN as reference_number, enrollment date, sets applicable_flag, adds nominee details
4. System validates, upserts the record, logs activity, redirects with success message

**Viewing PF Contribution Register**
1. Payroll Manager navigates to Payroll → Compliance Registers → PF Register
2. System loads with current month/year as defaults
3. Payroll Manager can change month/year filters to view historical data
4. System displays the aggregated register table

Sunshine Academy enrolls new teacher Priya Sharma in PF scheme. HR Manager opens her compliance screen, selects type "pf", enters UAN "123456789012", sets enrollment_date = "2025-07-01", adds nominee with 100% share to spouse. Later, the Payroll Manager views the PF register for July 2025 and sees Priya's record alongside all other PF-enrolled employees with their computed contributions.

## Requirements

- `ComplianceController` handles requests with methods: `show()` (lines 25–34), `store()` (lines 39–55), `update()` (lines 60–63), `pfRegister()` (lines 68–78), `esiRegister()` (lines 83–93)
- `show()` validates type, calls `ComplianceService::getByType($employee->id, $type)`, renders view
- `store()` and `update()` both call `ComplianceService::upsert($employee->id, $type, $request->validated())`; `update()` is an alias for `store()`
- `pfRegister()` loads `ComplianceService::getPfRegister($month, $year)` which queries `PfContributionRegister::with('complianceRecord.employee')->active()->where('month', $month)->where('year', $year)->orderBy('compliance_record_id')->get()`
- `esiRegister()` loads `ComplianceService::getEsiRegister($month, $year)` which queries `EsiContributionRegister::with('complianceRecord.employee')->active()->where('month', $month)->where('year', $year)->orderBy('compliance_record_id')->get()`
- `validateComplianceType(string $type)` aborts with 404 if type not in `['pf', 'esi', 'tds', 'gratuity', 'pt']`
- Route names: `hr-staff.compliance.pf-register` (GET), `hr-staff.compliance.esi-register` (GET), `hr-staff.compliance.show` (GET), `hr-staff.compliance.store` (POST), `hr-staff.compliance.update` (PUT)
- All methods gate for `hrs.compliance.manage`
- `StoreComplianceRecordRequest` validates: `reference_number` (nullable, string, max:100), `enrollment_date` (nullable, date), `applicable_flag` (required, boolean), `nominee_json` (nullable, array) with sub-fields name/relationship/share_pct, `details_json` (nullable, array); `prepareForValidation()` normalizes `applicable_flag` via `$this->boolean('applicable_flag', true)`
- Activity logged on create/update (type 'Saved') with message "Compliance record saved."
- Policy: `CompliancePolicy` — defines viewAny, view, create, update, delete, restore, forceDelete; all check `hrs.compliance.manage`

| Gate/Permission | Methods | Notes |
|-----------------|---------|-------|
| `hrs.compliance.manage` | `show()`, `store()`, `update()`, `pfRegister()`, `esiRegister()` | Required for all compliance operations |
| Policy | `CompliancePolicy` | viewAny, view, create, update, delete, restore, forceDelete — all check `hrs.compliance.manage` |

## Logic Flow

**Page Load (`show()`).** Route-model-binding loads Employee. Gates for `hrs.compliance.manage`. Validates `$type` via `validateComplianceType()`. Calls `ComplianceService::getByType($employee->id, $type)` returning the record or null. Renders view with employee, type, and record.

**Create/Update (`store()` / `update()`).** Gates for `hrs.compliance.manage`. Validates `$type`. Validates via `StoreComplianceRecordRequest` (which also gates). Calls `ComplianceService::upsert()` which wraps `ComplianceRecord::updateOrCreate()` in a transaction with `employee_id` and `compliance_type` as match keys, and `is_active = true`, `created_by`, `updated_by` merged into data. Activity logged. Redirects to show page with success message.

**PF Register (`pfRegister()`).** Gates for `hrs.compliance.manage`. Reads `month` and `year` query params (defaults to current values). Calls `ComplianceService::getPfRegister()` which queries `PfContributionRegister` with eager-loaded `complianceRecord.employee`, filtered by active, month, year, ordered by `compliance_record_id`. Renders view.

**ESI Register (`esiRegister()`).** Same flow as PF register but for `EsiContributionRegister`.

## Validate Before Save

| Field | Rule(s) | Error Message |
|-------|---------|---------------|
| `reference_number` | `nullable`, `string`, `max:100` | "The Reference Number (UAN/IP/PAN) must not exceed 100 characters." |
| `enrollment_date` | `nullable`, `date` | "The Enrollment Date is not a valid date." |
| `applicable_flag` | `required`, `boolean` | "The Applicable field is required." |
| `nominee_json` | `nullable`, `array` | "The nominee_json must be a valid array." |
| `nominee_json.*.name` | `nullable`, `string`, `max:100` | — |
| `nominee_json.*.relationship` | `nullable`, `string`, `max:50` | — |
| `nominee_json.*.share_pct` | `nullable`, `numeric`, `min:0`, `max:100` | — |
| `details_json` | `nullable`, `array` | "The details_json must be a valid array." |

`prepareForValidation()` normalizes `applicable_flag` to boolean with default `true`.

## Success Scenarios

**SC-001 — Create PF Compliance Record.** HR Manager creates a PF compliance record for employee ID 5. Enters reference_number = "UAN1234567890", enrollment_date = "2025-07-01", applicable_flag = true, nominee with name "Raj Sharma", relationship "Spouse", share_pct = 100. System upserts the record, logs activity, redirects with success "pf compliance record saved successfully."

**SC-002 — View PF Register.** Payroll Manager views PF register for July 2025. System displays all PF-enrolled employees with their basic wage, contributions, NCP days, and filing status.

**SC-003 — Update Compliance Type.** HR Manager updates the existing TDS compliance record for employee ID 5, changing applicable_flag from true to false. System upserts (updates) the record, logs activity, redirects with success.

## Failure Scenarios

**FC-001 — Invalid Compliance Type.** User accesses `/compliance/xyz` (invalid type). System returns 404 "Invalid compliance type: xyz."

**FC-002 — Missing Permission.** User without `hrs.compliance.manage` attempts to access any compliance route. Returns 403 "This action is unauthorized."
