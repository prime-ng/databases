# [Student Groups] Master Tab Screen

---

## What Does This Screen Do?

The Student Groups screen is where school administrators define pre-set groups of students drawn from a specific class and section. These groups are NOT about organizing students socially — they are a critical tool for exam allocation. When a school wants to give different question papers to different subsets of students within the same class (to prevent copying), they create student groups.

For example, Class 9-A has 40 students. For the Annual Exam, the school wants to split these 40 students into two groups — "Group SET-A" (20 students) and "Group SET-B" (20 students) — and assign different paper sets to each group. The Student Groups screen is where you create these two containers. The Group Members screen is where you put individual students into each container.

Each student group has:
- A **Class** and **Section** it belongs to (e.g., Class 9, Section A)
- A **Code** — an auto-generated identifier like `GRP_9_A_X7K2`
- A **Name** — a descriptive name like "Class 9th-A, Group SET-A"
- A **Description** — optional notes about the group's purpose
- A list of **Members** — the actual students (managed on the Group Members screen)

---

## Real-Life Example

Mr. Kumar, the Exam Coordinator at Sunshine International School, is setting up for the Half-Yearly Exam. Class 10-B has 50 students. He wants to split them into two groups to assign different paper sets.

He opens the Masters tab, clicks the "Student Groups" sub-tab (third tab), and clicks "Add Group." He selects Class 10, Section B, enters the name "Class 10-B Group SET-A", and lets the system auto-generate the code `GRP_10_B_H8K3`. He saves.

He repeats for a second group: "Class 10-B Group SET-B" with code `GRP_10_B_M9P1`.

Now he goes to the Group Members screen and puts 25 students in SET-A and 25 in SET-B. Later, when allocating exams, he assigns Paper Set A to Group SET-A and Paper Set B to Group SET-B.

Later, the school decides to discontinue one of the groups because students were re-sectioned. Mr. Kumar tries to delete the group, but the system blocks him because the group is already allocated to exams. He must first remove the exam allocation before deleting the group.

## How the List Page Works

The Student Groups index is the third sub-tab inside the Masters tab (`active_tab=exam_student_group`). It loads a paginated list immediately — unlike Group Members, you don't need to apply filters first.

### Filters Available
- **Class** — Filter by a specific class (dropdown)
- **Section** — Filter by a specific section (dropdown)
- **Active Status** — Show only active or inactive groups (dropdown)
- **Search** — Free-text search across group code, name, description, and class name/code

### Columns Displayed
- **Code** — The unique group code (e.g., `GRP_9_A_X7K2`)
- **Name** — The group's display name
- **Class** — The associated class
- **Section** — The associated section
- **Description** — Optional notes
- **Active** — Status toggle (AJAX)
- **Actions** — View, Edit, Delete

### Pagination
10 rows per page. The list is ordered newest-first.

### Trash Page
A separate page showing soft-deleted groups. From here you can Restore or Force Delete.

## How to Create

**Step 1:** Open the Masters tab, click "Student Groups" sub-tab, then click "Add Group."

**Step 2:** Fill in the form:
- **Class** (Required) — Select from the dropdown of all active classes in the school.
- **Section** (Required) — Select from the dropdown of all active sections.
- **Code** (Required) — This can be auto-generated by the system. The auto-generation format is:
  `GRP_{CLASSCODE}_{SECTIONCODE}_{RANDOM4}` → e.g., `GRP_9_A_X7K2`
  If the generated code already exists in the database, the system appends `_1`, `_2`, etc. until it finds a unique one.
  
  **IMPORTANT:** The auto-generation logic is implemented in the model's `generateCode()` static method. HOWEVER, the store() method has the code generation COMMENTED OUT — meaning when creating a new group, the code is NOT auto-generated unless the user enters it manually. The update() method DOES have auto-generation enabled (if code is left empty on update, it gets auto-generated). This appears to be a discrepancy/bug where auto-generation only works on edit, not on create.

- **Name** (Required) — A descriptive name like "Class 9-A Advanced Group" (max 100 characters).
- **Description** (Optional) — Any notes about the group's purpose (max 255 characters).
- **Active** — Checked by default.

**Step 3:** Click "Create." The system:
1. Validates the form (via ExamStudentGroupRequest)
2. Creates the group record in the database
3. Logs the activity: "A new exam student group was created."
4. Redirects back to the Masters tab with a success message

### What the Form Request Validates
- `class_id` — Required, must exist in sch_classes table
- `section_id` — Required, must exist in sch_sections table
- `code` — Required, max 100 characters (NO unique validation at FormRequest level — uniqueness is NOT enforced here!)
- `name` — Required, max 100 characters
- `description` — Optional, max 255 characters
- `is_active` — Boolean (converted from checkbox)

### In Plain English: Code Uniqueness Gap
The FormRequest does NOT have a `unique` rule on the `code` column. This means two groups CAN technically be created with the same code through the form. The only uniqueness safeguard is the model's `generateCode()` method (which checks for existing codes when auto-generating), but that method is NOT called on create (it's commented out in store()). On update, code generation IS active and checks uniqueness. This is a gap in the current implementation.

## How to Edit/Delete

### Editing
Click the Edit button (pencil icon) next to a group. Before the edit form opens, the system checks usage.

**Usage Check Logic:**
The `ExamStudentGroupUsageCheckService` checks two things:
1. Whether the group is referenced in any `lms_exam_allocations` (allocated to an exam)
2. Whether the group has any members in `lms_exam_student_group_members`

If EITHER exists, editing is blocked: "Cannot edit this group because it is allocated to exams."

Wait — this is important. The usage check for editing counts MEMBERS as "usage." This means even if a group is NOT allocated to any exam, but it HAS members, you CANNOT edit it. Is this intentional? Looking at the code:
```php
public function getUsageCount($groupId): int {
    $allocationsCount = ExamAllocation::where('exam_group_id', $id)->count();
    $membersCount = ExamStudentGroupMember::where('group_id', $id)->count();
    return $allocationsCount + $membersCount;
}
```
Yes — members are counted as usage. So a group with members is considered "in use" and cannot be edited or deleted, even if it has no exam allocations. This is stricter than what the original requirement described.

If allowed: The edit form opens with current values pre-filled. After saving, the system logs changes with old/new value comparisons.

### Deleting (Soft Delete)
Click Delete → Usage check → If blocked, error shown. If allowed:
1. The system sets `is_active = false` (deactivates the group)
2. Then soft-deletes the record (sets `deleted_at` timestamp)
3. Logs: "Exam student group was deactivated and trashed."
4. Redirects with success

The group's members are NOT automatically deleted — they remain in the database with their `group_id` still pointing to the soft-deleted group. This means the member records become orphaned references.

### Restoring from Trash
Usage check again → If the group is STILL allocated to exams or has members, restore is blocked. If allowed:
1. Restores the record (`deleted_at = null`)
2. Sets `is_active = true` (reactivates)
3. Logs and redirects

### Force Delete (Permanent)
Same usage check → If passed, permanently removes the record. No recovery possible.

### Toggle Active Status (AJAX)
The green/red toggle switch on each row sends an AJAX request to toggle `is_active`. No usage check is performed — you can deactivate a group even if it's allocated to exams. The toggle just hides it from dropdowns.

## Business Rules Summary

| # | Rule | Details |
|---|------|---------|
| 1 | **Class + Section Required** | Every group must belong to a specific class and section. |
| 2 | **Code Uniqueness (Partial)** | The `generateCode()` method ensures unique codes when auto-generating, but the FormRequest does NOT enforce unique codes on manual entry. |
| 3 | **Usage Check Blocks Edit/Delete/Restore/ForceDelete** | If a group has exam allocations OR members, all destructive operations are blocked. |
| 4 | **Usage Check NOT on Toggle** | The AJAX status toggle is always allowed, even if the group is in use. |
| 5 | **Deactivation on Delete** | Soft-delete automatically deactivates the group (`is_active = false`). |
| 6 | **Reactivation on Restore** | Restore automatically reactivates the group (`is_active = true`). |
| 7 | **Code Auto-Generation (Update Only)** | The `generateCode()` is called on update() but is COMMENTED OUT on store() — auto-generation does NOT work on create. |
| 8 | **Members Are Usage** | Having members alone (even without allocations) blocks editing and deletion. |
| 9 | **Show Page Shows 20 Members** | The details page loads only the first 20 members. |
| 10 | **Search Across Related Data** | Search filters through code, name, description, AND class name/code. |

## Technical Implementation Details

### Database Table: `lms_exam_student_groups`

| Column | Type | Details |
|--------|------|---------|
| id | INT UNSIGNED PK | Auto-increment |
| class_id | INT UNSIGNED FK | References `sch_classes.id` |
| section_id | INT UNSIGNED FK | References `sch_sections.id` |
| code | VARCHAR(50) | Group code (e.g., `GRP_9_A_X7K2`) |
| name | VARCHAR(100) | Display name |
| description | VARCHAR(255) NULL | Optional notes |
| is_active | TINYINT(1) | Default 1 |
| created_at / updated_at / deleted_at | TIMESTAMP | Soft deletes |

**Unique Constraint:** `(class_id, section_id, code)` — at database level, no two groups with the same code can exist in the same class-section combination. **However**, the FormRequest does NOT validate this — uniqueness is only enforced by the database's unique index, meaning a duplicate entry will cause a database-level SQL error rather than a clean validation message.

### Code Generation Logic (`generateCode()`)
The model has a static method to auto-generate unique codes:
1. Builds a base code: `GRP_{CLASSCODE}_{SECTIONCODE}_{RANDOM4}`
   - If no class: uses `CLS` instead of class code
   - If no section: uses `ALL` instead of section code
   - Random 4 characters: uppercase alphanumeric (Str::random(4) + Str::upper())
2. Checks if the base code already exists in the database
3. If it exists, appends `_1`, `_2`, etc. until a unique code is found
4. Returns the unique code

**Current Implementation Gap:**
- In `store()` (create): The code generation is COMMENTED OUT — no auto-generation happens
- In `update()` (edit): Code generation IS active — if code is left empty on edit, it gets auto-generated
- The FormRequest does NOT include a unique rule for the `code` field
- This means:
  - On CREATE: user must enter a code manually, and there's no validation preventing duplicates
  - On EDIT: if user clears the code field, it gets auto-generated uniquely
  - In both cases, the database unique index is the last line of defense

### Data Loading Architecture
The `ExamStudentGroupController@index()` method:
1. Authorizes the user
2. Builds a query via `queryBuilder()` with filters (class_id, section_id, search, is_active)
3. Paginates at 10 rows per page
4. Loads class and section relationships
5. Passes all active classes and sections to the view for filter dropdowns

The same query can also be built by `ExamQueryService@examStudentGroupsQuery()` from the Masters tab.

### Search Behavior
The search filter searches across:
- Group code (`GRP_9_A_X7K2`)
- Group name
- Group description
- Class name AND class code (via relationship)
- Section name (via relationship)

This means searching "9" will find groups belonging to Class 9 even if the group name doesn't contain "9."

### Show Page Details
When viewing a single group (`show($id)`):
1. Finds the group or returns 404
2. Runs usage check (is it allocated? does it have members?)
3. If used, loads usage details (allocation count and member count)
4. Loads the first 20 members with their student information
5. Renders the show view with all this data

### Transaction Handling
Every mutating method uses database transactions:
- `store()` — Create + activity log
- `update()` — Update + change detection + activity log
- `destroy()` — Deactivate + soft-delete + activity log
- `restore()` — Restore + reactivate + activity log
- `forceDelete()` — Force delete + activity log
- `toggleStatus()` — Save toggle + activity log

If any step fails within a transaction, all changes are rolled back.

### Usage Check Service: Dual Check
The `ExamStudentGroupUsageCheckService` counts TWO things:
1. `ExamAllocation::where('exam_group_id', $id)->count()` — How many exam allocations use this group?
2. `ExamStudentGroupMember::where('group_id', $id)->count()` — How many members belong to this group?

If EITHER count > 0, the group is "in use." This means a group with just 1 member (and zero allocations) is still locked from editing or deletion.

### The is_active Cast
The model casts `is_active` as `boolean`, which means:
- When reading: 1 becomes `true`, 0 becomes `false`
- When writing: `true` becomes 1, `false` becomes 0
- The FormRequest also converts the checkbox value to boolean in `prepareForValidation()`
